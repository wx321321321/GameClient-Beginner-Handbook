# 网络同步链路

[返回本章目录](README.md) · [返回手册首页](../README.md)

原项目的同步框架可沿五条线阅读：同 EntityID 的实体镜像、AOI 决定接收范围、Property 同步状态、RPC 传递请求或事件、独立通道同步高频位置。本文中的类名、flag、回调和发送周期均来自原项目笔记；仓库未附对应源码，需与实际版本核对。

## 先创建可对应的实体镜像

服务端有权威的 `CombatAvatar`，客户端创建与它对应、使用同一个 `EntityID` 的代理。它们不共享内存，只同步协议规定的数据。

```text
服务器 CombatAvatar（EntityID = X）
           ↓ 创建与后续同步
客户端 CombatAvatar / PlayerCombatAvatar（EntityID = X）
```

原项目里主控玩家通常是 `PlayerCombatAvatar`，其他玩家是普通客户端 `CombatAvatar`。因此“同 ID”不必然意味着两端 C++/Python 具体类型完全相同；ID 是对应关系，端侧类型承担不同职责。

## AOI 管理代理对象的可见生命周期

服务器不会把全地图全部实体发给每个客户端。某个实体进入观察者的兴趣范围时：

```text
发送实体创建信息
→ 客户端建立对应 Entity
→ 下发该客户端有权接收的初始 Property
→ 此后接收属性增量、事件和位置更新
```

离开范围时，原项目代理执行 `on_out_sight`，再进入销毁流程。初始数据与增量的顺序必须由协议保证，不能让尚未创建的实体直接消费增量。

这里的 `ALL_CLIENTS` 按原项目约定通常指符合 AOI 可见条件的客户端，不是全服务器广播。如何维护进入、离开及反向观察者表，见 [AOI 兴趣区域管理](aoi.md)。

## Property：从声明到表现回调

注册示例：

```python
Property("hp", 100, Property.ALL_CLIENTS)
Property("ammo", 30, Property.OWN_CLIENT)
```

原笔记中，`PropertyMetaClass` 在注册 Entity 类时收集属性名、默认值、同步标记，再注册到原生 `asiocore`。字段编号和编码由该套框架处理，不应当成 UE 的 UPROPERTY 复制机制。

```text
服务器修改 Property
→ asiocore 检测/记录变化
→ 编码 EntityID + 属性索引或路径 + 操作 + 新值
→ 按同步 flag 与观察范围选择客户端
→ 客户端更新相应 Property
→ ClientEntity.on_setattr
→ 分发到 _on_set_hp 等约定回调
→ 刷新血条、模型等表现
```

| 标记 | 原项目记录的含义 |
| --- | --- |
| `SERVER_ONLY` | 服务端数据，不向客户端同步 |
| `OWN_CLIENT` | 发给该实体所属的主控客户端 |
| `ALL_CLIENTS` | 发给符合该实体 AOI 可见条件的客户端 |
| `SPECTATOR_*` | 对应观战接收范围，具体子标记按项目定义 |
| `PERSISTENT` | 还需要持久化；它不等于网络接收范围 |

要排查“服务器改了，但客户端没变”，应沿这条链检查：字段是否注册、变化是否被记录、接收者是否符合范围、客户端字段是否更新、表现回调是否执行。

## RPC：传达一次请求或事件

攻击请求、进入射击状态等行为可以通过 RPC 传递。Property 适合描述“目前血量是多少”，事件适合描述“发生了一次开火”。两者经常协作：请求触发服务端计算，计算结果再表现为属性变化。

原稿没有记录 RPC 的可靠性、顺序和重发语义，不能仅凭名字推断。具体开火例子见[射击框架与开火链路](shooting-pipeline.md)。

## 位置为什么走独立通道

原项目的位置链路记录为：

```text
主控客户端即时移动
→ 按固定间隔上传移动结果
→ 服务器检查并保存
→ 转发给其他观察者
→ 必要时修正或拉回主控客户端
```

这描述的是原项目的客户端上报方案，不代表所有状态同步游戏都信任客户端位置。服务端校验的内容、容差和权威范围需要源码佐证。

### 本地一帧移动与一次发送不是同一频率

```text
输入系统
→ 角色移动逻辑
→ CharacterController
→ 按实际依赖整合碰撞、重力、Graph 和根运动
→ 得到 Entity 的最终 Transform
```

本地表现可能每画面帧更新，`posesendercomponent` 则按发送间隔上传。原笔记记录约 **33 ms** 一次，人多时频率可能下降；这是项目配置线索，不能当成稳定协议常量。

PoseSender 的工作顺序是：

```text
本帧位置更新结束
→ 调用 PoseSender
→ 累计距上次发送的时间
→ 达到发送间隔
→ 读取最终位置和 yaw
→ 判断是否有需要上报的变化
→ 调用 area 的发送回调
```

### 接收端只有采样点，无法还原所有运动细节

保留原笔记的离散例子。以下“帧”只是用于说明时间，不对应实际 33 ms：

```text
A 第 0 帧：0m，发送 P0
A 第 1 帧：1m
A 第 2 帧：2m，发送 P2
A 第 3 帧：3m
A 第 4 帧：4m，发送 P4
A 第 5 帧：5m
A 第 6 帧：6m，发送 P6
```

假设端到端传输延迟为两帧，则 B 的接收顺序是：

```text
B 第 2 帧：收到 P0，时间戳为 A 第 0 帧，位置 0m
B 第 4 帧：收到 P2，时间戳为 A 第 2 帧，位置 2m
B 第 6 帧：收到 P4，时间戳为 A 第 4 帧，位置 4m
```

B 可以保留一个缓冲区，让播放时间落后于最新收到的采样时间，再在两点之间插值。例如 B 第 4 帧有 P0 与 P2，若播放 A 第 1 帧的状态，就能在两者之间计算位置。**网络延迟**与额外的**插值缓冲延迟**是两件事，不能只说“故意晚两帧”却不说明参照哪条时间线。

如果数据尚未覆盖要显示的时间，就需要等待、冻结或外推，这才涉及预测；插值已有两点和预测未来不能混为一谈。

```text
A 第 0 帧：0m，发送 P0
A 第 1 帧：0m
A 第 2 帧：1m，发送 P2
A 第 3 帧：2m
A 第 4 帧：1m，发送 P4
```

这个例子中 P2 与 P4 都是 1m，B 无法仅凭它们知道 A 曾在第 3 帧到过 2m。提高采样频率、携带速度或关键事件可以改善某些情况，但不能凭空恢复没被发送的信息。
