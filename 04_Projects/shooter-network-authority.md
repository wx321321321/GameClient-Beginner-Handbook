本篇把 Arena 的本地规则进程拆成服务端和两个客户端。
服务端以示例 60 Hz 推进模拟；客户端渲染帧率、命令发送频率与快照发送频率分别配置。
第一版快照可选 20 Hz，即通常每三个服务端 tick 发一次，但这不是任何引擎的默认保证。
网络模块的任务是让状态在延迟、乱序、重复和断线下仍有清楚的归属。

## 4.5.1 一份权威世界，多份客户端视图

服务器拥有位置、武器、血量、碰撞、AI 和对局结果。
本地玩家拥有预测副本，远端角色拥有快照缓冲，表现系统拥有相机和音画实例。
“客户端看见了”既不代表服务端当前如此，也不授予客户端修改服务器的权力。

```text
本地输入 -> InputCommand -> 服务端接收窗口 -> 按序规则模拟
    |                                           |
    +-> 本地预测                     Snapshot + CommandAck + Events
                                                    |
                           本人校正并重放 / 远端插值 / 表现确认
```

同机运行时也保留这个接口，便于在没有网络噪声时先验证规则。
UE CharacterMovement 也区分拥有客户端、服务端和模拟代理，并保存移动供校正后重放。
这里是 Arena 的固定 tick 课程设计，不是对 UE 内部 ServerMove 调度的一比一复刻。
[Epic 网络移动说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine)

## 4.5.2 协议先写字段语义，再选择传输

| 消息 | 关键字段 | 处理语义 |
| --- | --- | --- |
| InputCommand | sessionEpoch、CommandSeq、clientTick、移动与按钮意图 | 去重、排序、过期策略 |
| FireRequest | 射手句柄、ShotSeq、关联 CommandSeq、瞄准信息 | 每个射击键最多一次副作用 |
| Snapshot | serverTick、stateVersion、实体状态、基线 ID | 最新可解码状态覆盖旧状态 |
| CommandAck | 已消费命令边界或窗口 | 客户端回收已处理命令 |
| ShotResult | 完整射击键、接受/拒绝、权威 tick | 重复结果不重复播放 |
| Spawn/Despawn | 实体句柄、生命版本、状态基线 | 可重放、不可误用旧 generation |

`CommandSeq` 和 `ShotSeq` 都用 `uint64_t`，它们不是同一个计数器。
网络包序号也不等于这两个业务序号：一个包可以带多个命令，一个命令也可能重发在不同包里。
同一会话 ShotSeq 不因切枪重置；重新连接产生新的 sessionEpoch，旧会话消息失效。
序号溢出前必须换会话或对局；不要在未定义规则下依赖无符号回绕比较。

序列化逐字段定义字节序、范围和协议版本，禁止直接发送 C++ 结构体的内存布局。
接收先检查长度、数量上限、有限浮点数与枚举范围，再构造业务对象。
客户端上报的 tick 只是一条待校验信息，不是直接设置服务器时钟的命令。

传输层可以采用现有引擎或成熟网络库。Steam 官方接口就同时提供可靠与类似 UDP 的通信能力。
选择哪一类消息需要哪种语义，仍是游戏协议的责任。[Steam Networking](https://partner.steamgames.com/doc/features/multiplayer/networking?l=english)

## 4.5.3 “可靠”不等于业务只执行一次

连续位置状态通常允许丢旧留新，避免过期状态占满可靠队列。
加入对局、实体创建基线、关键结果等需要确认或重传，但必须限制队列长度和等待时间。
高频输入可以冗余发送最近未确认命令，由业务序号去重；不要无限堆积每帧可靠 RPC。
一次性开火请求需有最终答复，可用可靠通道或应用确认重发；无论哪种方式都使用同一个射击键。

即使底层在一次连接内有可靠有序保证，业务超时重试、重连和消息处理恢复仍可能造成重复请求。
服务器缓存第一次处理的接受或拒绝结果，重试返回原结果，不能重新扣弹。
有界账本保留窗口内结果，窗口外拒绝重放；跨进程“恰好一次”还需要持久化事务，不由一个 `set` 自动提供。

乱序命令放进有限接收窗口，按 CommandSeq 消费。
某个序号缺失时，短暂等待重传；超过预算后按已定义策略填中性输入或跳过，并推进可确认边界。
客户端得知该边界后不再重放已被服务器放弃的命令。
旧移动命令不能在几秒后突然执行一次；状态过期策略是玩法的一部分。

## 4.5.4 本地预测需要完整的可重放状态

拥有客户端在产生命令时，用相同运动规则立刻模拟，并保存命令与预测状态。
服务器返回“已处理到命令 N 的状态 S”后，客户端把物理状态重置为 S，再重放 N 之后的未确认命令。
这里的 S 至少包含位置、速度、运动模式、接地与平台关联等实际影响后续模拟的字段。
只保存位置无法正确重放跳跃、加速、台阶和移动平台。

```text
收到权威状态 S(N)
  校验 sessionEpoch / 实体 generation / lifeId
  删除 <= N 的已确认命令
  模拟状态 = S(N)
  按序执行剩余命令，禁止再次生成不可重复的外部副作用
  记录最终校正误差；可见模型逐渐收敛到新的模拟位置
```

该流程是需要引擎运动适配的逻辑示意。
重放时不能重新播放枪声、生成永久弹孔、提交统计或再次发网络请求。
把可重演的状态计算和一次性表现事件分开，事件以射击键或命令标识去重。
碰撞胶囊使用校正后的模拟位置，视觉偏移用于平滑；不能只把模型移回去而让碰撞体留在错误位置。

客户端与服务端配置、时间步长或碰撞场景不一致时，预测会持续偏差。
首先量化误差与重放次数，再判断是否缺字段；不要只增大“容忍误差”掩盖规则差异。
缓冲超过上限时请求完整基线并重置预测，不允许数分钟命令占满内存。
物理浮点、并行求解等未必跨机器确定，因此固定步长本身不保证逐位一致。

## 4.5.5 远端插值主动显示稍早的时间

远端角色没有本机输入，先将收到的状态按 serverTick 存入缓冲。
根据平滑估计的服务器当前时间减去插值延迟，得到 `renderTick`，寻找包围它的两个样本。
插值延迟覆盖一部分网络抖动，越大通常越平滑，也会增加视觉延迟。
不要把每个新包到达瞬间都当作新的零点，否则包间抖动会变成运动速度抖动。

下面是 C++17 独立的位置插值示例，可编译为目标文件。

```cpp
#include <algorithm>
#include <cmath>
#include <cstdint>
#include <stdexcept>
struct Sample { std::uint64_t tick; double x; };
double InterpolateX(Sample a, Sample b, double renderTick) {
    if (b.tick <= a.tick || !std::isfinite(renderTick))
        throw std::invalid_argument("unordered interpolation samples");
    const double alpha = std::clamp(
        (renderTick - static_cast<double>(a.tick)) /
        static_cast<double>(b.tick - a.tick), 0.0, 1.0);
    return a.x + (b.x - a.x) * alpha;
}
```

样本 tick 100 在 x=0 m、tick 106 在 x=6 m，渲染 tick 103 得到 x=3 m。
先转换再相减，避免 `renderTick < a.tick` 时无符号减法下溢。
本示例假定对局 tick 远小于 double 精确整数上限；超长运行系统应以局部时间原点计算小差值。
样本相同 tick 先去重；倒序到达先入有序缓冲，不能直接套公式。
旋转采用合适的四元数插值并处理等价符号，不能对欧拉角 359° 与 1° 直接求中点。

缓冲不足时可以短时保持或有界外推，超过上限显示网络退化；不可无限沿速度穿墙。
传送、复活、generation 改变需要清空或切分历史，不能从旧生命平滑穿越整个地图。
这种保留时间样本的插值与历史查询思想，可对照 Bernier 的原始网络设计论文。
[Latency Compensating Methods](https://www.gamedevs.org/uploads/latency-compensation-in-client-server-protocols.pdf)

## 4.5.6 射线命中回溯查历史，不倒放整场对局

快照插值让射手看到过去的目标。服务端若只查“包刚到达时”的位置，移动目标可能已经离开准星。
Arena 为可受击目标保留有界历史：tick、句柄、lifeId、碰撞体姿态、蹲伏状态和必要的部位信息。
教学配置可选 200 ms 的最大回溯窗口，对应 60 Hz 下约 12 个 tick；这是可调整的公平性选择。
缓冲额外保留插值端点，不能仅按 12 个槽位就假定覆盖了所有查询边界。

服务端将命令时间映射到自身时间轴，并结合测得的延迟、已发送快照、允许的插值范围校验查询时刻。
客户不能任意选择窗口内最有利的一帧；也不能声称使用十秒插值从而射中早已离开的目标。
所有请求被限制在允许的过去区间，未来时间和过旧时间按策略拒绝或钳制并记录原因。
最终选定的查询 tick 必须进入日志，便于解释争议命中。

```text
合法 FireRequest
  -> 选择并校验 queryTime
  -> 从历史重建查询用碰撞代理
  -> 在该查询场景中做枪口/射线遮挡与目标测试
  -> 产生带目标 lifeId 的候选命中
  -> 回到当前规则时刻提交伤害
```

优先使用独立的历史查询场景或只读代理，避免修改实时世界时触发物理回调和游戏事件。
若必须临时挪动现有碰撞体，恢复需要异常安全、线程隔离和严格作用域，且不能让其他查询看到半恢复状态。
不会回滚实时弹药、冷却、死亡和所有实体；当前提交仍检查目标是否属于可结算的生命版本。
第一版规则选择：已在当前时刻死亡的目标不再重复接受伤害，也不复活过去的目标供再次击杀。

静态墙可直接用不变场景；会移动的门、盾牌和平台必须决定是否保存并回溯。
只回溯人物、不回溯移动掩体会混用两套时间，引发“穿门命中”；这是需定义的游戏规则，而非插值公式的小误差。
被射击者已经躲到墙角后却仍被较早视角击中，是延迟补偿的公平性权衡之一，不能声称完全消除了延迟。
Bernier 的论文也讨论了该权衡，并区分即时射线与持续存在的飞行弹。[原论文](https://www.gamedevs.org/uploads/latency-compensation-in-client-server-protocols.pdf)
Arena 的第一版飞行弹按服务器当前时间推进，不复用“把目标倒回一次”的射线方案。

## 4.5.7 快照基线和 AOI 一起设计

第一版先发送小规模全量快照，确认正确后才做字段量化、变化掩码和增量基线。
增量消息必须引用客户端已拥有的基线；缺基线不能拿随机旧状态解码，应请求全量恢复。
量化精度以玩法误差预算决定，例如位置厘米级是否足够，要结合地图尺度与命中体大小测量。
序列化单位仍是课程约定的米，UE 的厘米转换只发生在适配边界。

AOI 决定“对谁发送哪些实体”，不直接决定这些实体是否在服务器继续模拟。
进入兴趣区域先发可用基线，之后发增量；离开时发送移出可见集语义，不能误当作世界永久销毁。
区域边缘用迟滞或最短驻留时间减少反复创建销毁。
枪声、远程投射物、队伍信息可能使用与角色位置不同的相关性规则。
AOI 能减少无关数据，但不应把它单独当作完整防透视方案。
具体网格和订阅集合的实践线索见 [AOI 笔记](aoi.md)。

## 4.5.8 用故障注入验证协议

| 场景 | 应观察的结果 |
| --- | --- |
| 同一个开火请求重复 | 一次扣弹、一份缓存答复、一次表现确认 |
| 命令缺口与乱序 | 有限等待与明确过期策略，不永久卡住后续输入 |
| 150 ms 延迟、30 ms 抖动、5% 丢包 | 数值可调整的实验条件，记录校正和缓冲下溢率 |
| 重连时旧包到达 | sessionEpoch 不匹配，旧预测不污染新角色 |
| AOI 退出后重新进入 | 获得新基线，无幽灵实体和错误增量 |
| 快照基线丢失 | 请求恢复，绝不把解码失败当合法状态 |
| 回溯查询超过窗口 | 规则可见的拒绝或钳制，日志保留原因 |

必须同时测 RTT、抖动、丢包、发送字节、可靠队列长度、预测校正距离和历史查询耗时。
只有一个 Ping 数字，无法判断卡顿来自模拟超时、丢包重传还是客户端帧率。
继续阅读 [表现层](shooter-presentation.md)，处理预测开火被拒绝时的视觉与音频收尾。
