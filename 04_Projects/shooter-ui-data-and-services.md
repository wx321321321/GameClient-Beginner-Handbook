能够开枪的关卡还不是一个完整的可进入、可退出的项目。
Arena 需要把状态展示、用户偏好、配置资源和在线会话接到同一套生命周期上。
本篇先用本地假服务实现接口，再替换为真实平台或业务 API；没有假定作者已有这些服务。

## 4.8.1 UI 显示状态，通过命令申请改变状态

HUD 至少显示生命、护甲、当前与备用弹药、准星、换弹/技能冷却、命中确认和连接状态。
数据从领域状态投影成 ViewModel，控件只绑定可显示值。
玩家点换弹按钮产生 ReloadCommand，不能由按钮直接把 ammo 写成容量。
MVVM 在这里表示把展示数据与控件分开，不要求引入一套特定框架。

| 数据 | 真正来源 | UI 规则 |
| --- | --- | --- |
| HP/护甲 | 服务端确认的战斗状态 | 受击动画可平滑，死亡结论来自服务器 |
| 弹药 | 权威值 + 明确标识的本地预测 | 被拒绝时恢复，不永久覆盖权威值 |
| 冷却 | 服务端结束 tick | 按估计服务器时间换算剩余秒 |
| 准星扩张 | 当前认可的散布状态 | 与纯视觉枪模后座分开 |
| 连接提示 | 会话状态机与超时 | 不凭“几秒没动”猜断网 |
| 外观预览 | 本地选择草稿 | 保存成功后才标为已提交 |

更新按状态版本或字段变化触发，避免每个控件每帧重新查找角色和拼接字符串。
动画数值与实际数值分开：血条的缓慢下降不能让技能系统看到旧 HP。
角色切换、复活、观战和 UI 关闭都要取消订阅，迟到回调用绑定版本过滤。

下面是 C++17 可编译为目标文件的投影示例，采用固定的 60 Hz 教学时钟。

```cpp
#include <algorithm>
#include <cstdint>
#include <stdexcept>
struct CombatView {
    int hp, maxHp, ammo, reserve;
    std::uint64_t reloadEnd;
    bool reloading;
};
struct HudModel {
    double hpFraction, reloadSeconds;
    int ammo, reserve;
};
HudModel ProjectHud(const CombatView& s, std::uint64_t estimatedServerTick) {
    if (s.maxHp <= 0 || s.ammo < 0 || s.reserve < 0)
        throw std::invalid_argument("invalid view state");
    const auto left = s.reloading && s.reloadEnd > estimatedServerTick
        ? s.reloadEnd - estimatedServerTick : 0;
    return {std::clamp(double(s.hp) / s.maxHp, 0.0, 1.0),
            double(left) / 60.0, s.ammo, s.reserve};
}
```

倒计时到零不表示 UI 已经拥有“换弹完成”的权力。
网络结果未到时可显示等待同步；不能因为控件计时结束自行补弹。
示例输入经过状态验证，完整工程还要处理暂无角色、观战目标与本地预测展示分支。
UI 不持有业务对象裸指针跨异步回调，参见 [实体生命周期](shooter-runtime-and-input.md)。

## 4.8.2 设置、存档、对局状态采用不同持久化边界

设置包含音量、灵敏度、键位、画质和辅助选项，优先保存本地偏好。
存档保存可恢复的单机进度或教学靶场记录；在线对局中的血量和弹药不由本地存档恢复。
账号库存、外观拥有权与排名等属于服务端业务记录，本地只能缓存。

设置结构包含 `schemaVersion`，读取时按版本迁移，未知新字段可忽略，缺失字段采用明确默认值。
键位冲突、音量范围、分辨率支持与枚举合法性在应用前验证。
应用失败要返回错误并保留上一个可用值，不让无法使用的设置反复在启动时生效。

```text
读取文件 -> 限制大小 -> 解析结构 -> 校验版本 -> 迁移 -> 校验字段 -> 应用
写入快照 -> 写同目录临时文件 -> 校验写入结果 -> 按平台能力替换正式文件
```

这是需要平台文件 API 的逻辑示意，不能假定 C++ `rename` 在所有平台和文件系统上都提供同样的替换与断电持久性保证。
关键文件保留最近一次可读备份，写入失败不删除旧文件；坏文件隔离并提示使用默认值或备份。
设置写入做防抖与合并，拖动音量滑块时不必每个像素都写一次磁盘。
后台保存拿不可变快照，完成回调不能把较旧版本覆盖较新的内存设置。

## 4.8.3 配置 ID、资源 ID 与文件路径不是同一个概念

WeaponConfigId 标识规则配置，ResourceId 标识可加载资源，文件路径由资源目录映射。
脚本和网络协议传稳定 ID，避免美术重命名目录就改变协议或存档含义。
构建清单记录资源 ID→打包路径、内容哈希、类型、依赖和版本。
规则配置校验其引用是否存在、类型是否正确，并拒绝重复 ID。

```text
rifle_basic@config-v1
  magazine=3, intervalTicks=6, reloadTicks=120
  model=weapon/rifle_basic
  shotSound=audio/rifle_shot
  muzzleEffect=fx/rifle_muzzle
```

这是教学配置草图，不是要求使用这种文本格式。
开发环境可读 JSON，正式加载可转换为校验后的紧凑结构，但两者必须产生相同含义。
服务器和客户端加入对局前检查协议版本、规则配置版本和必要资源版本。
纯外观资源缺失可用占位效果降级；影响碰撞或规则的配置不一致应拒绝进入并显示具体原因。
资源异步请求带取消与版本号，完成时重新确认调用者仍需要它。

## 4.8.4 登录、大厅、匹配和战斗连接分别建模

登录回答“是谁”，大厅管理组队与准备，匹配选择合适对局，会话票据授权加入指定服务器。
连接建立回答“网络通了没有”，完整基线加载完成才回答“可以开始操作了吗”。
不能把一个 `isOnline` 布尔值同时代表这五件事。

```text
SignedOut -> Authenticating -> Lobby -> Matchmaking
              |                  |          |
              +-> LoginFailed    +<-Cancel--+
                                           |
                                      Connecting
                                           |
                                       Loading
                                           |
                                        InMatch
                                           |
                                 Reconnecting / Returning
```

每个状态定义允许按钮、进入动作、超时、取消和失败去向。
请求有递增 requestVersion；用户取消匹配后迟到的旧成功回调不能擅自把用户再次拉入对局。
同时，服务端若已分配席位，要按协议释放席位，不能仅忽略回调造成资源泄漏。
连接失败区分鉴权失败、版本不兼容、服务器满、超时和对局已结束，给出对应可恢复动作。

平台大厅也不等于实际游戏服务器。Steam 的大厅用于组织用户，之后仍需连接游戏主机或服务器。
[Steam Matchmaking & Lobbies](https://partner.steamgames.com/doc/features/multiplayer/matchmaking)
Arena 先实现同样接口的本地模拟服务，能够注入延迟、拒绝和乱序回调，再接入具体平台 SDK。
客户端不内置服务端密钥；认证票据有效期与身份校验由所选服务方案负责。

## 4.8.5 断线重连恢复基线，不能照搬旧预测

断线被确认后停止提交新权威请求，保留可见场景或退回加载界面，按策略允许有限等待。
重连请求携带对局标识与服务端签发的恢复凭据，服务器验证账号、席位、有效期与对局状态。
认证成功后分配新的 sessionEpoch，旧连接残留消息全部失效。
服务器下发最新完整基线和必要业务结果，客户端清空旧命令、插值历史及预测事件后重新绑定。

已完成的开火与伤害不能因为重连再执行一次。
若在途请求在断线前究竟有没有提交不确定，应通过服务器当前状态或业务查询恢复，不能一股脑重发为新请求。
玩家离线期间角色是保留、托管、无敌还是移出比赛是玩法决定，需写入规则并对所有客户端一致展示。
重连到已结束对局时返回最终结果，不重新创建旧比赛。
重试采用有限退避和上限，用户可以取消；无限重连会掩盖永久错误并消耗资源。

## 4.8.6 外观预览和保存是两条不同路径

预览只修改本地草稿，可以即时换模型、颜色和动画，失败时回退占位资源。
保存请求发送外观 ID、槽位、期望版本和业务请求 ID。
服务器检查玩家是否拥有、槽位是否兼容、组合是否允许、配置版本是否有效，再事务性更新外观版本。
响应确认后才把草稿标为已保存，其他玩家从服务器认可的外观状态加载资源。

```text
SaveAppearance(requestId, expectedRevision, selections)
  -> 验证身份与请求作用域；已处理 requestId 直接返回原结果
  -> 拥有权/槽位/版本校验
  -> 若 revision 冲突，返回最新状态供合并或重选
  -> 原子保存新 selections 与 revision
  -> 缓存 requestId 结果，重试不重复执行业务
```

这是需要后端接口的逻辑示意，不包含任何真实账号服务调用。
本地资源存在不能证明账号拥有；客户端预览成功也不能证明服务端允许保存。
同一账号两个设备同时保存时用 revision 处理冲突，不让较旧响应覆盖新的外观。
原有 [QQ 飞车动画与 UI 笔记](qq-speed-animation-and-ui.md) 的换装、状态与业务校验线索可用于对照，不代表 Arena 已实现同一工程。

## 4.8.7 将服务失败当作正常验收场景

- 关闭再打开 HUD、切换角色或复活，订阅数不增加，旧角色事件不更新新 HUD。
- 设置文件损坏、磁盘写入失败、旧版本迁移都能保留可用配置并给出可理解结果。
- 取消匹配后成功回调才到达，界面仍留在用户选择的状态，已分配资源被释放。
- 版本不兼容时拒绝进入且说明缺哪一类版本，不在加载进度 99% 永久等待。
- 重连后血量、弹药、生命版本与服务器一致，没有旧枪声重播或旧命令突然移动。
- 未拥有外观、非法槽位、重复保存和并发版本冲突都有确定答复。

练习：用假服务分别让登录、匹配、连接、加载延迟两秒或失败一次，记录每个界面允许的操作与取消后的资源清理。
完成这一轮后再进入 [性能与工程工具](shooter-performance-and-tooling.md)，把这些边界纳入长期回归。
