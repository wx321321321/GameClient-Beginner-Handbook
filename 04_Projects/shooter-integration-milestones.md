# 4.10 射击项目的实现顺序、验收与排错

前面的技术篇定义了 Arena 的接口，本篇把它们串成可以一步步完成的工程路线。
每一阶段都留下能运行、能观测、能复现的产物，再引入下一种复杂度。
本文是教学实施计划；仓库中的独立实验只实现了其中的纯规则边界，不是已经制作完成的游戏。

## 4.10.1 M0：让纯规则先跑起来

输入：手写 tick、射击序号、伤害事件与位置样本。
产物：武器状态、伤害幂等与插值三个独立实验。
使用 [shooter-labs.cpp](../examples/course/shooter-labs.cpp)，阅读断言，再运行；不要只看到成功字样就跳过规则。

实验需要 C++17 编译器，不依赖 UE 或其他第三方库。
在已配置 GCC 或 Clang 的终端中，从仓库根目录可执行以下示例；Windows 输出文件使用 `.exe` 后缀。

```text
c++ -std=c++17 -Wall -Wextra -pedantic examples/course/shooter-labs.cpp -o shooter-labs
./shooter-labs
```

这些是适用于相应编译环境的命令示例，不表示所有机器都已配置 `c++`。
Windows PowerShell 若使用生成的 `shooter-labs.exe`，运行 `./shooter-labs.exe`；MSVC 则使用其开发者环境与 `/std:c++17`。
不要定义 `NDEBUG`，否则标准 `assert` 会被禁用；实验文件对此设有编译保护。
成功输出为 `Arena labs: weapon, combat, timing assertions passed.`。

验收先逐条解释：重复开火为何不扣弹、冷却拒绝重试为何仍拒绝、换弹为何只转移一次、lifeId 如何拒绝旧生命伤害。
然后故意破坏一条规则，确认对应断言失败，再恢复它。
这一步用于理解边界，不能替代引擎碰撞与网络测试。

## 4.10.2 M1：一张灰盒地图的单机垂直切片

先完成 [循环与输入](shooter-runtime-and-input.md)，让胶囊按命令在地面、墙角和台阶上移动。
再加入相机中心射线和枪口查询，记录命中点但暂不依赖枪模与粒子。
接入武器状态、目标 HP/Armor、死亡、复活和最小 HUD。
最后用简短音效或调试闪光确认一次开火，只做一个目标、一种武器。

| 顺序 | 可运行产物 | 当场验收 |
| --- | --- | --- |
| 1 | 输入→固定步运动→胶囊 | 30/60/144 FPS 不改变同命令模拟时长 |
| 2 | 相机/枪口两段查询 | 相机能看见、枪口被墙挡时不能射穿 |
| 3 | 射速、弹药、换弹 | 冷却边界、空弹匣、取消、死亡均正确 |
| 4 | 命中→护甲→HP→死亡 | 重复事件不重复扣血和计分 |
| 5 | 复活与 HUD | 旧生命消息不影响新生命，展示不写规则 |

M1 的“单机”只是不跨网络，状态仍由同一个规则世界决定。
显示层拿只读快照，输入走命令接口；这样 M2 可以替换传输，不必拆开所有 UI 和动画回调重写。
此时不追求多人、复杂背包、完整技能树或大量枪械。
验收产物是一条完整玩法闭环，以及能关闭表现后继续跑的规则核心。

## 4.10.3 M2：本机权威服务器和两个客户端

保持原规则模块，把权威世界放到服务端实例，客户端只保留输入、预测占位与表现。
先不做预测，接受本地网络下可见的小延迟，验证客户端结果全部来自服务端。
实现加入、实体基线、输入序号、开火答复、状态快照与离开清理。
两个客户端分别控制不同角色，禁止通过提交别人的句柄操纵对方。

先用全量快照，暂不增加压缩、增量基线和复杂 AOI。
服务器端关闭任何渲染依赖，客户端关闭本地命中判断后，服务器仍能正确产生伤害。
修改客户端显示的血量或弹药不会改变服务端世界。
重发同一个请求 100 次，服务器只有一次扣弹和一次相应伤害。
从服务端日志能追到连接、角色、命令、射击与伤害，才算这一阶段通过。

## 4.10.4 M3：给延迟补偿增加可控复杂度

依次加入本地移动预测、权威校正与命令重放，再给远端角色加入快照插值。
验证重放不会再次播放枪声，然后加入本地开火预测的确认与拒绝收尾。
基础移动稳定后再做射线历史命中查询，最后增加 AOI 与增量快照。
这样若出现持续校正，可以先定位运动状态，而不被五种新机制同时干扰。

| 子阶段 | 核心数据 | 必测边界 |
| --- | --- | --- |
| 本地预测 | 未确认命令、权威基线 | 丢 ACK、缓冲上限、配置不同 |
| 远端插值 | 按 tick 排序的快照 | 乱序、重复、下溢、传送 |
| 预测射击 | 完整射击键、表现状态 | 拒绝、结果重复、重放 |
| 命中回溯 | 有界历史碰撞体与生命版本 | 过旧/未来查询、动态掩体 |
| AOI/增量 | 可见集、基线版本 | 进入退出、缺基线恢复 |

使用可重复的网络参数，例如双向链路分别配置延迟、抖动和丢包，明确统计的 RTT 不是单向延迟。
逐项增加故障，不要一开始把所有参数调到极端后只得到“不能玩”的结论。
验收结果不仅写“流畅”，还记录预测误差、下溢次数、流量、重复事件数与最坏 tick 耗时。
具体机制见 [网络权威](shooter-network-authority.md)。

## 4.10.5 M4：在稳定接口上增加内容与 AI

先添加一种拾取物，验证两个玩家争抢只成功一次，再加入服务器 AI 和路径跟随。
AI 通过同一动作意图、武器 FSM 与伤害规则攻击，不写一条绕开验证的扣血捷径。
接入基础运动、上半身持枪、换弹、ADS、后座、Foot IK 和有界特效池。
每添加一种表现，都验证关闭它之后玩法结果不变。

之后选择一个机制扩展：飞行弹、霰弹、穿透或主动技能，不同时加入全部武器类型。
分别写清每发弹药、每个弹丸、每次伤害的身份与生命周期。
等小地图资源流程稳定后再做区块流式加载，验证任务取消、路径失效和复活预加载。
每类内容都提供坏资源/坏配置时的回退或拒绝，不靠正式资源“永远不会缺失”的假设。

M4 通过的标志是能复用接口添加第二种内容，而不是复制第一种的整条调用链。
例如换一把枪只更改配置与弹种策略，不复制 HUD、网络去重和死亡结算。
相关实现分别在 [世界与 AI](shooter-world-and-ai.md)、[表现](shooter-presentation.md) 和 [战斗技能](shooter-combat-and-abilities.md)。

## 4.10.6 M5：进入、离开、重连、构建与诊断

用假服务完成登录、大厅、匹配、连接、加载、返回的状态机，再接真实平台适配。
加入版本协商、设置存档、外观预览与服务端业务保存校验。
断线恢复新 sessionEpoch 和完整基线，清空旧预测，验证迟到包不能污染新会话。
构建时收集源码/协议/规则/资源版本，产出可以复现的客户端与服务器包。

同时完成后台自动化、固定场景性能测量、弱网脚本和状态事件记录。
保存一段可离线回放的故障窗口；回放不能向真实业务服务重复发奖励或保存请求。
长时间循环进出对局，内存、任务、订阅、特效池与网络队列回到稳定范围。
功能验收与性能验收都通过后，才把该阶段标为完成。

## 4.10.7 用一发子弹串起所有接口

假设服务端在 tick 120 接受玩家 P 的输入命令 80，其中携带 ShotSeq=1001。
该会话 epoch=7，射手句柄为 `{slot=3,generation=2}`，武器 Ready、弹匣 3、nextFire=120。
目标句柄 `{9,4}`，lifeId=1，HP=100、Armor=40；这一发基础伤害为 30。

1. 输入适配器构造命令 80，客户端为射击键 `(7,{3,2},1001)` 创建一次预测反馈。
2. 传输层校验消息边界并送入接收窗口，服务端按序将命令交给规则层。
3. 会话验证 P 控制 `{3,2}`；武器验证生命、装备、冷却、弹药与瞄准输入。
4. 第一次接受该射击键，弹匣从 3 变 2，nextFire 从 120 变 126，并缓存结果。
5. 服务端构造合法枪口和方向，选择经过验证的查询时间，做遮挡与目标碰撞查询。
6. 命中 `{9,4}` 的生命 1，服务器分配 DamageEventId=500，记录命中点和部位。
7. 战斗模块首次应用事件 500，护甲从 40 变 10，HP 仍为 100，不产生死亡事件。
8. 服务端发送 ShotResult、状态快照及相关命中事件，按接收者相关性分发。
9. 拥有客户端确认原预测反馈，修正弹药，更新 HUD；远端按唯一事件播放一次开火。
10. 命令或结果再到达一次时，复用原答复并跳过副作用，不再扣弹、扣甲或播放一次枪声。

如果第 3 步因为冷却拒绝，后面命中和伤害阶段都不应执行，客户端收尾被拒绝的预测。
如果第 5 步没有命中，扣弹仍然成立，不能因为打空退还一发。
如果命中记录在应用前发现目标 lifeId 已变化，拒绝旧生命伤害，不把它转给复活后的角色。
网络延迟改变结果到达时间，不能改变这条链中每个状态的唯一写入者。

## 4.10.8 用小型合同检查拒绝错误数据

下面是 C++17 可编译为目标文件的教学检查函数，验证单次 ShotAccepted 的部分不变量。
它不能替代完整规则，但可用于测试或调试构建的边界断言。

```cpp
#include <cstdint>
struct AcceptedShot {
    std::uint64_t tick, sequence, nextFire;
    int ammoBefore, ammoAfter;
};
bool HasValidCommit(const AcceptedShot& s, std::uint64_t interval) {
    if (s.sequence == 0 || interval == 0 || s.ammoBefore <= 0)
        return false;
    if (s.nextFire < s.tick) return false; // 拒绝计时回绕。
    return s.ammoAfter == s.ammoBefore - 1 &&
           s.nextFire - s.tick == interval;
}
```

此外每个模块要维护以下接口不变量：

- 单位只有米、秒与内部弧度，转换集中在引擎边界。
- 服务端 tick、CommandSeq、ShotSeq 含义不同，不拿包序号代替业务序号。
- generation 区分实体重用，lifeId 区分同一实体复活，epoch 区分连接会话。
- 所有重试先确定身份与结果账本，再决定是否产生副作用。
- 动画、HUD、粒子与音效不拥有权威伤害和弹药。
- 异步结果检查句柄、请求版本与取消状态；失效结果不写入新对象。
- 所有缓冲、查询循环、对象池和重试都有上限及超限策略。

## 4.10.9 按第一处错误排查，不从最终特效倒猜

| 现象 | 最先收集的证据 | 下一步 |
| --- | --- | --- |
| 点了没开枪 | 按下沿、CommandSeq、服务端拒绝原因 | 检查输入消费与武器门槛 |
| 枪声两次 | 同一射击键的预测/确认记录 | 检查确认是否重复创建表现 |
| 连发速度随 FPS 改变 | 服务端接受 tick 序列 | 检查是否用渲染帧做冷却 |
| 打中却没伤害 | 起点、方向、查询 tick、目标 lifeId | 区分遮挡、时间和结算拒绝 |
| 血量重复减少 | DamageEventId 及首次消费记录 | 检查生产与消费两端去重 |
| 人物不断被拉回 | 配置版本、基线与重放字段、碰撞差异 | 先修模拟差异，再调平滑 |
| 复活后旧枪弹生效 | epoch/generation/lifeId | 查生命周期校验缺在哪层 |
| 运行越久越卡 | 队列、池、订阅和历史缓冲数量 | 查未释放与无界增长 |

每个问题先固定一个输入序列，收集版本与状态，再做最小修改并回归同一序列。
不要同时改变网络频率、伤害公式和动画通知后，仅凭症状消失判断根因已解决。

## 4.10.10 进一步练习与原项目对照

练习一：把射速改成 750 RPM，计算 tick 量化后的实际射速，并设计需要精确射速时的子步方案。
练习二：增加可破坏掩体，分别决定当前碰撞、历史回溯、视觉碎片与网络基线如何更新。
练习三：在换弹即将结束时死亡并立刻复活，证明旧完成事件不能给新生命加弹。
练习四：客户端先预测命中远处目标，服务端接受开火并扣弹，但枪口查询被墙遮挡，没有命中该目标；列出哪些预测命中反馈可撤销、哪些开火反馈应保留。
练习五：重连发生在外观保存请求之后、响应之前，使用业务请求 ID 查询结果，避免重复扣除或覆盖。
