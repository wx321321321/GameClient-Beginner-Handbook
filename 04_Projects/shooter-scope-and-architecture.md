本组教程设计一个新的教学项目 **Arena**：先做单机可玩的射击闭环，再接入服务器权威的多人对战。
这里的模块和接口是教学设计，不代表作者在原工程中已经实现。
后面的 S18、ALS、QQ 飞车笔记用于对照真实项目经验，不能混作同一套源码。

## 4.1.1 先把“做一款射击游戏”变成可验收的范围

第一版只需要一个灰盒场地、一名玩家、一把步枪和一个可受伤靶子。
玩家可以移动、瞄准、开火、换弹；靶子会扣血、死亡、复位。
屏幕显示血量、弹药和开火结果，能从日志解释每一发为何成功或失败。

第二版允许两个客户端连接同一个独立服务器。
服务器决定位置、弹药、命中、伤害和死亡，客户端负责输入、预测和表现。
再加入队伍、复活、拾取、简单 AI、断线重连，最终扩展成小型竞技场。
人数上限、地图尺寸和目标平台是预算参数，不由框架名字自动决定。

| 先实现 | 延后实现 | 延后的原因 |
| --- | --- | --- |
| 灰盒地图、步行跳跃 | 大世界、载具、破坏场景 | 会同时扩大物理、网络与资源范围 |
| 单把 Hitscan 步枪 | 多种复杂投射物 | 先证明一次命中链正确 |
| 一个伤害模型 | 大量天赋与装备词条 | 先明确数据归属和结算顺序 |
| 两端对战 | 匹配排位与长期运营 | 连接正确后再扩展外围服务 |
| 简单日志和断言 | 完整编辑器工具 | 先找到真正需要自动化的重复工作 |

“先单机”只是在同一进程调用服务器逻辑，不能把客户端 UI 当成战斗状态的拥有者。
这样联网时替换的是传输，不必重写全部战斗规则。
Epic 的联网设计文档也强调尽早确定多人场景的数据归属。[官方联网概览](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine)

## 4.1.2 整组教程共用的约定

- 长度用米，时间用秒，速度用米/秒；接入 UE 时在适配层处理厘米与米的换算。
- 坐标示例为 X 前、Y 右、Z 上，重力为负 Z；数学接口里的角度使用弧度。
- `Tick`、输入命令序号和 `ShotSeq` 使用 `std::uint64_t`。
- 固定模拟 **60 Hz** 是示例，`dt = 1/60 s`；渲染帧率与快照发送率可以不同。
- `CommandSeq` 标识一次输入命令，`ShotSeq` 标识一次开火请求，不能混用。
- 实体句柄包含槽位与 generation；复活还需要 `lifeId` 区分同一实体的不同生命。
- 逻辑时钟在一局内单调前进，禁止由客户端自行增加模拟时间；示例不处理持续数百年的计数回绕。

网络中的完整开火身份是 `sessionEpoch + shooterHandle + ShotSeq`。
换武器不能重置同一会话内的射击序号；重连则明确更换 epoch 并清理旧预测。
原生结构体不能直接按内存布局发包，要做字段编码、范围检查和协议版本校验。

## 4.1.3 模块图：每一层对外提供什么

```text
Input → CommandQueue → Simulation
                         ├─ Movement / Collision
                         ├─ Weapon / Ability
                         ├─ HitQuery → Damage → LifeState
                         └─ World / AI
                                  ↓
                           Snapshot + Event
                                  ↓
                    ClientState / Prediction
                                  ↓
                 Animation / Camera / FX / HUD

ResourceCatalog → 配置与资产适配
SessionService  → 身份、连接、匹配、重连
Diagnostics     → 日志、指标、回放、断言
```

箭头表示依赖与数据流，不表示所有工作必须在同一线程串行完成。
Simulation 不引用按钮、音效组件或动画蓝图；Presentation 只消费状态与事件。
网络传输不能直接修改任意实体，要先验证消息并交给所属模拟线程。

| 模块 | 输入 | 输出 | 唯一写入者 |
| --- | --- | --- | --- |
| Movement | 已验证输入、dt、碰撞世界 | 位置、速度、落地状态 | 权威模拟；本地主控另有预测副本 |
| Weapon | 开火/换弹意图、武器配置 | 接受或拒绝、射击事件、弹药状态 | 服务器武器系统 |
| HitQuery | 起点、方向、范围、历史查询时刻 | 有序碰撞结果 | 只查询，不直接扣血 |
| Damage | 已验证命中、属性与规则 | 伤害事件、生命状态变化 | 服务器战斗系统 |
| Presentation | 快照、确认事件、预测事件 | 姿势、相机、音画 | 客户端表现系统 |
| Services | 用户意图、身份与版本 | 会话/保存结果 | 对应后端业务服务 |

## 4.1.4 用接口隔离引擎，而不是从头写引擎

Arena 需要碰撞、动画、音频和资源加载，但教程不重新实现这些底层。
UE 的 Character Movement、动画图和 Trace 可以成为适配器；其他引擎也可实现相同契约。
接口应围绕业务需要设计，不要先为每个类写一个没有用处的抽象基类。

以下是可独立编译为对象文件的 C++17 接口示意，没有提供真正碰撞世界：

```cpp
#include <cstdint>
#include <optional>

using Tick = std::uint64_t;
using ShotSeq = std::uint64_t;
struct Vec3 { double x, y, z; };
struct EntityHandle { std::uint32_t slot, generation; };
struct RayQuery {
    Vec3 origin;
    Vec3 unitDirection;
    double maxDistanceMetres;
    EntityHandle ignore;
};
struct Hit {
    EntityHandle target;
    Vec3 point, normal;
    double distanceMetres;
};
struct ICollisionWorld {
    virtual ~ICollisionWorld() = default;
    virtual std::optional<Hit> ClosestHit(const RayQuery&) const = 0;
};
struct FireRequest {
    ShotSeq sequence;
    Tick clientTick; // 仅是待验证的时间信息，不是服务器时钟。
    Vec3 aimDirection;
};
```

`HitQuery` 只返回碰撞事实，Damage 再决定队伍、护甲、无敌和死亡。
这样同一条命中查询可以用于枪械、AI 视线或调试，不会偷偷触发伤害。
真正接口还需表达碰撞通道、多个命中、历史场景句柄与查询失败。
这些能力在需要时增加，不靠一个巨大参数对象把全部模块绑在一起。

## 4.1.5 一次开火的总时序

1. 输入层采集按下/持续状态，生成命令和新的 `ShotSeq`。
2. 主控客户端保存预测记录，立即播放可撤销的枪口、后座和弹药预览。
3. 服务器检查身份、命令顺序、存活、当前武器、射速、换弹与弹药。
4. 接受后原子提交“扣一发 + 下次开火时刻 + 接受结果”，生成唯一射击事件。
5. 用服务器规则构造方向、散布和碰撞查询；必要时进入有边界的历史命中查询。
6. 将有效命中交给伤害系统，按事件 ID 防重复，处理护甲和生命状态。
7. 发出权威快照、开火答复及相关事件，按相关性选择接收者。
8. 客户端用相同键确认已有预测，或撤销被拒绝的预测；远端玩家播放事件。
9. HUD 读取已对账状态，命中特效与击杀提示按其确认等级显示。

这里的第 3～6 步都在服务器的同一模拟责任范围内完成。
动画 Cue 可以控制换弹手势与音效，不能因某台客户端少播一帧就永久不扣弹或不开枪。
真实项目的 Cue 驱动方案可对照[射击开火链路](shooting-pipeline.md)，重点比较时钟和责任差异。

## 4.1.6 状态、事件与命令不能互相替代

命令表达“我想做什么”，例如按住开火。
状态表达“现在是什么”，例如弹匣剩 8 发、正在换弹。
事件表达“发生过什么”，例如第 105 发已被接受。

晚加入的玩家需要当前状态，不能依赖重播全部历史事件重建血量。
本地一次枪口闪光需要事件，不能仅观察弹药少了就猜测发生过几次开火。
命令被拒绝时必须有原因，不能只是不发事件，让客户端永远停留在等待。

## 4.1.7 把依赖排成里程碑

| 里程碑 | 产物 | 完成标志 |
| --- | --- | --- |
| M0 | 纯逻辑实验 | 武器、伤害、插值断言通过 |
| M1 | 单机垂直切片 | 移动、命中、换弹、死亡、HUD 成闭环 |
| M2 | 本机权威双端 | 关闭本地命中也不影响服务器判定 |
| M3 | 预测与弱网 | 延迟、乱序、丢包不造成重复伤害 |
| M4 | 内容与 AI | 拾取、导航、动画、资源流转可复用接口 |
| M5 | 会话与诊断 | 重连、版本拒绝、回放和打包可验证 |

具体实施顺序与验收脚本集中在[集成里程碑](shooter-integration-milestones.md)。
先做 M1 不意味着跳过 M0 的状态归属，也不意味着 M3 前永远不测网络故障。

## 4.1.8 第一轮设计评审应能回答什么

- 玩家断线时，谁停止角色输入，谁清理子弹与特效？
- 同一开火包重发两次，哪个键保证只生成一次攻击？
- 动画被 LOD 跳过时，换弹是否仍按服务器状态完成？
- 重生后旧命中消息到达，怎样知道它属于上一条生命？
- 换色预览失败时，是否会覆盖服务器已经保存的外观？

如果答案都是“到时候在回调里处理”，说明接口缺少生命周期和消息身份。
先把这些约束写成断言，再增加表现，后续扩展才不会靠更多布尔变量互相补丁。
