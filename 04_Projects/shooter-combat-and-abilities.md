开火被接受，只说明武器合法地发出了一发；它不等于命中了某人，更不等于客户端已经可以决定死亡。
Arena 将武器、命中查询、伤害、生命状态分开，避免一个射击函数同时改十几个系统。
本篇的护甲和技能数值是教学规则，原项目实践可对照 [属性与同步](attributes-and-sync.md)。

## 4.4.1 谁提供什么证据

| 阶段 | 输入 | 输出 | 权威状态归属 |
| --- | --- | --- | --- |
| 请求验证 | 连接身份、输入命令、射击键 | 接受/拒绝原因 | 会话与武器 |
| 命中查询 | 合法起点、方向、查询时间 | 候选命中、碰撞部位 | 服务端碰撞场景 |
| 伤害规则 | 候选命中、配置、攻防属性 | 伤害明细 | 战斗规则 |
| 状态提交 | 唯一伤害 ID、目标生命版本 | 新血量、死亡事件 | 目标战斗状态 |
| 表现 | 已确认结果与本地预测 | 飘字、音效、击杀提示 | 客户端表现 |

客户端可以报告“我想朝这个方向开火”，服务器必须自己回答“这是否成立”。
验证包括连接是否控制该射手、角色是否存活、命令是否过期、武器是否装备、状态与弹药是否允许。
瞄准方向需要检查有限数值、长度与游戏允许的视角范围；简单角速度限制不是完整反作弊方案。
射线起点来自服务端认可的姿态；客户端世界坐标和客户端上报的目标 ID 都不能直接成为命中结论。
需要历史碰撞时，查询时间按 [网络权威与回溯](shooter-network-authority.md) 的窗口约束取得。

权威服务端架构意味着客户端结果最终服从服务端状态；这也是 UE 网络模型的核心职责划分。
具体服务器验证规则仍需由游戏实现。[Epic 网络概览](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine)

## 4.4.2 一次伤害必须有可追踪的身份

`ShotSeq` 标识一次开火请求，`DamageEventId` 标识一次伤害贡献。
一发霰弹可能产生多个伤害贡献，一枚爆炸物也可能影响多个目标，所以不能拿 ShotSeq 当所有伤害的唯一键。
Arena 由服务端为对局内的伤害贡献分配递增 `uint64_t` ID。
记录同时带有射击键、攻击者、目标句柄、目标 `lifeId`、技能或武器配置 ID、结算 tick。

实体句柄由槽位与 generation 组成，防止实体销毁后槽位重用造成误伤。
`lifeId` 则区分同一个角色实体的不同生命：死亡复活可能没有销毁实体，但旧生命的延迟消息仍应被拒绝。
如果对局重新开始，事件 ID 的作用域也要更新；不要拿两个对局的数字直接比较。
并发伤害先进入服务端规则线程，在明确的 tick 内排序结算；“最后一击”规则因此可以重现。

## 4.4.3 先使用明确、可解释的护甲规则

教学版护甲是一个额外的点数池：先扣护甲，剩余伤害再扣生命。
例如 HP=100、Armor=40，受到 30 点伤害后是 HP=100、Armor=10；再受 50 点伤害后是 HP=60、Armor=0。
这不代表护甲百分比减伤，也不等于所有射击游戏的公式。
如果以后加入减伤比例、穿甲和部位倍率，必须写出运算顺序，例如基础伤害→部位倍率→抗性→护甲池→HP。
随意交换这些步骤会改变结果，配置表只写几个系数不足以定义规则。

下面是 C++17 独立示意，可编译为目标文件；数值使用非负整数，先避免浮点舍入争议。

```cpp
#include <algorithm>
#include <cstdint>
#include <set>
struct Target {
    std::uint32_t lifeId = 1;
    int hp = 100, armor = 40;
    unsigned deathTransitions = 0;
    std::set<std::uint64_t> applied;

    bool Apply(std::uint64_t eventId, std::uint32_t expectedLife,
               int rawDamage) {
        if (eventId == 0 || expectedLife != lifeId || rawDamage < 0 || hp == 0)
            return false;
        if (!applied.insert(eventId).second) return false;
        const int absorbed = std::min(armor, rawDamage);
        armor -= absorbed;
        hp = std::max(0, hp - (rawDamage - absorbed));
        if (hp == 0) ++deathTransitions;
        return true;
    }
};
```

这里的返回值表示本条事件是否被首次应用，不是“是否死亡”。
死亡是 HP 从大于零转为零的状态迁移；死亡次数不能由每次收到 `hp == 0` 的消息累加。
示例集合无界，仅用于小实验；长对局要做有界事件账本、生命周期清理和服务端唯一分发约束。
生产属性载入时还需保证 HP、Armor 非负且不超过上限，避免损坏数据进入此规则。
完整断言包括重复伤害、连续致死与复活后迟到事件，见 [实验代码](../examples/course/shooter-labs.cpp)。

## 4.4.4 属性计算保留基础值与修饰来源

角色属性可分为基础配置、装备加成、临时 Buff、最终派生值和当前资源值。
最大生命是派生属性，当前生命是状态；两者不应放进同一个每帧重新计算函数。
最大生命从 100 增到 150 时，当前生命保留绝对值、同比增加还是补满，是玩法规则，要明确选一种。
Arena 第一版选择保留当前生命数值，并限制到新的最大值。

一种可解释的派生公式是：

```text
final = clamp((base + sum(flatModifiers)) * product(multipliers), min, max)
```

每个修饰器保存来源 ID、属性键、数值、叠加组和到期 tick。
移除 Buff 时删除对应修饰器，再重算派生值，不能尝试从最终值“减回去”恢复基础状态。
这种重算可在修饰集合变化时进行，不需要对所有属性每帧全量刷新。
不同乘法来源相乘可能形成极端值，应给出上限与数据校验。
网络只同步客户端确实需要的最终状态及必要 Buff 展示信息，不把内部所有计算过程都广播。

## 4.4.5 Buff 先定义叠加，再实现计时

每种 Buff 明确：是否可叠层、最大层数、重新施加刷新时长还是增加时长、来源是否独立。
Arena 的灼烧示例选择“同来源刷新持续时间，不增加层数；不同来源独立计时”。
持续伤害的每次跳伤都有独立 DamageEventId，全部受目标 lifeId 检查。
到期 tick 和下一跳 tick 都是服务端时间，暂停本地渲染不会暂停服务器中的 Buff。
当服务器一帧处理多个 tick 时，按固定模拟顺序逐次结算；不能因为一帧较长把伤害跳数悄悄丢掉。

解除、净化、死亡移除和正常到期是不同退出原因。
退出处理集中在一处并保证只执行一次，否则同一个属性修饰可能被重复撤销。
Buff 保存实体句柄，不保存跨 tick 的裸指针；目标销毁后解析失败即按规则清理。

## 4.4.6 技能激活是一笔规则事务

第一版技能选择“消耗 20 能量、冷却 5 秒、瞬时恢复 25 HP”。
执行顺序是验证生命与控制状态→检查冷却→检查资源→一次提交扣资源、设置冷却与效果。
如果最终不能激活，不应只扣掉资源却没有技能效果。
冷却结束 tick 属于服务器，HUD 只按服务器时钟估计剩余秒数。

```text
ActivateAbility(abilitySeq, actor, now)
  去重/返回已处理结果
  校验：活着、可操作、能力已获得、资源足够、now >= cooldownEnd
  提交：energy -= 20；cooldownEnd = now + 300；ApplyHeal(25)
  发布：AbilityAccepted + 新属性版本
```

这是需要引擎集成的逻辑示意，不是完整 C++ 接口。
技能请求也需要独立请求序号与幂等答复，不挤占武器 ShotSeq 的含义。
持续施法则引入 Casting 状态、开始 tick、完成 tick、可中断原因和资源退款规则。
动画完成通知用于对齐可见动作；权威冷却与施法完成不能依赖某台客户端是否播放了动画。

## 4.4.7 死亡与复活串起多个模块

服务器第一次进入 Dead 时，禁止新的动作、禁用武器、按规则清 Buff、记录归因，再发布一次 DeathEvent。
掉落、分数、击杀奖励也必须绑定这次死亡迁移，不能订阅重复网络消息后反复生成。
死亡动画可以慢于权威死亡；表现层的尸体和可被射击的战斗目标要明确区分。

复活由服务器验证计时与出生点，增加 lifeId，重置 HP、武器与允许恢复的状态，再发布完整基线。
旧生命的伤害、技能完成、换弹完成与动画回调都不能改新生命。
不要在复活时复用旧异步任务中的 `this` 或局部引用；请求要携带句柄和生命版本。
先检查 lifeId 再查当前生命的去重集合，可以安全清理上一生命的事件账本。
服务端重启或跨服迁移若需恢复幂等信息，必须有独立持久化设计；本地集合不提供跨进程保证。

## 4.4.8 验收与排错

| 现象 | 先查的边界 |
| --- | --- |
| 同一枪扣两次血 | DamageEventId 是否重复生成，消费是否幂等 |
| 复活后突然死亡 | 迟到事件是否携带并验证 lifeId |
| Buff 移除后速度不对 | 是否在最终值上反向加减而未保留来源 |
| 技能失败但扣资源 | 激活验证与提交是否分成了可中断的两条路径 |
| 击杀数和死亡数不一致 | 奖励是否依附死亡迁移，是否重复消费 |
| 头部命中判定不稳定 | 历史碰撞体、部位映射、查询时间是否统一 |

- 让伤害事件重复、乱序到达，先去重并按约定顺序整理后结算，最终状态可重现且重复事件不增加奖励。
- 同一 tick 两人互相命中，按照事先选择的同时伤害或顺序伤害规则得到固定结果。
- 给将死角色同时施加治疗、伤害、净化，保存输入序列后能重现结算顺序。
- 复活后重放上一生命的所有延迟消息，新的 HP 与弹药保持不变。
- 服务器日志能用射击键连到命中记录、伤害 ID、死亡事件和最终属性版本。

练习：把护甲改成百分比减伤，先用三组手算样例写清顺序，再修改规则和断言。不要让 UI 公式与服务端各写一份。
