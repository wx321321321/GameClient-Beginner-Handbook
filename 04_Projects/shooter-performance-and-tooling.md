Arena 做到两人互射后，就要建立可重复的性能与质量检查。
“我的电脑上挺流畅”不能解释低配置机器、多人同时开火或长时间运行时的问题。
本篇不要求开发一套完整引擎工具链，而是确定每次修改怎样被构建、测量、定位和回归。

## 4.9.1 先定义测量场景和预算

课程示例选择客户端目标 60 FPS，意味着每帧约 16.67 ms；服务器示例 60 Hz 也有约 16.67 ms 的单 tick 时限。
这两个预算分属不同进程，不是共用同一份时间。
客户端 CPU 与 GPU 可以流水并行，总帧时不能简单等于所有线程耗时相加。
服务器需要留出抖动余量；平均 16 ms 但频繁 40 ms 的 tick 仍会积压模拟与消息。

| 场景 | 固定条件 | 记录指标 |
| --- | --- | --- |
| 空场移动 | 固定地图、路线、分辨率、构建版本 | CPU/GPU 帧时、内存基线 |
| 双人交战 | 固定武器、持续时间、网络参数 | 校正、命中查询、流量 |
| 内容压力 | 预设数量 AI、粒子与音频 | 决策、动画、Draw Call、并发数量 |
| 长时间循环 | 多轮进出对局与资源加载 | 内存增长、订阅数、句柄数量 |
| 冷启动 | 清楚标注缓存条件 | 加载阶段耗时、首帧与首枪卡顿 |

为目标设备设预算后，再分配子系统预算，例如服务端留 3 ms 给运动与碰撞、2 ms 给 AI 等。
这些分配必须由实测修订，不是所有项目通用的常数。
将平均、p95、p99、最大耗时一起看，并记录样本数量与测量窗口。
不同地图、硬件、画质、人数和构建模式的数值不能直接混合成一条趋势。

## 4.9.2 用分位数暴露偶发停顿

下面是 C++17 独立示例，可编译为目标文件，采用 nearest-rank 定义求分位数。
输入是毫秒样本；复制排序便于教学，正式每帧热路径可用有界采样或直方图。

```cpp
#include <algorithm>
#include <cmath>
#include <cstddef>
#include <stdexcept>
#include <vector>
double PercentileMs(std::vector<double> samples, double p) {
    if (samples.empty() || !std::isfinite(p) || p <= 0 || p > 1)
        throw std::invalid_argument("invalid percentile request");
    for (double x : samples)
        if (!std::isfinite(x) || x < 0)
            throw std::invalid_argument("invalid timing sample");
    std::sort(samples.begin(), samples.end());
    const auto rank = static_cast<std::size_t>(
        std::ceil(p * static_cast<double>(samples.size())));
    return samples.at(rank - 1);
}
```

100 个样本中有 99 个为 5 ms、1 个为 100 ms，平均约 5.95 ms，最大值却说明一次明显卡顿。
该定义下 p95 与 p99 仍可能都是 5 ms，所以不能只挑一个分位数代替全部尾部观察。
计时使用单调时钟，避免系统时间调整制造负耗时。
采样本身也有成本，诊断级别和采样率要可调，并记录是否启用了高开销追踪。

## 4.9.3 调试可视化回答具体问题

游戏内调试层可以绘制胶囊、枪口射线、相机射线、命中点、地面法线和导航路径。
历史命中查询用不同颜色画出当前与回溯碰撞体，显示查询 tick 与选用的 lifeId。
网络面板显示未确认命令数、插值缓冲深度、校正距离、可靠队列和每秒字节数。
动画面板显示运动模式、上半身权重、IK 权重与当前装备状态。
每个开关针对一个问题，不能默认把所有线条和日志堆在画面上。

日志使用结构化字段，至少包含构建 ID、对局 ID、sessionEpoch、serverTick、实体句柄与事件类型。
射击相关日志附 ShotSeq，伤害附 DamageEventId，异步任务附 requestVersion。
不要只写“开火失败”：写 `reason=Cooldown, now=121, nextFire=126` 才能定位规则边界。
日志不记录访问令牌或服务密钥，账号标识按诊断所需最小范围处理。
高频日志使用有界缓冲、采样和分级，磁盘写满时不能阻塞服务器规则循环。

UE 项目可使用其 Trace/Insights 体系分析计时、内存、网络与资源加载，不必先自己写全套分析器。
本课程只依赖采集结果和可复现数据，具体工具入口以目标引擎版本为准。
[Epic Unreal Insights](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-insights-in-unreal-engine)

## 4.9.4 沿瓶颈方向优化

CPU 先区分游戏规则、动画、物理、提交渲染、等待与锁竞争。
GPU 先区分几何、像素填充、阴影、透明、后处理和带宽，不把所有慢帧都归因于多边形。
降低分辨率后帧时明显改善是像素相关瓶颈的线索，但仍需要 GPU 数据确认。
关闭 AI 后服务器 tick 改善则继续细分感知、寻路和行为更新，而不是直接减少所有角色。

常见改进包括查询粗筛、缓存稳定数据、按变化更新 UI、减少重复地面检测、池化高频短命效果。
对象池需要容量和回收检查；无限池只是把频繁分配变成常驻内存增长。
动画 LOD、粒子裁剪和音频并发限制不能改变权威换弹、伤害与技能时钟。
渲染相关原理可复习 [渲染管线与 GPU](../02_Graphics/rendering-and-gpu.md)。
每次只改变可解释的一组因素，用相同场景比较前后数据，同时验证玩法结果未变。

## 4.9.5 线程分工从单写者和快照开始

第一版让规则状态由模拟线程唯一写入，网络线程只解析并提交验证后的消息队列。
资源 IO 与解码在后台任务执行，结果以带版本的完成消息返回主责任线程。
渲染或动画任务读取不可变快照，不能直接遍历正在被修改的实体容器。
消息队列设置容量、丢弃/背压策略与关闭流程；不存在“开一个线程就自然不会卡”的保证。

```text
网络线程 -> 有界接收队列 -> 模拟线程 -> 不可变表现快照 -> 客户端表现
后台 IO  -> 完成队列（资源 ID、请求版本、结果） -> 资源拥有者提交
寻路任务 <- 只读导航数据 + 请求版本 -> 规则线程验证后采用路径
```

这是线程架构示意，具体队列使用经过验证的库或引擎任务系统。
双缓冲也需要同步发布与读写生命周期；仅用一个索引翻转不能证明没有数据竞争。
`shared_ptr` 只协助对象寿命，不自动让对象内部字段线程安全。
任务捕获句柄和值快照，避免长期捕获局部变量引用或随时会销毁的 `this`。
关闭时先停止生产新任务，再取消或等待已提交任务，最后释放它们依赖的资源。

## 4.9.6 资产制作也有接口契约

模型约定单位、朝向、枢轴、材质槽、LOD、碰撞代理和骨架版本。
武器约定枪口、握持点、抛壳点和挂点；动画约定参考姿势、根运动、曲线与事件命名。
纹理约定色彩空间、尺寸、压缩和用途；法线数据与颜色贴图不能不加区分地采用同样解释。
音频约定响度策略、空间化、循环边界和并发分类。
具体导入参数由目标引擎与资产规范决定，不把一个项目的坐标习惯直接当作行业通用值。

资产验证在构建前检查缺失引用、重复 ID、无碰撞关卡、错误骨架和超限资源。
正式打包包含资源依赖闭包，不能只在开发机“恰好曾经加载过”的缓存中找到文件。
首次播放卡顿要区分资源 IO、解压、Shader/Pipeline 准备与实例创建，再决定预加载位置。
大资源可增量发布，但规则与碰撞相关版本必须保持会话兼容。

## 4.9.7 构建结果应能回答“这是什么版本”

每个构建保存源码版本、编译器/引擎版本、协议版本、配置哈希、资源清单和构建时间。
服务端、客户端和崩溃符号能够相互对应；只保留一个叫 final.exe 的文件无法定位线上问题。
调试构建与优化构建都要验证，性能评估使用接近交付的构建配置。
保留符号文件但按发布策略管理，不能为了缩包丢掉诊断所需的所有映射。

## 4.9.8 自动化分层覆盖有意义的风险

纯规则测试覆盖武器状态、重复请求、生命版本、插值边界和坏配置。
协议测试覆盖截断包、超大数量、非法浮点、重复/乱序消息与未知版本。
引擎集成测试覆盖枪口遮挡、角色碰撞、命中部位、资源卸载与异步回调失效。
服务测试覆盖取消、重试、重连和业务幂等，压力测试覆盖持续运行后的数量与内存上限。
单元断言通过不代表真实引擎、GPU、平台服务与网络已验证，需要明确区分报告范围。

[shooter-labs.cpp](../examples/course/shooter-labs.cpp) 是本课程真正可运行的纯 C++17 实验。
它没有引擎、网络连接或窗口，使用标准库和 `assert`，编译时不能定义 `NDEBUG`。
它验证规则的几个关键边界，不能据此宣称完整多人射击项目通过验收。
新增用例应针对可能破坏的行为，不为每个 getter 写重复实现的断言。

## 4.9.9 弱网与回放使错误可重现

网络模拟器独立控制双向延迟、抖动、丢包、重复、乱序、带宽和短时断连。
固定测试种子与包处理日志，既测连续小丢包，也测突发丢包；同一平均丢包率可能产生完全不同体验。
还要注入服务端长 tick 和客户端低帧率，避免把计算拥塞全归为网络延迟。
保存错误附近的命令窗口、权威快照、射击/伤害事件与版本信息，供离线复现。

回放分两类：状态回放重现服务器确认的轨迹，命令重模拟尝试重算规则。
状态回放适合观察与诊断，命令重模拟只有在配置、随机、初始状态和外部输入都足够确定时才可比对。
物理不确定或版本变化时，记录周期性状态校验与关键帧，不能许诺跨版本逐位还原。
回放的副作用进入沙箱，不能重新发奖励、存档、真实网络请求或业务统计。
教学第一版只记录必要状态与事件，完整回放文件格式留作后续扩展。

## 4.9.10 交付前留下可以核对的证据

- 固定场景的帧时与 tick 分布，标明设备、分辨率、人数和构建模式。
- 一次开火的关联日志，从 CommandSeq 连到 ShotSeq、命中与 DamageEventId。
- 弱网用例结果，以及重连、复活、取消任务后的数量与内存稳定性。
- 缺资源、坏配置、版本不匹配时的明确失败结果。
- 当前已实现与仅做设计的边界，避免把实验代码包装成完整游戏能力。

练习：制造“客户端每五秒卡一次”的问题，分别用资源加载、过量日志和模拟长帧实现它，说明三者的计时轨迹为何不同。
