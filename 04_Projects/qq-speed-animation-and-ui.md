## 外骨骼+结算场景：

### gb动画系统：

#### 介绍一下gamebryo的动画系统：

我接触到的 Gamebryo 动画系统，核心是控制器机制。动画不是凭空播放，而是对象上挂了一系列控制器，控制器会随着时间推进去修改节点、骨骼或其他对象的状态。所以从运行时角度看，它本质上是“时间驱动控制器，控制器驱动场景对象变化”。像角色动画、结算镜头演出、外骨骼附加动画，本质上都是这个机制的不同应用。
这与UE的动画系统不一样的是，UE动画系统将网格骨骼体和动画拆开，只将一个时间传给动画，从而得到最终的pose，再应用，这个过程就可以扔到多线程上去计算。而gamebro它是要把动画数据存在模型的节点下的控制器中。每帧实时去修改节点本身的属性。缺点是性能较差，因为每一次人物移动，都在做大量深层树形结构的遍历和节点更新。
大量深层树形结构遍历”正是这类架构的性能杀手
UE 在初始化时，会把那棵复杂的 aiNode 树“拍扁”，存进一个连续的数组（TArray<FTransform>）。

批量计算：解算时，不看树，只看数组。CPU 只需要线性扫描一遍内存，利用 SIMD（单指令多数据流） 极快地算出所有骨骼的矩阵。

#### 详细说下动画文件格式：

NIF 更像承载模型、骨架、场景节点和控制器关系的主体资源；而 KF 更偏独立的关键帧动画数据。
所以运行时通常是：模型和骨架来自 NIF，具体播哪段动作由 KF 这类动画资源来驱动
.nif，包括网格、骨骼、蒙皮等，是一种树状结构，文件内容里面为头文件和数据块，对于不同类型的数据，存在对应的数据块中，当把这个文件读入内存时，会将树节点下的索引替换为内存指针  ，比如NiNode / NiAVObject存储骨骼结构，然后具体的蒙皮逻辑等，会存在另一个数据块中，在读入内存时第二遍过程替换指针，从而得到最后的模型树·

#### 场景图：

场景图架构可以理解成用树形结构组织场景对象。每个节点除了挂资源本身，还带有父子层级关系和局部变换，最终通过整棵树计算出对象在世界中的最终状态。它的好处是，像角色、骨骼、挂件、相机这类有层级依赖的对象都能统一管理。在 Gamebryo 这种引擎里，动画控制、渲染遍历和节点挂接很多都是基于场景图完成的
和UE区别：gb所有的节点都在一颗大树下面，而UE是有局部的层级数，不是所有东西都塞入一个场景图中

### 外骨骼管理器原理：

做了什么：
这个需求的背景是，一些特殊服饰在装备时不仅要显示模型本身，还要播放配套的演出动画，比如火焰翅膀这类带额外骨骼和动画表现的效果。这类资源不能简单当成普通挂件处理，因为它们会影响角色当前的动画表现，甚至和本体骨骼系统产生关联，所以把他们统一做成一个外骨骼资源。
我主要做的是设计并实现一个外骨骼管理器类，负责在指定时机把外骨骼资源挂载到角色上，同时对角色本体中部分重复或关联骨骼的控制器进行替换，让外骨骼动画能够正确接管对应的表现。
在动画播放完成后，管理器再负责把外骨骼卸载，并恢复原本的骨骼控制器，保证角色回到正常状态。
这个需求主要解决的是：如何让特殊服饰的额外动画能力和角色原有骨骼系统平滑协作，而不是简单叠加后互相冲突。

#### 控制器劫持怎么做的？

需要替换控制器的原因是，特殊服饰的外骨骼动画并不是纯附属挂件，它会驱动角色身上某些相关骨骼一起参与表现。
如果不做替换，角色本体原来的控制器和外骨骼资源里的控制数据会同时作用在相关骨骼上，就容易出现冲突，比如动作不同步、姿态错乱或者表现覆盖不正确。我的做法是做一层控制器劫持：在播放前先把角色当前相关骨骼的原控制器保存下来，再把这些骨骼的控制器切到外骨骼资源对应的控制器上，让这段演出期间由外骨骼动画接管。等播放完成后，再恢复原控制器，这样既能保证演出正确，又不会破坏角色原有动画系统的正常状态。

#### 容易存在的问题：

恢复不完整
我觉得这个方案里最需要小心的风险点，是控制器接管之后的恢复过程。
因为这类逻辑不是单次赋值就结束了，而是“先接管、播放一段、再恢复”，中间如果出现中断、角色切状态、场景切换或者资源提前释放，就可能导致恢复逻辑没走完整。
一旦恢复不完整，后续角色动画就可能继续挂着外骨骼控制器，出现表现异常，严重一点还会有悬挂引用问题。
所以这类系统除了播放正确，更关键的是生命周期管理和兜底恢复机制。
时间对其：
因为角色本体和外骨骼本质上是两套动画控制器，如果只是同时开始播放，它们后续还是可能因为各自推进时间而慢慢出现偏差。
所以我这里的做法是用统一的播放时间去驱动它们：每帧先算当前演出已经播了多久，再把这个时间同时传给本体动画和外骨骼动画。
这样两边不是各播各的，而是始终按同一个时间点更新，所以能保证帧同步。

### 结算场景优化：

#### 做了什么：

这个需求的背景是，原有结算流程比较简单，主要是收包后直接弹出结算面板，表现上偏静态。这次项目希望把结算过程做成更完整的演出流程，提升玩家在结算阶段的视觉体验。
我主要做了两部分工作：第一部分是基于 Gamebryo 的动画系统，把原来比较割裂的表现改成多段动画和镜头连续播放，构造一套完整的结算演出；第二部分是做 FOV 管理器，因为从 Unity 导出的 .nif 资源里，相机节点只保留了命名和变换信息，没有直接存 FOV 数据，所以我把这部分需求映射到特定节点或骨骼数据上，在播放过程中动态读取并驱动相机 FOV。最终解决的问题是：结算场景不再只是简单弹窗，而是有更完整的镜头和动画表现；同时 FOV 也能跟随演出过程动态变化，保证结算效果更自然、更有层次。

#### 怎么触发回调的：

结算动画本质上是由多段 kf 动画资源组成的，我会先把这些资源加载并注册到动画系统的管理器里。

段与段之间的衔接，我主要利用 Gamebryo 自带的 TextKey 回调机制。

具体做法是在每段动画的结尾或者关键时间点打上 TextKey，当播放到对应位置时，底层回调会被触发，然后驱动切换到下一段动画或下一段镜头逻辑。

这样做的好处是，动画串联的时机不是硬编码死时间，而是跟资源本身的关键帧事件绑定，更适合演出型流程控制。
注册一个回调函数（Callback Function）。通常签名类似于 void MyTextKeyCallback(NiControllerSequence* pkSequence, NiTextKeyExtraData* pkExtraData, const NiFixedString& kTextKey, void* pvAppData)

#### textkey机制：

底层：
C++ 底层本质上是一个按时间排序的数组，数组元素是一个简单的结构体（或类），包含 float fTime（触发时间）和 NiFixedString kTextKey（文本内容，比如 "start_attack", "play_sound:footstep"）
Tick 逻辑： 在每一帧的动画更新中（NiControllerManager::Update），引擎会记录该动画序列的上一帧时间 ($t_{prev}$) 和当前帧时间 ($t_{curr}$)。
如果跳帧：
底层扫描的是时间区间，所以这 3 个 TextKey 都会被扫到，并且会按照时间顺序依次触发。但这往往会引发业务层面的灾难（比如同一帧内连续播放了 3 次脚步声，导致爆音）。
解决办法：
为了避免一帧里重复执行或跨帧重复扫到同一个 key，一般会配合：上一帧时间戳当前循环次数或 loop index必要时给事件加一次性标记 / 本轮已触发记录
字符串比对费时：
NiFixedString (全局字符串池/哈希字符串)。Gamebryo 底层会在加载时将 TextKey 字符串存入全局 Hash Set，并返回一个指针。比较字符串时，其实比较的是指针地址（整数比对），而不是逐字符比对，类似于UE 的FName系统、

### fov管理器：

#### 为什么

因为 .nif 导出链路里，相机节点本身没有直接保存 FOV 数据，所以我需要找一种能够随资源一起传递额外参数的方式。

我的做法是让美术在相机对应的空节点下额外挂一个约定好的骨骼 / 节点，并用它的某个变换分量去编码 FOV 信息，这里我用的是 x 坐标。

运行时播放结算动画时，程序会同步读取这个节点的变换值，把它按预先约定的规则解释成 FOV，再进一步换算成相机视锥参数并更新到相机对象上。

这样就绕过了资源格式本身不直接支持 FOV 的限制，同时又能把镜头参数变化跟动画资源一起驱动
fov怎么计算？fov分为水平fov和垂直fov，通过最后视野的长/宽的一半除以camera到远平面距离得到，水平fov和垂直fov可以通过长宽比来转换。

#### 问题：

它依赖约定，比较适合这种定制化结算演出，不一定适合更通用的相机系统
总结
这两个项目虽然都基于比较老的 Gamebryo，但我觉得它们体现的是比较通用的客户端动画工程能力。

一个项目里我做的是把结算流程从简单弹面板升级成完整演出，要处理动画串联、镜头切换和 FOV 驱动；另一个项目里我做的是特殊服饰动画接管，要处理外骨骼挂载、控制器替换和播放后的恢复。

所以它们本质上都不是单点功能，而是在解决动画表现怎么真正落地成系统流程的问题。

## 赛车换色

### 做了什么

这个模块本质上是一个车辆外观换色系统，玩家可以抽取颜色、预览颜色，并选择是否保存到指定槽位。我的工作主要分两部分：一部分是在 Lua 侧基于 MVC 做换色面板的交互和数据流转，把 UI 展示、用户操作和业务状态拆开；另一部分是在 C++ 侧负责和服务端的通信，因为外观数据是服务端权威，所以像抽色、保存槽位、读取已有换色数据这类操作都要通过协议请求服务端。客户端这边会做一层数据缓存，再把结果提供给 Lua 层使用，或者把颜色参数传给渲染侧做最终表现。

### MVC框架

Model：负责数据和业务状态，例如当前对象是什么、有哪些配置、状态是否变化。它不直接关心界面怎么画。
View：负责界面展示，把状态渲染成用户能看到的内容，比如列表、按钮、弹窗、文本和图片资源。
Controller：负责接收用户操作，组织业务流程，决定什么时候改数据、什么时候刷新界面。

#### 我们的MVC架构：

换色模块整体仍然遵循 MVC 思路：Model 保存当前车辆、当前槽位、换色配置和界面运行状态；View 负责颜色列表、按钮、弹窗和资源展示；C而是拆成了 Mediator、Action 和 Proxy：Mediator 更偏界面内部交互协调，比如响应按钮事件、驱动界面刷新；Action 更偏模块对外能力封装，供其他系统调用；Proxy 负责和服务端通信、缓存数据、处理回包并同步更新本地数据。

#### 其它架构：

##### MVVM (Model-View-ViewModel)

自动把 View 的 UI 元素和 ViewModel 里的变量“绑”死在一起当 Model 数据改变时，ViewModel 的变量随之改变。这极大地消灭了样板代码

##### ECS(Entity-Component-System):

MVC\MVVC都是面向对象，现代游戏开发，OOP 的继承树和 MVC 的对象通信会导致致命的 CPU 缓存未命中（Cache Miss）和性能瓶颈
Entity（实体）： 只是一个纯粹的整数 ID（比如 ID: 1001）。它没有任何逻辑，甚至不算个对象
Component（组件）： 纯粹的数据结构Position {x, y, z}，Health {hp}。没有函数，只有数据。相同类型的组件在内存中是连续排列的纯数组
system（系统）： 纯粹的逻辑函数。比如“移动系统”每帧启动一次，它直接去内存里遍历所有同时拥有 Position 和 Velocity 组件的数组
优点：
CPU 缓存友好（核心优势）： 这是我们之前聊过的 Cache Line 逻辑。OOP 中对象散落在堆上，指针跳转极多。ECS 将同类组件放在连续内存（如 std::vector），CPU 一次搬一个块进缓存，几乎全是 Cache Hit。
彻底解耦： 没有 OOP 那种复杂的继承树。想让一个“玩家”能“飞”？加个 FlyComponent 即可，不需要改动父类。
极高的并行潜力： 因为 System 之间的数据依赖非常明确，非常容易做多线程并行（如 Unity 的 Job System）。
缺点：
逻辑碎片化： 简单的功能（如捡起一个道具）可能要跨越多个 System，代码很散。
系统间通信困难： 状态改变时，如何通知另一个 System？通常需要用消息队列或 Tag 组件，开销和复杂度上升。
不适合 UI 和复杂交互： UI 这种高度事件驱动、层级嵌套的场景，用 ECS 简直是自讨苦吃。

### UI 表现和业务数据的彻底解耦

我理解的“UI 表现和业务数据解耦”，不是简单地把代码分文件，而是让页面层不直接承担核心业务状态和网络逻辑。
在这个换色模块里，数据大致分两类：
业务数据：比如玩家已解锁的卡槽、每个卡槽当前颜色、抽取结果、当前可用的换色资源，这些以服务端数据为准，由 C++ 侧负责请求、缓存和提供接口；
UI 状态：比如当前选中的车辆、当前选中的卡槽、当前打开的是颜色列表还是抽取界面、某个按钮是否高亮，这些只服务于页面交互，由 Lua 层维护。
用户操作时，数据流不是“按钮直接改 UI”，而是“View 触发事件 -> 业务层请求或查询数据 -> Model 更新 -> View 根据状态刷新”。
比如用户点击颜色列表按钮时，Lua 侧先响应交互，再通过 C++ 接口拉取当前车辆对应的换色数据；拿到数据后，页面层只负责把这些数据转换成列表项和预览表现，而不会自己决定哪些颜色是合法的、哪些槽位已解锁。
这样做的好处是，UI 只是消费状态，不掌握业务真相；业务变化时可以复用同一套数据接口，页面改版时也不用去动底层逻辑。

### cpp与lua交互：

Lua 调 C++``，在我们项目里是通过注册接口暴露能力，本质上还是基于 Lua C API 的虚拟栈机制：Lua 把参数压栈，C++` 侧取参执行，再把结果压回栈返回。对于换色模块这种涉及服务端数据的场景，Lua 更多是发起请求和接收结果，真正的数据拉取、校验和缓存是在 C++ 侧完成。
C++ 拿到服务器回包后，会在对应的回调里更新本地状态，再通知 Lua 侧执行相应的刷新逻辑，比如触发 onResponse 或类似事件，让页面根据最新状态生成颜色列表和预览表现。
任何想要暴露给 Lua 的 C++ 函数，最终都必须被包装成这个长相：接收一个虚拟栈 L，返回一个 int（告诉 Lua 往栈里压了几个返回值）。

### 注册发生了什么？

当你在 C++ 引擎启动时写下注册代码，本质上是 C++ 对 Lua 喊话：“我把功能的内存执行地址交给你了，你在你的全局表（_G）里给它起个名字记下来
Lua 收到这个函数指针后，会它放在环境表中
指令解析： Lua 虚拟机读取字节码，看到了一个 CALL 指令。
查表确认： 虚拟机去查表，发现 ChangeVehicleColor 不是一段 Lua 代码，而是一个 C 函数指针 (0x00A1B2C3)。
环境准备（压栈）： 虚拟机乖乖地把 car_id 和 new_color_id 压入虚拟栈。
就在这一瞬间，CPU 的指令寄存器（PC）被强行修改，程序执行流从 Lua 虚拟机内部的 C 循环，瞬间跳跃到了你写的 C++ 函数体内！

### 遇到的问题：

做这个项目遇到最大的问题就是换色的多端实时一致性
在这上遇到了很多问题：
1.最简单，在房间内玩家换了色，其它玩家没显示
比较简单，因为原本有换车的同步相应，这个没响应是因为同一辆车换色id还是一样的，去看了下是服务器那边没发包，所以这边没收包后处理
2.显示时序问题
数据是服务器权威的，cpp这段只作为缓存，每次要拿服务器数据后再显示，这就是一个时序性问题，做法是在回包消息的响应函数内调用lua，检测结果码正确再显示，如果没收到包或者拉取失败，那就不显示颜色列表了，反正没什么影响。
3.用户连续快速切颜色
快速点击按钮，会引起的问题是客户端这边连续发包，服务器那边收到这几个包后，有一个异常机制，会直接不回包了，改进办法是给按钮加冷却
4.其它的时序问题，其实也是自己一开始写代码规范不好引起的，如果从头开始都严肃按照时许关系，这样来写，就不会出很多问题。

### 觉得哪里容易出现问题：

我觉得换色模块里最容易出问题的是异步请求导致的状态不一致，尤其是重复点击、请求并发和旧回包覆盖新状态。

我实际遇到过一个问题，就是玩家快速连续点击操作按钮，短时间内发出多次请求，可能导致服务端处理顺序和客户端预期不一致，进而引发显示错乱。

我第一层处理是在 UI 上对关键按钮加冷却或临时禁用，先防止用户短时间重复触发。

### RPC：

介绍一下RPC
不是标准 RPC 框架”。它更像是游戏客户端自定义的请求-响应消息框架，只是业务语义上看起来像 RPC：有请求函数有请求参数结构体有服务端处理后回包有客户端回调业务逻辑业务代码自己组包 → 按消息号发给 GameServer → 网络层收包 → 分发到指定 C++ 处理函数 → 再转给 Lua 业务层包：
头部是固定的，像是玩家id、时间、结果码这些，然后，我们一共是有五种操作要上报给服务器：拉取数据，抽取颜色、保存颜色、应用颜色、解锁槽位，它们共用一个包，只不过根据操作码来决定怎么操作，数据部分就是：解锁的卡槽数量、每个卡槽的颜色、当前操作卡槽这些。

#### 标准 RPC 框架和请求响应框架区别

1.使用：前者需要手动拼包，发送，后者使用起来感觉和调用自身函数一样，具体的打包发包是RPC框架自己干的
2。契约请求响应框架客户端和服务端通常靠文档来约定，改了参数会空指针，RPC用极强的强类型契约。RPC 必须先定义契约文件（如 .proto），客户端和服务端的代码都是由同一个契约自动生成的。如果服务端改了参数类型，客户端在编译阶段就会直接报错，绝不把问题留到运行时。
3.底层传输协议：
RPC：不拘一格，什么快用什么。请求框架：被 HTTP 协议死死绑架。绝大多数普通请求框架建立在 HTTP/1.1 或 HTTP/2 之上
