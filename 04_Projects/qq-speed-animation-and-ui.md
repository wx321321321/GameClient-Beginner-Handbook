这篇整理我在 QQ 飞车中做过的两类工作：一类围绕 Gamebryo 动画，完成外骨骼接管、结算串联和相机 FOV 驱动；另一类围绕赛车换色，把 Lua UI、C++ 缓存与服务端请求接起来。它们共同需要处理状态和生命周期，但各自的数据流不同，下面分开复盘。

Gamebryo 类名、回调、协议和导出限制来自我接触的项目版本，本仓库未附对应源码。涉及底层实现时，保留原有搜索线索，并区分已记录的工程行为与需要回查的细节。

## 4.17.1 Gamebryo 动画：时间驱动控制器，控制器更新对象

我接触的 Gamebryo 动画以控制器机制为中心：节点、骨骼或其他对象关联控制器，控制器随着时间采样数据并更新目标属性。外骨骼动画和结算镜头演出，是这个机制在不同对象上的应用。

### 4.17.1.1 NIF、KF 与场景图怎样连接

NIF 承载模型、骨架、场景节点、蒙皮及控制器等资源关系；KF 更偏向可独立加载的关键帧动画数据。运行时先获得模型与骨架，再把动作资源关联到需要驱动的目标上。

原笔记记录的加载过程是：文件有头部和不同类型的数据块，块间先保存索引或引用标识，加载时再把这些关联解析为内存中的对象关系。`NiNode` / `NiAVObject` 是阅读节点和空间对象的入口，蒙皮等信息由其他相关块承载。不能简单说所有数据都直接存在一棵骨骼树的节点里。

场景图把对象的局部变换与父子关系组织起来，向上传播或向下组合得到最终变换，因此角色、骨骼、挂件和相机容易共享层级管理方式。项目可以有多个根和独立场景，不宜断言 Gamebryo 的所有对象永远挂在同一棵全局树下。

### 4.17.1.2 与 UE 对照时要比较同一层次

UE 骨骼动画常先采样和混合姿势数据，再应用到组件；Gamebryo 项目的控制器与目标对象联系更直接。这会影响计算和场景更新的组织方式，但不能仅凭架构名称就判定谁一定更快。

原笔记关心的性能点仍然成立：大量指针跳转、重复深层遍历和散乱节点更新可能影响缓存。扁平骨骼数组和批量姿势运算有利于连续访问，也更便于组织 SIMD 或并行工作。不过 UE 并不是固定把 Assimp 的 `aiNode` 树拍平成数组；`aiNode` 不是 UE 骨架系统的通用源类型，原句应去掉这种错误对应。多线程能力也取决于数据依赖，不是“传一个时间进去”就自动安全。

## 4.17.2 外骨骼管理器：接管期间要正确，退出之后也要恢复

特殊服饰不只是显示一个挂件模型。例如火焰翅膀既带额外骨骼和动画，也可能要求角色本体的一部分骨骼配合演出。如果本体控制器与外骨骼控制数据同时写同一目标，就会出现不同步、覆盖或姿态冲突。

我设计外骨骼管理器，统一处理挂载、控制器接管、播放与恢复：

```text
准备外骨骼资源
→ 找到需要关联/接管的本体骨骼
→ 保存原控制器及恢复所需关系
→ 挂载外骨骼，切换相应控制器
→ 用演出时间驱动两套动画
→ 演出结束或中断
→ 恢复原控制器，解除挂载并释放关联
```

“控制器劫持”指的是这个临时替换过程，不是永久修改角色骨架。管理器既要知道接管哪些目标，也要保存足够信息恢复它们，不能只记新控制器。

### 4.17.2.1 两类风险：恢复缺失与时间不一致

恢复流程不只发生在正常播放结束。角色切状态、场景切换、动画中断、资源提前释放，都可能打断原来的结束回调；遗漏恢复会让后续动作继续使用外骨骼控制器，甚至形成无效引用。因此恢复逻辑应被统一收口，并处理重复结束或部分接管失败。

时间对齐则用共同的演出时钟解决：每帧先算演出已经播放多久，再把同一个时间传给本体与外骨骼控制器。这样两者按相同进度采样，而不是分别累计时间后慢慢漂移。这里说的“同步”是两套动画的时间对齐，不是多人网络的帧同步。

## 4.17.3 结算演出：用资源事件串联动作和镜头

原结算流程收到结果后直接弹面板，表现偏静态。我把它改成多段角色动作和镜头连续播放，再进入相应结算展示；同时实现 FOV 管理，让相机视野也能跟随演出资源变化。

### 4.17.3.1 TextKey 决定段落衔接时机

先加载并向动画管理器注册多段 KF，在结尾或关键时间点加入 TextKey。播放跨过该事件时，业务回调切换后续动画或镜头。这样衔接跟资源时间线绑定，避免在业务代码里另写一个与动画长度容易失配的倒计时。

原笔记记下的回调形式如下，作为查项目接口的线索；Gamebryo 版本和项目封装不同，不能当成通用可编译签名：

```cpp
void MyTextKeyCallback(
    NiControllerSequence* pkSequence,
    NiTextKeyExtraData* pkExtraData,
    const NiFixedString& kTextKey,
    void* pvAppData);
```

TextKey 可按“时间 + 文本事件”的序列理解：

```text
float fTime                 触发时间
NiFixedString kTextKey       例如 start_attack、play_sound:footstep
```

`NiControllerManager::Update` 是原笔记中的更新时间入口。关键机制应按**经过的时间区间**处理，而不是只比较当前时间是否正好等于某个 key：若一帧跨过三个事件，逻辑可能需要依次触发三个事件。

### 4.17.3.2 跳帧、循环与重复事件

跨过多个事件不一定是错误，例如三段必要的状态更新不能随意丢弃；但脚步声等表现事件可能不适合同一帧全部堆叠。应按事件语义决定是否合并、限频或跳过过期表现。

需要同时核对上一帧时间、当前时间、循环次数、跳转/倒放语义，以及“一轮只触发一次”的记录。比如使用半开时间区间可以避免边界 key 在连续两帧重复触发，但循环跨界要拆成相应区间处理。原稿没有证明底层具体采用哪种策略，这些是回查和业务保护的重点。

`NiFixedString` 是固定/驻留字符串相关类型，原项目利用它降低反复逐字符比较的成本。原笔记将其概括为全局字符串池、地址比较，这可作为源码核查方向；类比 UE `FName` 时只能说都避免直接重复比较长字符串，不能说两者内部结构相同。

## 4.17.4 FOV 管理器：补上导出链路缺失的镜头参数

我遇到的具体限制是：从 Unity 导出的这批 `.nif` 演出资源，相机节点保留了名称与变换，却没有按项目需要带出动画 FOV。这个限制属于当时的导出链路，不能扩展成“NIF 格式或 Gamebryo 相机永远不能保存 FOV”。

我的解决办法是在相机对应空节点下挂一个约定节点/骨骼，用它的 **X 坐标分量编码 FOV**。美术在资源里为该分量做动画，运行时 FOV 管理器读取、按约定解码，再更新相机视锥。

```text
演出统一时间
→ 更新相机相关节点动画
→ 读取 FOV 约定节点的 X 分量
→ 转换单位/范围
→ 得到水平或垂直 FOV
→ 更新相机投影参数
```

必须约定读取局部还是世界变换、数值单位、水平还是垂直视角，以及异常范围。否则父节点变换或单位变化会污染参数。

### 4.17.4.1 FOV 换算中不能漏掉反正切和半角

假设距离 d 处的视平面宽高为 W、H，宽高比 `aspect = W/H`：

```text
horizontalFov = 2 * atan((W/2) / d)
verticalFov   = 2 * atan((H/2) / d)

tan(horizontalFov/2) = aspect * tan(verticalFov/2)
```

原稿“宽/高的一半除以距离得到 FOV”缺少 `atan` 与乘 2。这个公式使用任意与相机垂直的参考平面都可，不必只取远裁剪面。

节点编码让参数和演出资源一起流转，适合当时的定制需求；代价是工具和运行时共同依赖一套隐含约定，后续维护应把这份约定明确下来。

## 4.17.5 赛车换色：区分服务器事实与界面选择

换色模块允许玩家抽取颜色、预览，并选择保存到槽位。我主要做了 Lua 侧的面板交互与数据流，以及 C++ 侧请求、回包和本地缓存。颜色是否合法、槽位是否解锁、保存是否成功，以服务端结果为准。

### 4.17.5.1 项目的 MVC 分工

| 部分 | 在换色模块中的职责 |
| --- | --- |
| Model | 当前车辆/槽位、配置与界面需要的状态 |
| View | 颜色列表、按钮、弹窗、文本和资源展示 |
| Mediator | 接收界面事件、协调交互和刷新 |
| Action | 封装模块对外能力，供其他系统调用 |
| Proxy | 请求服务端、处理回包、维护缓存并通知数据变化 |

这里把传统 Controller 的工作拆给 Mediator、Action、Proxy。实际类在哪个语言侧、谁持有最终缓存，应以项目代码为准；不要因为都参与控制就把它们当成同一个对象。

数据也分两类：

- **业务数据**：已解锁卡槽、槽位颜色、抽取结果、可用换色资源等，源头在服务器，C++ 侧缓存并暴露接口。
- **UI 状态**：当前选中的车辆和槽位、打开哪个面板、按钮高亮等，由 Lua 侧维护。

用户点击颜色列表时，Lua 发起查询或请求，C++ 返回当前车辆的数据，Model 更新后由 View 转成列表和预览。页面消费业务事实，不自己决定服务端尚未确认的解锁和保存结果。

### 4.17.5.2 一次请求与一次预览不要混成一个动作

```text
View 产生用户操作
→ Mediator / Action 组织请求
→ C++ Proxy 查询缓存或组包发出
→ 服务端处理
→ C++ 回包函数校验结果码、更新缓存
→ 通知 Lua（如 onResponse / 事件）
→ 校对当前页面上下文
→ 刷新 Model、View 与车辆颜色表现
```

本地预览可以先改变渲染参数，但“看起来换了色”不代表“服务器已经保存并向其他玩家同步”。这正是后面多端一致性问题的根源。

## 4.17.6 Lua 与 C++ 接口怎样工作

我使用注册接口向 Lua 暴露 C++ 能力。标准 Lua C API 通过 `lua_State*` 对应的虚拟栈交换参数与返回值，C 回调的基本类型是：

```cpp
typedef int (*lua_CFunction)(lua_State* L);
```

进入回调后，C/C++ 从 Lua 栈读取参数，执行逻辑，将返回结果压栈，返回值表示返回结果数量。项目绑定库可以自动生成包装，不表示所有原始 C++ 方法都必须手工改成这一个签名。[Lua 5.4 官方 C API](https://lua.org/manual/5.4/manual.html#lua_CFunction)

注册时把 C 函数/闭包放到 Lua 可访问的表中，可能是 `_G`，也可能是模块表、对象方法表或注册表。Lua 执行 `ChangeVehicleColor(car_id, new_color_id)` 时，VM 解析出相应 C 函数值，按 C API 约定调用包装函数。

原稿用“CPU 的 PC 被强行修改、瞬间跳出 VM”解释这个过程容易误导：它就是解释器执行到 C 函数分支后的普通原生函数调用，不需要特殊强制改写机制。

网络返回是稍后的另一条调用链。C++ 收到服务端数据后先更新缓存，再通过约定回调或事件通知 Lua；发送请求时立即刷新结果列表，就会读到旧数据或尚未存在的数据。

## 4.17.7 我实际遇到的一致性与时序问题

### 4.17.7.1 同一辆车换色，房间里的其他玩家没变

项目已有换车同步，但同一辆车只是颜色变化时，车辆 ID 没变，原有同步路径没有覆盖。排查发现服务端没有发出相应更新包，客户端自然也没有回包可处理。

这个问题说明同步判断不能只用车辆 ID：车辆外观变化也需要进入协议或状态更新链。不能只在本机预览代码上反复刷新来修复远端未收到消息。

### 4.17.7.2 列表展示早于数据到达

服务端是权威，C++ 只是缓存；请求之后不能立刻假设拿到了最新数据。我的实现改成在回包响应中检查成功结果码，再调用 Lua 展示颜色列表。没收到包或拉取失败时不展示该列表。

这是当时的实际处理。若继续完善体验，可在界面上区分等待与失败，但这里不把尚未实现的方案写成已有成果。

### 4.17.7.3 快速连续点击触发多次请求

我遇到用户快速操作后连续发包，服务端的异常/限制处理可能导致不回包的情况。具体是限流、防重还是其他校验，原稿没有服务端证据，不宜只写成“收到几个包就会异常”。

第一层处理是在关键按钮上加冷却或临时禁用，减少重复触发。它能降低频率，但不能从逻辑上完全解决并发：旧回包覆盖新选择、页面已切车但旧请求刚返回等，还需要根据车辆、槽位、请求上下文判断是否适用。后者是复盘时识别的风险，原稿没有证明已经补齐。

### 4.17.7.4 反思：把时序当成接口的一部分

早期代码对“发送、返回、更新、展示”顺序处理不够严格，导致多个零散问题。重新看这段经历，关键不是多加几个刷新函数，而是为每种操作明确：谁发起、什么时候认为成功、更新哪份数据、谁通知界面，以及中途切换页面后如何处理结果。

## 4.17.8 项目消息协议与 RPC 的区别

这套换色通信在业务上像远程调用，但实现是项目自己的请求—响应消息框架：

```text
手动创建请求结构体并填字段
→ 指定 ID_CMS_REQUEST_KART_CHANGECOLOR_OPERATE
→ 调用统一发包接口
→ 网络层收包，按消息号分发到 C++
→ switch 操作类型，更新缓存
→ 触发 Lua 事件
```

原笔记记录五种操作共用一个包，通过操作码区分：**拉取数据、抽取颜色、保存颜色、应用颜色、解锁槽位**。相关数据包括已解锁槽位数、各槽位颜色、当前操作槽位等。玩家 ID、时间、结果码等属于记录的协议字段线索；请求与回包的头部不必完全一致，结果码通常在响应中，需以协议定义确认。

| 比较点 | 手写请求—响应框架 | 带调用抽象的 RPC 框架 |
| --- | --- | --- |
| 调用方式 | 业务显式构造消息、发送和处理回包 | 常把编解码与分发封装到代理/桩代码后面 |
| 契约 | 可以有结构体、消息定义、代码生成，也可能依赖文档 | 可以使用 IDL/Schema，也可能是动态约定；不是全部必须 `.proto` |
| 类型与兼容 | 取决于协议设计和实现 | 强类型生成可提早发现部分错误，但不能保证部署后的版本不兼容全在编译期暴露 |
| 传输 | 可用 TCP、UDP、HTTP 等 | 同样不由“RPC”这个名字唯一决定 |

原稿把“手动拼包”和“像本地函数一样调用”的前后对应写反，又把请求—响应限定为 HTTP；两处都应纠正。参数变化也不必然导致“空指针”，常见后果应具体分析为解码失败、字段误解、版本不兼容或业务错误。

我记录的飞车项目分工是：UDP 用于高频实时同步，TCP 用于游戏主服务及换色，HTTP 用于下载。这是接触到的模块范围，不代表项目所有流量永远如此。

## 4.17.9 MVC、MVVM、ECS 的旁支理解

这部分是做 UI 时延伸出的架构比较，应放在项目数据流之后理解。

MVVM 用 ViewModel 暴露界面状态和操作，配合绑定机制减少手写刷新；“自动绑定”依赖框架提供通知和绑定能力，并不是把变量写进 ViewModel 后 UI 就天然跟着变化。

ECS 把实体标识、组件数据和系统处理分开：Entity 常是带有效性信息的 ID，Component 存状态，System 按所需组件查询并处理。数据导向实现可将同类数据连续存放，改善缓存并让读写依赖更清晰，利于并行调度。但组件是否连续取决于存储设计，缓存命中与多线程安全也不是 ECS 名字自带的保证。

它的代价是跨系统流程和事件通信可能更分散，需要额外组织消息或 Tag。UI 的层级和交互通常用 MVC/MVVM 更直观，但不能说 ECS 绝对不适合 UI。MVC/MVVM 主要讨论界面职责，ECS 主要讨论实体数据和处理方式，二者可在同一项目共存；不应把 UI 架构选择直接归结为 OOP 必然产生致命 Cache Miss。
