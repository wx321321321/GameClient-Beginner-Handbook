Arena 的第一把武器是射线步枪：弹匣 3 发，备用弹药 5 发，射速 600 RPM，换弹 2 秒。
这些数值故意很小，便于观察状态边界；它们是本课程的新设计。
先把扣弹、射速和换弹做正确，再换成大弹匣、霰弹枪、飞行弹或穿透武器。
只要“同一发到底是否成立”还不明确，增加特效只会让错误更难定位。

## 4.3.1 武器配置和运行状态分开放

配置是某个版本下所有同类武器共享的数据，运行状态属于某个玩家手里的具体实例。

| 数据 | 示例 | 谁可以修改 |
| --- | --- | --- |
| 配置 ID 与版本 | `rifle_basic`、版本 1 | 构建或受控配置发布流程 |
| 弹匣容量、射速、换弹时长 | 3、600 RPM、2 s | 配置加载器；进对局后固定版本 |
| 射程、基础伤害、散布角 | 100 m、30、0.01 rad | 配置加载器 |
| 当前弹匣、备用弹药 | 3、5 | 服务端武器规则 |
| 状态、下次可开火 tick、换弹结束 tick | Ready、0、无 | 服务端武器规则 |
| 本地后座、枪口火焰实例 | 可见效果 | 客户端表现层 |

客户端可维护预测弹药，但服务端快照中的数值最终覆盖它。
配置加载时检查容量、射速、时长、数值范围和资源 ID，不能等到开火时才发现除零或负弹药。
对局锁定配置版本；中途热更新需要明确迁移规则，入门阶段不做。

60 Hz 是本课程的示例模拟频率。
600 RPM 等于每秒 10 发，因此两次开火间隔为 6 个 tick。
一般换算可用 `ceil(60 * 60 / RPM)`，它会把射速量化到 tick 边界，实际射速可能略低。
第一版每武器每 tick 最多接受一发；更高射速应引入子步时间或发射批次，不能随意循环补发无限颗。
换弹 2 秒对应 120 tick，所有结束判断都采用 `now >= endTick`。

## 4.3.2 Ready 不等于此刻可以开火

我们用三个互斥阶段：`Ready`、`Reloading`、`Disabled`。
射击冷却由 `nextFireTick` 表示，不再增加一个容易和换弹交叉的“正在冷却”布尔值。

```text
Ready --合法换弹请求--> Reloading --到结束 tick--> Ready
Reloading --取消换弹--> Ready
Ready / Reloading --死亡、卸载--> Disabled

Ready + now >= nextFireTick + magazine > 0 + 允许操作
    --接受开火--> 扣 1 发，推进 nextFireTick，产生一次 ShotAccepted
```

开始换弹时不转移弹药；完成时一次性执行 `min(容量 - 当前弹匣, 备用弹药)`。
取消换弹不补弹。死亡先进入 Disabled，不能在下一次 Update 又完成旧换弹。
按住开火只是持续意图，输入层或武器驱动器按规则生成不同 `ShotSeq` 的请求。
半自动武器只响应按下沿；按键释放不能通过动画通知来推断。

接口输入包括射手、会话、`ShotSeq`、服务端当前 tick、瞄准意图。
输出是包含接受或拒绝原因的结果，接受时还输出唯一的射击事件。
结果和副作用必须一起提交：不能先扣弹，碰撞模块报错后又把同一请求当成新请求重做。
实际实现可先构造结果，再在单线程规则事务中更新状态和事件队列。

下面是 C++17 独立的纯规则示意，可编译为目标文件；它只演示冷却边界，不包含网络去重。

```cpp
#include <cstdint>
#include <stdexcept>
using Tick = std::uint64_t;

struct FireGate {
    int ammo = 3;
    Tick nextFire = 0;
    Tick interval = 6;

    bool Accept(Tick now) {
        if (interval == 0) throw std::logic_error("zero fire interval");
        if (now < nextFire || ammo <= 0) return false;
        --ammo;
        nextFire = now + interval;
        return true;
    }
};
```

`now == nextFire` 可以开火，这是测试必须覆盖的边界。
这里不追赶所有错过的射击：玩家卡顿后到达当前 tick，只能根据当前状态接受一发。
不能把客户端声称经过了十秒当成服务端可以一次批准一百发的依据。
完整的状态与重复请求实验见 [shooter-labs.cpp](../examples/course/shooter-labs.cpp)。

实验为每个 `ShotSeq` 缓存第一次处理结果，重复请求得到相同答复，冷却拒绝不会在重试时变成成功。
生产键必须包含 `sessionEpoch + shooterHandle + ShotSeq`，缓存属于会话射手，不能在切枪时清空。
实验仅演示有序请求流；网络乱序包要先排序或使用接收窗口，不能直接按最大序号丢掉合法的旧包。
实验的结果表不淘汰，仅适合有限测试；正式服需要有界重放窗口及窗口之外的明确拒绝规则。

## 4.3.3 散布是射线方向分布，后座是反馈与瞄准变化

准星中心给出基础瞄准方向，散布围绕它采样偏移。
镜头抖动、枪模回弹和服务器计算的弹道散布是三件事。
如果镜头后座确实改变瞄准，变化要体现在后续输入中；不能让枪模抖动暗中决定权威方向。
移动、跳跃和连续射击可改变散布角，但这些条件取自服务端认可的运动、武器状态。

圆锥内“角度均匀”和“立体角均匀”并不相同。
下面选择立体角均匀；输入 `u,v` 是 `[0,1)` 的两个随机数，输出局部 X 向前的单位方向。
它是可编译为目标文件的 C++17 数学示例，不依赖引擎。

```cpp
#include <cmath>
#include <stdexcept>
struct Direction { double x, y, z; };
Direction UniformCone(double halfAngle, double u, double v) {
    constexpr double pi = 3.14159265358979323846;
    if (!std::isfinite(halfAngle) || halfAngle < 0 || halfAngle > pi ||
        !(u >= 0 && u < 1) || !(v >= 0 && v < 1))
        throw std::invalid_argument("invalid cone input");
    const double c = 1 - u * (1 - std::cos(halfAngle));
    const double s = std::sqrt(std::fmax(0.0, 1 - c*c));
    const double phi = 2 * pi * v;
    return {c, s * std::cos(phi), s * std::sin(phi)};
}
```

将局部方向用正交基变换到世界空间；方向归一化和基向量构建由数学适配层提供。
若要预测一致，双方必须统一随机算法、种子派生、每发的取样次数和配置版本。
不能假定 `std::uniform_real_distribution` 在所有标准库实现中产生逐位相同结果。
可以由服务端分配种子并随接受事件回传；客户端提前显示近似轨迹，确认后纠正。
如果允许客户端提交种子，必须防止其挑选“最好的一次随机结果”。

## 4.3.4 相机瞄准和枪口遮挡分别处理

相机射线先取得期望目标点，枪口再朝该点查询真正可发射路径。
第三人称尤其需要这一层：相机能看到墙外不代表墙后的枪口可以开火。
服务端采用自身维护的角色姿态、允许的视角和枪口位置，不能接受客户端任意上报的世界空间起点。
枪口贴墙、相机在身体后方、目标近于枪口都是要单测的场景。
原有 [相机与射击方向笔记](camera-and-shooting-direction.md) 保留了坐标转换和原项目追踪线索，可用于对照。

## 4.3.5 射线和飞行弹共用结果，不共用时间模型

| 路径 | 服务端计算 | 客户端表现 | 典型边界 |
| --- | --- | --- | --- |
| Hitscan | 在一次认可的开火时刻查询射线 | 曳光线可晚些播放 | 延迟补偿与遮挡策略 |
| 飞行弹 | 创建实体，每 tick 推进并扫掠碰撞 | 插值或预测可见弹体 | 高速穿透、寿命、销毁同步 |

飞行弹使用米、秒：`pNext = p + v * dt + 0.5 * g * dt * dt`，`vNext = v + g * dt`。
本课程 Z 向上，重力例子为 `(0,0,-9.81)` m/s²。
不能只在 `pNext` 做一个点检测；应从旧位置到新位置做线段或球体扫掠，记录最早碰撞时间。
带半径的榴弹适合球扫掠，复杂运动则需要引擎连续碰撞或子步处理。
命中后剩余步长是停止、反弹继续还是穿透继续，必须由弹种定义。
到达寿命、越界、命中或销毁射手不一定同义；例如射手死亡后已发出的火箭可以继续存在。

射线击中和弹体碰撞最终都产生同一类候选命中记录：射击键、目标句柄、目标生命版本、位置、法线、部位。
它们交给 [伤害与技能](shooter-combat-and-abilities.md) 结算，而不是让特效回调扣血。

## 4.3.6 穿透从有界的材质规则开始

第一版只做不穿透；第二版用“初始能量 + 材质厚度成本”的教学规则。
查询入射和离开表面，得到有效厚度；扣除能量后仍大于零才继续剩余射程。
需要明确哪些网格支持厚度查询，单面薄片和非封闭网格不能凭两个任意命中点猜厚度。
每次继续前沿方向推进一个合理 epsilon，避免同一表面无限命中。
每发设置最大穿透次数、总查询次数、最小剩余能量和最大射程。
多颗霰弹或穿透命中同一目标时，为每个伤害贡献分配独立伤害事件 ID；整个开火请求仍只扣一发弹药。
不要把“同一 ShotSeq 去重”错误扩展成“这发只能对一个目标造成一次伤害”。

## 4.3.7 验收时看数据和事件数量

- 冷却边界前一 tick 拒绝，恰好到边界接受；客户端频繁请求不能增加服务端射速。
- 同一射击键重复 100 次，只扣一次弹，产生一个接受事件；第一次拒绝的请求始终拒绝。
- 换弹完成调用两次只转移一次；取消、死亡、切枪的弹药规则都可复现。
- 相机看到目标但枪口被墙挡住时，不能绕过墙造成伤害。
- 600 m/s 飞行弹在一个示例 tick 前进约 10 m，仍能命中中间薄障碍物。
- 随机样本检查单位长度、锥角上界和平均分布；不凭“看起来随机”验收。
- 穿透查询在所有坏几何输入下都能在预算内退出。
