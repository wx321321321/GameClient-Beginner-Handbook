# 内存模型与编译管线
## 一.基本概念：
    --这里是基本要了解的概念，也是面试中常问的基本点，在了解了这些之后，才可以向下去深挖原理。
### 1.内存模型：
    一般指，cpp内存模型，广义上cpp内存模型分为五个区域：代码区（存储编译好的代码段）、
    全局静态区（存储全局变量、静态变量，其中又分为初始化的部分和未初始化的部分）、
    常量区（如字符串常量、虚表等）、堆区（动态分配的变量存储的地方，需手动处理）、栈区（程序自动管理，储存局部变量）。

### 2.编译管线：
    总共会经历四步：预处理（文本替换）、编译+汇编（编译器发挥作用）、链接（链接器发挥作用）。

### 3.地址与内存：
#### 存储结构：
计算机存储结构为：CPU-寄存器-Cache-内存-外存，其中，内存外存作为主要的存储媒介。
#### 地址：
物理地址：指内存上的地址，逻辑地址指os管理所有进程的地址，外存地址一般是磁盘地址。
#### 段页式管理：
对于内存、外存上的空间，os使用页的方式进行管理，每次交换页。而段是程序员划分的逻辑段，不常用。
#### 虚拟地址：
os管理资源，当一个进程创建，os会分给他内存空间，但物理内存上的空间不是连续的，而进程渴望得到一段连续的空间，所以os会给进程一段连续的虚拟地址，并为进程创建页表（实际上也是一段连续的信息，开头地址存在进程控制块中），在页表中存储，虚拟地址划分为页后对应的实际物理页。
#### 进程-内存-外存信息交换

##### 执行单位：CPU 里的 MMU 内存管理单元。
它负责把程序使用的 虚拟地址 翻译成真正访问 RAM 的 物理地址。
##### 交换原因：
cpu只能直接读取内存中的信息，而内存空间有限，所以os要负责页的换入换出，常用的算法如先进先出、LRU最近没被使用、LFU最近最少被使用。
##### 详细过程：
（1）当启动一个进程后，os读取其进程控制块，找到页表起止地址。（2）当进程要用某个页，首先cpu去内存查页表，找到对应页，如果对应页已在内存中，直接读，如果没在，发生缺页异常，由os负责去外存中寻找对应页，将其读入到内存中。
##### 优化：
__TLB快表__：里面存着常用页的对应信息，是页表信息部分的备份，类似于cache，cpu去查更快，节省了访问内存的时间。缺点是每换一次进程内容全部失效，需要清空并重新填入（进程刚加载的慢热原因）
__一种解决办法__：TLB 里的每条记录打上一个“标签”，标记它是属于哪个进程的。这样切换进程时，不需要清空 TLB。CPU 只要比对一下当前的进程ID和缓存里的标签对不对得上就行了。这极大地提升了高性能服务器切换进程时的速度。
##### 几种缺页异常：
（1）读的地址不合法，发生缺页中断，抛出错误。
（2）有对应的物理地址，但在外存，内存中没有，需要缺页中断，去将页替换进来。
（3）分配了空间，但还没对应的物理空间：
	eg：int* p = new int[1000000];，页表先记着这段地址属于变量，但此时还没分配真实物理页框。当第一次向里面写入内容，发生缺页中断，访问到对应页，才会触发缺页，然后 OS 给这页分配物理页。      栈也是如此，在地址范围内，慢慢增加。


# 二、编译管线：
从cpp文件到.exe，都经过了哪些步骤？

### 1、预处理：本质上还是文本替换和展开，还没真正理解 C++ 语义
由“预处理器”完成的，而预处理器通常集成在编译器里。输出的还是cpp代码。
主要职责：处理 #include、处理宏 #define、去注释
#### pragma 家族:
	一个预处理指令。它的核心作用是：允许开发者向编译器发送特定的非标准指令。实际起作用是编译器读取才能明白怎么做！
__预处理指令__：在 C/C++ 的语法解析规则中，有一条绝对的“一刀切”标准：凡是以 # 开头的行，在词法归类上，统统被称为预处理指令 (Preprocessor Directives)。
走预处理器的后门： 利用现成的 # 通道。因为 C 标准规定：如果编译器遇到了它不认识的 #pragma 指令，它必须默默忽略掉，绝对不能报错，通过这个避免更改c语法。

__#pragma once__ 只编译一次
			基于“物理文件路径”来判断的。如果同一个头文件在操作系统中通过不同的路径（比如存在软链接、硬链接，或者网络映射盘的不同挂载点）被引用，编译器可能会把它当成两个不同的文件
__更改对齐方式__：
#pragma pack(push, 1)#pragma pack(pop)

### 2.编译：编译器对cpp进行编译，生成.s文件
编译的基本单位不是纯粹的 .cpp 文件，而是翻译单元
翻译单元 = 1 个 .cpp 文件 + 展开所有 #include 的头文件内容 + 展开所有宏定义 - 剔除条件编译（#ifdef）未命中的代码
#### （1）词法分析：这个字符序列能不能被识别成合法的基本单位：
eg：int a = 10 @ 3;
@ 在普通 C++ 表达式里不是合法 token，词法分析阶段就可能报错。
#### （2）语法分析：语法分析器会看这些 token 能不能组成合法 C++ 结构
eg：int = a 10 + ;语法分析报错
#### （3）语义分析：检查这段程序到底合不合法
语义分析是真正开始理解程序意义的阶段，主要作用：检查（1）变量是否已声明（2）类型是否匹配（3）函数调用是否合法（4）作用域和名字查找
##### 建立内容：
__符号表__：维护的一张表，用来记录程序里的名字，以及哪些需要去寻找实现的函数的名字
__类型信息__：类型信息就是记录变量、表达式、函数、类成员的类型。
__作用域信息__：作用域信息用来判断一个名字能不能在当前位置被访问。
__类布局信息__：确定一个类对象的内存结构。
__重载决议结果__：记录函数调用最终选哪个版本
__模板实例化结果__：记录模板生成出来的具体类型/函数

##### 名称查找：
编译器看到 func()，它得先确定这个名字在哪个作用域（Scope）里,这也是为什么，子类定义了同名函数，即使不同参数，也会隐藏父类的所有函数，因为子类定义完后直接将名字作用域确定了。如果没定义，会往上寻找，将名字的作用域定为父类
__名字查找顺序__：
	局部作用域（函数内部）-》类/派生类作用域（Derived）-》基类作用域（Base -> GrandBase...）-》命名空间作用域（如果你在某个 namespace 里）-》全局作用域-》ADL 查找（参数相关查找，如果是函数调用）。
__如果找不到__：nodeclare
	验证类型并不需要等到最后面的代码生成它在名字查找完后的一瞬间就开始了。

#### 名称重整：支持重载的原因：
c++里面的函数在编译阶段将函数的参数类型、数量、顺序等信息作为签名，与函数名组合成一个新的符号名记录到符号表中。因此，同名但参数不同的函数在底层实际上是完全不同的名字，所以支持函数重载。返回值类型不参与名字重整，只有函数名、参数类型数量顺序
__为什么返回值不参与名字重整__:
	因为调用歧义
		int func();    // 重整为 _Z4funci
        void func();   // 重整为 _Z4funcv
	fund()不知道调用哪个函数
#### ODR单一定义规则：
.h 头文件中定义了全局变量或实现了非 inline 的函数，被多个 .cpp 包含后，每个 .cpp 编译出的 .obj 里都有这个符号。链接器在合并数据段/代码段时，发现同一个符号出现了多次，就会报错。

#### （4）中间表示（IR）生成
	编译器通常不会直接从 AST 一步生成机器码，而是先转成一种更适合优化的中间表示，进行处理：
	优化常量-》折叠常量-》传播-》死代码删除-》公共子表达式消除-》内联-》循环优化
    然后根据CPU架构生成对应代码，一般是汇编代码（.s）
### 3.汇编：生成机器码，结果为.obj文件
#### .obj文件格式：
__ELF Header__ ：它是 64 位还是 32 位，字节序是大端还是小端？
__text__：二进制机器码（CPU 的指令流）。
__rodata__：只读数据，比如代码里的字符串常量 ""Hello World""。"
__data__：初始化的全局、静态变量。
__dss__：未初始化的全局、静态变量。
__symtab__：符号表：链接时的核心索引。它记录了两个清单：我能提供什么：本文件定义的函数名、全局变量名及其在文件内的偏移地址（例如：func1 在 .text 的第 20 字节处）。我需要什么：本文件用到了但没定义的外部名称（例如：我需要 Base::vtable）。
__rel.text__：重定位表：告诉链接器哪些指令需要“打补丁”。编译 a.o 时，不知道引用的 b.o 函数地址，所以它会先在代码里留下占位符，并在重定位表里写下：链接器！等你知道了 Base::func 的地址后，请回来把 0x40 偏移处的这 4 个字节改成那个真正的地址
__Section Header Table__：描述以上所有段的起始位置和长度。
								

### 4.链接：将所有的.obj文件链接到一起
输出是一个.exe文件，结构上与 .obj 很像，但它变得“完整”且“自洽”了：
（1）不再有重定位表：所有的地址都已经填好了，可以直接交给 CPU 跑
（2）包含入口地址 (Entry Point)：文件头里记录了程序的第一行指令在哪里
（3）包含加载信息：告诉操作系统，运行这个程序需要多少内存，哪些部分是只读的。
#### 流程：
__符号解析__：main.o 里调用了 foofoo.o 里定义了 foo链接器要把这俩对上。
__重定位__：前面目标文件里很多地址是占位的。链接器要把：函数地址全局变量地址跳转目标都填成最终地址
__合并 section__：链接器会把所有 .obj 文件中属性相同的段合并在一起。所有的 .text（机器码）合成一个大的代码段。所有的 .data 合成一个大的数据段。意义：这样操作系统加载程序时，只需要分配一块连续的内存给代码，一块给数据，效率极高。
__处理库__：静态库的代码可能会被拷进去；动态库则通常记录依赖关系，运行时再装载。

#### 静态链接：
链接时，将所有的lib等包含进入最终的程序中。.lib实际上就是一个别人写好的.obj的集合。
优点是独立运行，没有环境依赖；缺点是体积大，如果有多个程序复用同一个库，内存和磁盘中会有多份代码副本

#### 动态链接：
优点是多个程序共享内存中的同一份代码段（数据段各自独立），节省物理内存；更新方便（只需替换 DLL）。缺点是存在依赖问题，运行时有少量的性能开销（通过跳转表调用）
dll不会被塞进 exe 的代码段里”，而是作为一个独立模块，被映射到进程虚拟地址空间的某一段区域（大多数是mmp）
##### 装入时链接：
程序启动时，操作系统加载器根据 .exe 里的导入表，自动加载需要的 DLL / so，并把函数地址填好。
没有手动加载.dll，但程序用了里面的函数。链接后，.exe 里的导入表会记录：需要导入.dll，所以库在程序启动时自动加载，符号在启动阶段完成绑定。

##### 运行时链接：
程序运行到某一段代码时，自己调用 API 加载动态库，再自己查找函数地址。

![](../images/01/LinkCompare.png)

### 5.程序运行前的流程：
创建进程->建立虚拟地址空间->把可执行文件和共享库映射进去->设置代码段、数据段、栈、堆初始状态，做动态链接器需要的符号解析->把入口点准备好最后跳到程序入口
__构造函数的调用时机__：全局/静态是main前，栈上和new分配的在main后。


# 三、内存模型：
在了解了计算机存储管理以及编译出来的文件内容后，要去考虑cpp内存空间和它们之间的关系，以及os是如何去做到上述内容的。

## 1.内存分区
实际上，一个操作系统的内存分区远不止cpp五层内存结构那么简单。一种基本的框架如图：
![](../images/01/Memory_Model.png)

#### 1.保留区：虚拟地址为0的周围的地址空间。
最底部通常有一小块不可访问的区域。这就是为什么 C++ 里操作空指针 会立刻触发崩溃的原因——操作系统故意不给地址 0 及其附近映射任何物理页。

#### 2.代码区：部分函数的代码编译后的机器指令
__其它函数为什么不被存入：__ 某些代码根本没进最终可执行文件，那当然不在代码区.像 printf、std::cout 背后的很多代码，可能在 共享库 / 动态库 里，不一定都在你主程序自己的代码区里，而是运行时另外映射进来。内联、优化、死代码消除

#### 3.全局静态区：
分为初始化和未初始化部分，未初始化部分会在程序启动前全部刷0，存全局变量和静态变量。
__未初始化的 static 变量和初始化为 0 的 static 变量，在可执行文件里占据磁盘空间吗?__
操作系统不需要在 .exe 文件里存储成千上万个 0，它只在文件头记录一个需要多大的 BSS 空间。直到程序被装入内存运行时，操作系统才会真正在物理内存中分配这块区域，并自动将其全部清零。
__static const__ 存在静态存储区的只读段。全局和函数内的必须初始化，类内的可以在类外初始化。

#### 4.常量区：存常量、虚表。
__对于动态链接进来的虚函数：__
虚表虽然可能在只读段，但装载阶段系统会先根据重定位信息把里面该修正的地方处理好，之后再按只读权限运行
可执行文件里的 .rodata 是“逻辑上的只读数据”但程序装载时，加载器并不是完全不能碰它。只要该段存在需要重定位的内容，加载器就会在装载/重定位阶段进行修正修正完后，再以只读方式供程序运行

#### 保护页：
在栈的底部、堆的顶部，以及各个重要区域之间，操作系统会故意放置一些没有映射物理内存、且没有读写权限的虚拟内存页，如果出现无限递归，查到这里，就会报错。
#### 5.堆：可向上扩展
堆，也被称为动态分配区，是程序员可以手动去管理的区域
__堆底指针__：堆底是一个固定的内存地址。当可执行文件被加载到内存时，堆的起始地址就已经确定了（通常在未初始化数据段 BSS 之后）。操作系统在进程的内存描述符中会记录这个起始地址。
__堆顶指针__：在 Linux 内核中称为 brk 。它标识了当前堆区的最高有效地址
当我们在 C++ 中调用 new 或 malloc，且底层分配器发现空间不够时，会通过系统调用 brk() 或 sbrk() 来向上移动这个堆顶指针。指针推高后，操作系统会将新的虚拟内存地址映射到物理内存页上，堆的范围就扩大了。
##### 碎片：

__内部碎片：__
__产生原因__：整个结构体大小是最大成员的倍数、任何类型的成员其起始地址必须是它自身大小的整数倍。为了满足这两条要求，需要使用padding补全字节。
__结构体内排序__：为什么是从大到小，不是从小到大：基本数据类型的大小通常是 2 的幂（1, 2, 4, 8）。如果你从大到小排，前面占据的内存大小总和，必然是后面小数据类型大小的整数倍。这意味着内部碎片完全在尾部，易于优化。
__alignas__： alignas(512) A* D=new A(); 对齐方式
__优化__：#pragma pack 一般用#pragma pack（push，1）#pragma pack（pop，1）中间包裹需要对齐为1的struct内容


外部碎片： 当从堆上连续分配三个1B，但中间的先释放了，这个不能给别人用（因为别的要求可能是2B，太小了），从而一直闲置，这就是外部碎片。产生原因是频繁newdelete+堆的分配释放没有顺序。
__解决办法__： 内存池

#### 6.未分配区域
堆的顶部和栈的底部之间，有着一大片区域，是没有使用的。

#### 7.mmp：地址映射区域：在未分配区域的高位，可向下扩展
并不是所有动态内容都会存入堆中，
__产生原因：__ 堆区是通过移动顶部的边界来扩张和收缩的。它是一个连续的线性空间。对于大内存带来了一个极其严峻的内存释放问题。所以不会在堆中对其进行分配，是在mmp区域。
__对象：__ C++ 代码一口气申请极大块内存（比如超过 128KB）时，分配器会直接在这里开辟空间。以及程序依赖的各种动态链接库（Windows 的 .dll，Linux 的 .so）也会被操作系统加载映射到这个区域
__缺点：__ 性能开销高，会系统调用。

#### 8.栈：完全被卡死，不能扩展

__栈顶指针：__ 永远指向最新被压入的数据。
__栈底指针：__ 它指向当前所在函数调用帧（Stack Frame）的底部。它的主要作用是作为一个锚点，用来定位当前函数内部的局部变量和传入的参数

__栈为什么没有碎片__：栈的分配和释放本质上只是对一个寄存器进行加减法。存入变量就将RSP指针向下移动，将内容写在这一片空间内。 代码编译成二进制的那一刻，每一个函数需要多少栈空间，已经像刻砖头一样写死在汇编指令里了。编译器会维护一张内部的符号表，取的时候根据符号查类型决定大小

__函数调用过程：__ 
（1）保存现场：调用者将参数放入压栈，并将返回地址（下一条指令的地址）压入栈中。
（2）建立新栈帧：CPU 会将当前的栈底指针寄存器压栈保存，将当前的栈顶指针寄存器的值赋给 栈底指针，标志着 funcB 的栈帧正式开始。
（3）分配局部变量空间：通过向下移动栈顶指针，在栈上圈地给 funcB 的局部变量使用。
（4）执行与销毁：函数执行完毕后，执行 leave 和 ret 指令，将栈底指针拨回到原来的位置，程序跳回返回地址继续执行。

__省略栈底指针：__  编译器在编译阶段就能算准栈顶 在每一行代码的准确偏移量。所以栈底指针实际没用了。于是编译器会直接把栈底指针当成一个普通的通用寄存器来使用，用来存运算数据，从而榨干 CPU 的最后一滴性能。

__线程帧：__ 主线程栈与子线程栈：
主线程栈：内核在进程虚拟地址空间的最顶端（高地址）划定一块区域作为主线程栈。物理绑定：内核会把当前的栈指针（RSP/ESP）指向这个位置
子线程栈：线程库（如 glibc）在创建子线程时，会调用 mmap 在进程的mmp申请一块固定大小的内存（默认通常是 8MB）

#### 堆和栈区别：
	1.堆是程序员手动分配，手动释放，栈是系统自动调用的，主要存储局部变量、函数切换上下文等。
	2.堆可分配空间较大，栈可分配空间较小 
	3.堆内存地址从低到高增长，栈从高向低。
	4.分配效率：栈分配较快，栈极快： 栈的内存分配和释放仅仅依靠移动 CPU 的栈指针，堆较慢，需要mallocfree。
	5.栈没有碎片，堆经常分配会产生大量外部碎片和内部碎片。

## 2.内存管理

### cache
#### L1:是离 CPU 核心最近的一级缓存。
最快、最小,通常每个核心私有一般分成两部分：L1I：指令缓存，L1D：数据缓存

#### L2 Cache：二级缓存，比 L1 大，但比 L1 慢。
比 L1 容量大，速度比 L1 慢一点，通常也是 每核私有，但不同架构可能有差异
#### L3 Cache：L3 是三级缓存，容量更大，但更慢。
多个核心共享、会有数据并发问题

### 内存管理器：
系统的存储空间是os管理，当动态分配需要物理页时，如果每次都向os申请，会产生系统调用，影响性能，所以，在os下实现了一个内存管理器，它的作用是，每一次向os申请一大段内存，并自行进行管理，user可以通过malloc、free这两个接口来申请。管理范围是堆底到堆顶指针的范围。
（1）当收到malloc申请，内存管理器首先看自己管理的内存是否可以分配，如果可以，拿一块稍微大一点的内存，前面装header信息，后面空闲区域为申请的大小。
（2）如果不可以分配，去向os申请移动堆顶指针，如果os同意了，拿来一大块内存，进行管理。
（3）如果os不同意，说明空闲区也不够分了，malloc失败，返回nullptr。

__管理方法__：
隐式空闲链表：在每个块首字节中标记块大小以及是否占用（因为8字节对齐，后3位都是0，用一位当标志位）
显式空闲链表 怎么做： 在空闲块的 User Data 区域里，偷偷塞进两个指针：next 和 prev。查找： 这样所有的空闲块就形成了一个真正的双向链表。查找时只需要遍历空闲块。

__header信息__：上一个块大小、当前块大小、当前块是否被分配，这也是free为什么不需要知道要释放多大空间的原因，直接去查header就好

### malloc\free:
内存管理器的接口。

### new\free：
基于mallocfree的操作符，但会调用构造、返回对象类型指针，自动计算大小空间。失败爆出异常，bad_alloc。

__std::bad_alloc__:抛出条件：内存真的耗尽了，堆内存碎片化严重，逻辑型错误

__delete nullptr__ 是安全的，什么都不做。

#### 定位new： 
__可以手动控制new的位置__
eg：char a[4]; int* b = new(a)int(1); 分配对象就在栈上了
如果是简单类型（int, float, 指针）： 你完全不用管，直接让它随栈消亡即可。
如果是复杂类对象（如 std::string）： 虽然不用释放内存，但你必须手动调用析构函数，因为栈回收内存时不会自动调用 Placement New 对象的析构函数。
__用途__：实现高性能内存池


#### new A和new A （）
__如果类 A 有“用户自定义构造函数__
	在这种情况下，两者没有区别。都会调用你写的那个默认构造函数
__如果类 A 没有定义构造函数（由编译器生成默认构造）__
	new A：编译器生成的构造函数不会对类中的内置类型成员进行初始化，它们将是随机值。\nnew A()：编译器会先对整个对象的内存进行“清零”处理（值初始化），然后再调用生成的构造函数。这意味着类中的内置类型成员会被初始化为 0。
#### sizeddelete：
跳过 Header 访问：内存管理器收到 ptr 和 size 后，可以直接根据 size 定位到对应的分级块（Bin/Bucket），省去了读取 Header 的那次昂贵的内存操作。\n硬件加速：对于像 tcmalloc 这样基于大小分类的分配器，这种“直接投递”的速度提升非常显著
编译器会自动把 sizeof(FastBullet) 传给 size 参数 void operator delete(void* ptr, std::size_t size)

#### new[]，delete[]
实际上就是将new重复多少次，也可以定位new

__析构时的区别：__
对于没有重写析构的对象（像 int、float、char 这样的基础类型，或者只有基础类型成员的纯数据结构体，它们内部没有额外管辖任何外部资源。它们仅仅是存放在内存中的一堆二进制数据，不用逐个去调用析构，直接把地址空间释放就好

__对于复杂类型__:

A* ptr = new A[10];
(1)A 对象除了 10 * sizeof(A) 之外，因为 A 有自定义析构函数，编译器必须多申请一块内存（通常是 4 或 8 字节，即 sizeof(size_t)）来存放元素个数（定位new[]就不会了，因为需要手动调用所有的析构函数）
(2)调用 operator new[](size_t)，底层通常是 malloc，编译器在分配好的内存的最起始位置（0x1000），写入数组的元素个数，也就是 10
(3)编译器将指针向后偏移 Cookie 的大小，来到 0x1008（假设 64 位系统，Cookie 占 8 字节）。然后从 0x1008 开始，依次调用 10 次 A 的默认构造函数，初始化这 10 个对象。
(4)最后返回的指针前有cookie，在header后，指针前
delete[] ptr;
(1)向前寻址，读取 Cookie，逆序调用析构函数：编译器知道有 10 个对象，于是从第 10 个对象开始，倒序（ptr[9] 到 ptr[0]）依次调用 10 次 A 的析构函数
(2)还原真实首地址并释放：编译器将指针 ptr 减去 Cookie 的大小算出了当初 malloc 分配的首地址。调用 operator delete[](void*)（底层是 free，将整块内存完好无损地还给操作系统
cookie：8B，无符号整数类型，专门用来表示：对象大小内存块大小数组下标 / 容器长度
#### 零页与写时复制：
__零页__：
	零页是物理内存中一个特殊的、内容全为 0 的共享页。当申请大块内存（如 .bss 段或 calloc）但还没写时，OS 会把所有的虚拟页都指向这个唯一的零页。无论你申请 10GB 还是 100GB，在没写之前，它们在物理上并不存在，当真正写入时，写时复制 机制，分配真实的物理页。
__写时复制__：
	OS 会把这块内存对应的页表项全部设为 只读（Read-Only）。任何一方尝试修改数据时，CPU 发现该页是“只读”的，立刻抛出异常。内核接管异常，发现这其实是一个 COW 页面，内核申请一块新的物理页，把数据拷过去，然后把发起写入操作的那个进程的页表指向新页面，并设为 读写（Read-Write）。程序甚至不知道发生了这一切，继续执行写入。

#### 内存中的内容和编译文件之间的关联：
计算机内存结构为：cpu-cache-内存-外存，其中，内存外存存储主要数据，cache里面是数据的拷贝，而大部分情况下，内存会映射外存的内容，比如cpp编译后的代码、全局静态变量（未初始化的数据不占或占一点，记录需要几个字节的0）、常量数据段。但对于堆等动态分配写入的，并不会有外存存储，当第一次写入，直接在内存中分配页，释放也直接释放，不会存储到外存。当然，静态变量修改也不会修改外存中的内容，不然每次点击.exe都会变，修改了只修改内存中的副本。修改过的页就变成了 “匿名页”它和磁盘上那个 .exe 文件彻底断绝了母子关系


# 常见问题：
### 物理内存和虚拟内存大小？
虚拟内存的总范围一般比物理内存大，很多页不需要分配物理页。

### 内存的数据一定是外存上的备份吗？
不一定，对于动态存储的部分，直接在内存中分配页，也不会写回外存。
### extern作用在哪里？inline、define作用在哪里？
extern作用域编译的符号表生成阶段，会去外部寻找这个变量。inline也是编译阶段，会有类型检查。define是预处理阶段，单纯文本替换。
### inline的类型检查
编译器会把 inline 函数当作一个完完全全的普通函数来对待。它会严格检查：传入的实参类型是否和形参匹配？返回值类型是否正确？对象的作用域和访问权限（public/private）是否合法？只有当类型检查百分之百通过，没有任何语法和语义错误时，才会进入下一步。
define替换后也会语义检查，但二者区别在：
#define SQUARE(x) ((x) * (x))
inline int SquareInline(int x) { return x * x; }
传入i++，第一个会被加两次，第二个只一次。
