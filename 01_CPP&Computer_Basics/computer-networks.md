# 计算机网络

网络通信不是一个模块一次完成的，而是分成七层，每一层只解决一种问题，并给上一层提供服务
在浏览器中发一句信息，需要经过一系列的流程，到另一台电脑上，对面再拆开。这个流程就是网络协议。

## 网络结构：

为什么要分层：假设不分层，写一个聊天软件时，你需要同时考虑应用消息格式，字符编码。连接管理......把整个过程分为七层，就是协议。
真正工作时，上层数据不断往下封装；接收时再不断往上拆解。

#### 传输层  找到目标程序

QQ 服务器那台电脑上不只有一个程序，可能同时运行，数据到达这台机器后，还需要知道：应该把数据交给哪个程序？这时就需要 端口号。

```
TCP链接通常由四元组唯一确定：
源 IP
源端口
目标 IP
目标端口
中间的路由器通常只负责根据 IP 转发数据包，并不参与这条 TCP 连接的可靠性管理。

TCP 仍然需要：IP + 端口
因为：
IP 找到目标主机，端口找到目标主机里的进程，只有端口不够。
例如两台不同服务器都可以监听 8000 端口：
服务器A：10.0.0.1 : 8000
服务器B：10.0.0.2 : 8000
它们是完全不同的 TCP 端点。
因此 TCP 连接不是：52000 → 8000
而是：
192.168.1.5:52000
        ↕
203.0.113.10:8000
端口只是一个数字；IP + 端口 才叫通信端点，也常叫 Socket 地址
```

TCP 头里没有 IP 地址，但他把报文段搞好后，交给ip会告诉ip层：这个 TCP 段要发往 203.0.113.10，ip再增加ip头。
客户端只需要认识服务器；服务器认识所有当前连接的客户端。A 发消息时只写“发给 B”，服务器负责找到 B 的连接并转发。

```
通过DNS协议，查到ip地址
启动时，通过服务器下发给服务器的ip地址
```

#### 网络层：网络层关心的是Q 服务器在哪台机器上？这个数据包应该经过哪些路由器？下一跳应该交给谁？  主要使用的是 IP 地址

```
网络层一般不负责可靠性,IP 网络层主要是：尽力把数据送到目标主机。
它更关心的是：
目标 IP 是什么下一跳往哪里走数据包还能经过多少个路由器
所以二者分工是：
网络层：负责走路、找机器
传输层：负责找进程，并按需要提供可靠性
```

```
应用数据
→ TCP 添加 TCP 头
→ IP 层根据 Socket 中保存的目标地址添加 IP 头
→ 路由发现目标属于本机
→ 通过回环路径交给服务器
```

#### 数据链路层：在当前这段局域网或当前这条链路中，把数据交给下一台设备

网络层只是知道，下一步跳到哪个ip，但真正决定跳的，是数据链路层。

```
假设路径是：
你的电脑
→ 家庭路由器
→ 运营商路由器
→ 其他路由器
→ 服务器
第一跳时，以太网帧可能是：
源 MAC：你电脑网卡的 MAC
目标 MAC：家庭路由器的 MAC
家庭路由器收到后，会去掉旧的链路层帧，查看里面的目标 IP，然后重新包装一个新帧：
源 MAC：家庭路由器出口网卡的 MAC
目标 MAC：下一个路由器的 MAC
到了下一台路由器，又重新包装。
所以通常：
IP 地址描述端到端目标，经过路由时一般保持不变
MAC 地址描述当前一跳，每经过一跳都会重新生成
```

##### 交换机:

```
它会维护一张 MAC 地址表：
MAC 地址 A → 端口 1
MAC 地址 B → 端口 3
MAC 地址 C → 端口 5
当交换机收到一个帧时，它看目标 MAC：
目标 MAC 在端口 3
就只从端口 3 发出去。
所以：
交换机根据 MAC 转发帧
路由器根据 IP 转发包
这是最常见的区别。
```

### TCP：全双工协议，可双向发送。

一个 IP 的同一个端口，可以同时存在很多条 TCP 连接
TCP 连接由四元组唯一确定：
源 IP + 源端口 + 目的 IP + 目的端口

```
客户端A 10.0.0.2:50001 → 服务器 10.0.0.1:8080
客户端B 10.0.0.3:50001 → 服务器 10.0.0.1:8080
客户端A 10.0.0.2:50002 → 服务器 10.0.0.1:8080
```

不过，完全相同的四元组不能同时存在两条 TCP 连接：

```
10.0.0.2:50001 → 10.0.0.1:8080
10.0.0.2:50001 → 10.0.0.1:8080
```

因为 TCP 连接并不是只靠“IP + 端口”区分，而是通过一个四元组区分：
(源 IP,源端口,目的 IP,目的端口)

#### 为什么是三次握手，不是两次

双方都需要确认自己的发送能力和接收能力正常，并确认对方知道这一点
如果是两次，有游离的请求包，B收到发给A，但其实A并没有请求，就会导致B以为自己在连接，而A并不在，造成状态错乱。

##### TIME_WAIT：主动关闭连接的一方，发送最后一个 ACK 后不会立即释放连接，而是进入 TIME_WAIT，等2MSL

保证最后一个 ACK 能够重传：如果客户端最后发送的 ACK 丢失，服务端会重新发送 FIN。客户端处于 TIME_WAIT 时，还能再次回复 ACK。如果客户端立即关闭，服务端重发 FIN 时就没人处理了。
防止旧连接的数据污染新连接：网络中可能还存在旧连接延迟到达的数据包。等待一段时间后，可以确保这些旧数据包从网络中消失，避免它们被误认为属于一个新的同四元组连接。

##### 为什么不是三次：

中间需要拆开，因为服务器会有没发完的数据包，不能在收到客户端的关闭后自己立刻也关闭。

#### 队头堵塞：

```
TCP 必须按序向应用层交付数据。
假设发送：
数据包 1
数据包 2
数据包 3
数据包 2 丢失，但数据包 3 已经到达。
TCP 不能直接把数据包 3 对应的后续字节交给应用层，因为中间缺了一段。它必须等待数据包 2 重传成功：
收到 1
收到 3
等待 2
收到重传的 2
按照 1、2、3 交付
这就是 TCP 层面的队头阻塞。
对于文件传输，这是正确行为，因为文件不能缺字节。
对于实时游戏状态，旧数据的重传可能增加延迟
```

### UDP：

UDP 发送数据前不需要建立连接，启动开销更小，是报文协议，UDP 保留消息边界

```
DP 保留消息边界，客户端发送两次：
sendto(sock, "abc", 3, ...);
sendto(sock, "def", 3, ...);
接收方会收到两个独立 UDP 数据报：
abc
def
不会像 TCP 一样自动合并成一个字节流。
但是接收缓冲区太小会产生截断。
例如发送方发送一个 1000 字节 UDP 报文，接收方只提供 500 字节缓冲区，那么剩余部分不会像 TCP 一样留给下一次读取，通常会被截断丢弃。
所以 UDP 应用层需要给每个报文准备足够大的接收缓冲区。
```

```
让 TCP 专注于可靠地传送字节，并灵活安排传输；“一条业务消息到哪里结束”由应用协议规定，这样文本、文件、音视频等都能使用同一种传输服务。
```

#### UDP 为什么快

UDP 协议机制更简单，延迟和额外开销更低，应用程序可以直接发送数据。
但是 UDP 不一定永远比 TCP 吞吐量高。
如果网络丢包严重，而应用又必须可靠传输，那么你在 UDP 上自己实现重传、确认、排序和拥塞控制，复杂度可能并不比 TCP 低。UDP 的优势主要在于：
应用可以根据自己的需求决定哪些数据值得重传，哪些数据过期后直接丢弃

#### 不保证：

不保证送达，不保证顺序，不保证不重复，不保证流量控制，不保证拥塞控制

#### UDP分片：

UDP 一个数据报如果过大，可能超过链路 MTU，IP 层可能进行分片。例如一个 UDP 报文被分成多个 IP 分片，只要其中一个分片丢失，整个 UDP 数据报通常就无法完成重组。所以实时网络程序一般会主动控制 UDP 包大小，尽量避免 IP 分片

#### 为什么实时游戏常用UDP：

实时游戏更关心：
最新状态能否尽快到达。而不是：每一个历史状态是否都必须到达。
例如玩家位置：
第 100 帧：位置 A
第 101 帧：位置 B
第 102 帧：位置 C
如果第 100 帧的数据丢了，但第 102 帧已经到了，再去重传第 100 帧的位置意义不大，因为它已经过期。
TCP 丢包时，为了保证有序，会等待丢失的数据补齐后再向应用层交付后续数据。这种现象经常被称为队头阻塞。
而 UDP 可以：
旧位置丢了就丢了
直接处理最新位置
所以适合：角色位置。朝向。速度。动画状态。瞄准方向。实时语音。视频帧。
但是游戏中并不是所有数据都可以丢。例如：
登录。购买物品。任务奖励。聊天消息。创建角色。伤害结算。关键技能事件。
这些内容需要可靠性。

### KCP：

是运行在应用层的，但实际上实现的传输层的功能。

#### 原因：

KCP数据封装在UDP Payload里，操作系统、路由器只认识UDP，因此KCP属于应用层协议。从功能看，KCP实现了序号、ACK、滑动窗口、重传、流量控制、分片重组和有序交付，这些都是典型传输层能力，所以也常被称为基于UDP的可靠传输协议

#### KCP提供：

```
KCP 通常提供：
可靠传输；默认按序交付；消息分片与重组；发送/接收窗口；ACK 与累计确认；RTT/RTO 估计；超时重传；快速重传；拥塞控制及可配置策略。
KCP 不提供：UDP Socket 创建与收发；握手和连接状态机；身份认证；加密、完整性认证和防重放；NAT 保活；地址迁移；路径 MTU 探测；业务超时和断线重连；线程安全封装。
```

#### 内部的四组核心队列：

发送侧：snd_queue → snd_buf → ACK 后释放
接收侧：rcv_buf   → rcv_queue → ikcp_recv
snd_queue：应用已经提交、尚未进入发送窗口的数据；
snd_buf：已经发送、等待确认或重传的数据；
rcv_buf：已收到但前面仍有缺口的乱序数据；
rcv_queue：已经连续、可以交给应用的数据。

#### 游戏为什么会同时使用三种协议？

因为不同消息的可靠性、顺序和过期语义不同。登录/下载适合 TCP，关键实时消息可能适合 KCP，高频可覆盖快照适合 UDP。

#### KCP 与 TCP 的核心差异是什么？

两者都能提供可靠有序交付。TCP 是标准、成熟、主要由内核实现的字节流；KCP 是通常基于 UDP 的用户态 ARQ 组件，消息模式和恢复策略更可调，但外围工程责任更大。

### 选择方式：

消息丢了必须补吗？
旧消息是否仍有价值？
是否必须与其他消息全局有序？
最大可接受延迟和带宽预算是多少？
团队是否有能力维护安全、拥塞、弱网和跨平台协议栈

#### 什么时候UDP，什么时候TCP,KCP：

能替代，就适合UDP

```
   角色位置、朝向      下一帧位置比旧位置更有价值
  ──────────────────  ────────────────────────────────
   瞄准方向            持续发送，丢一次影响很小
  ──────────────────  ────────────────────────────────
   速度、载具姿态      后续状态可以覆盖
  ──────────────────  ────────────────────────────────
   动画状态            通常会周期性刷新
  ──────────────────  ────────────────────────────────
   摄像机或观战位置    晚到的旧位置没有意义
  ──────────────────  ────────────────────────────────
   语音帧              过时语音重传回来也没价值
  ──────────────────  ────────────────────────────────
   实时输入            有时会连续发送或携带前几帧冗余

实际工程通常还会给UDP消息增加序号：
  位置序号 101：收到
  位置序号 103：收到
  位置序号 102：晚到
由于102比103旧，直接丢弃102。这叫“不可靠有序”或“Unreliable Sequenced”：允许丢包，但不允许旧状态覆盖新状态。
```

对于速度不敏感，直接TCP：如商城，购买，账号登录等。

对于速度敏感，但还要求数据准确：实时战斗中的关键RPC，需要可靠到达，但又希望弱网恢复更快的数据

### RPC：一般靠着TCP实现

我在本地调用一个函数，但这个函数真正的执行位置是在另一台机器或另一个进程上

```
例如客户端执行：
ServerUseSkill(1001);
看起来像普通函数调用，但实际上过程是：
客户端调用 ServerUseSkill
        ↓
序列化函数名和参数
        ↓
通过网络发送给服务器
        ↓
服务器收到并反序列化
        ↓
服务器执行 ServerUseSkill_Implementation
所以 RPC 并不是普通的本地函数跳转，而是：
调用函数
→ 转换成网络消息
→ 发给远端
→ 远端执行对应函数
在 UE 中，RPC 可以指定在服务器、拥有该 Actor 的客户端，或者所有相关机器上执行。
```

#### UE中的RPC：

##### Server RPC：客户端请求，最终是否允许执行，通常应该由服务器判断

```
客户端请求移动；
客户端请求释放技能；
客户端请求购买道具；
客户端提交交互行为。
```

##### Client RPC 服务器调用，指定客户端执行

```
某个玩家弹出提示；
通知登录失败；
返回个人操作结果；
播放只属于该玩家的界面效果。
Client RPC 通常发送给拥有该 Actor 的客户端，而不是所有客户端。
```

##### NetMulticast RPC 服务器调用，在服务器和相关客户端上执行

```
服务器调用
   ├→ 服务器执行
   ├→ 客户端 A 执行
   ├→ 客户端 B 执行
   └→ 客户端 C 执行
适合：
播放爆炸特效；
播放音效；
临时动画；
一次性表现事件。
UE 官方也把“某个位置发生爆炸”作为适合 RPC 的典型事件：事件发生时调用一次，而不是长期维护一个状态变量。
```
