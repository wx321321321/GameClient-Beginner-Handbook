# 操作系统

操作系统负责协调程序与硬件：给运行中的程序分配资源，控制谁能访问资源，并提供文件、进程、网络等接口。本篇先理清内核与系统调用，再沿着“一次文件读取”理解文件的逻辑组织、磁盘分配、共享和空闲空间管理。进程调度见[进程、线程与同步](processes-threads-and-synchronization.md)，虚拟内存见[内存模型与编译管线](memory-and-compilation.md)。

## 1. 操作系统管理什么

主要职责可以分成五类：进程与线程管理、内存管理、设备与 I/O 管理、文件管理，以及供应用和使用者调用的接口。网络协议栈也通常有重要部分由内核实现。

教材中的四个特征，可以这样联系实际：

| 特征 | 含义 |
| --- | --- |
| 并发 | 多个活动在一段时间内交错推进；多核还可真正并行 |
| 共享 | 多个活动按规则使用 CPU、内存、文件和设备等资源 |
| 虚拟 | 把有限物理资源抽象成更易使用的逻辑资源，例如虚拟地址空间和分时 CPU |
| 异步 | 各活动的推进速度受调度、I/O 等影响，不能假定每次运行都有相同时间顺序 |

### 内核、用户态与内核态

内核是操作系统中负责核心资源管理的部分，通常运行在高权限模式。应用一般运行在用户态，不能随意修改页表、执行特权 I/O、改变中断控制或读取其他进程的受保护内存。具体权限级与指令限制由 CPU 和操作系统共同决定，并不只是软件约定。

内核态拥有更高权限，也不是每条内核指令都可以不受任何映射、访问检查和虚拟化规则限制。隔离通常能把应用崩溃限制在其进程内，但共享资源损坏、资源耗尽或内核故障仍可能影响其他程序。

### 系统调用怎样进入内核

应用需要内核服务时，通过系统调用接口请求，例如打开文件、读写数据、建立进程或映射内存。普通库函数与系统调用要区分：库可能先在用户态完成缓冲或检查，只有必要部分才进入内核。

```text
用户代码调用库/API
        ↓
系统调用入口，按架构机制进入内核态
        ↓
内核检查参数、权限和对象状态，执行服务
        ↓
返回结果或错误，继续用户态执行
```

进入内核态不等于一定切换到另一个进程，也不代表每次使用资源都要调用内核；例如读取已经映射且可访问的内存，通常直接由硬件执行。

### 启动时内核从哪里来

固件通常保存在主板的非易失存储中，常见为 Flash；传统系统称 BIOS，现代系统常用 UEFI。开机后固件完成必要初始化并进入引导流程，引导程序把内核及启动所需内容装入内存，内核再初始化设备、内存与调度等子系统。

操作系统的文件通常保存在存储设备上，运行所需部分驻留或按需装入内存。不能把固件描述成普通 RAM 中已经运行着的内核。

## 2. 从一次文件读取理解文件系统

文件通常向程序呈现字节序列及相关元数据。程序内部可以把这些字节解释为记录、图片或日志；文件系统则负责命名、权限、存储分配与读写。

### 文件偏移怎样变成存储位置

```text
应用按关键字找到记录
        ↓
得到记录在文件中的字节偏移
        ↓
确定涉及哪些文件逻辑块
        ↓
文件系统查找块/extent 映射
        ↓
获得存储设备上的对应位置
```

“按关键字找记录”常由应用、数据库或特定记录式文件系统完成，普通文件系统不会自动理解学号等业务字段。文件系统块通常是固定大小的管理单位，4 KiB 很常见，但不是固定标准；它与设备扇区、虚拟内存页以及某次 `read` 请求的长度不必相同。

### open、read、close 各做一步

以下以 Unix/Linux 常规文件为例：

1. `open/openat` 进入内核，解析路径，查找目录项和文件，检查打开方式及权限，建立打开文件描述等内核状态，在进程文件描述符表中分配一个 fd 返回。缓存可能避免实际读盘。
2. `read(fd, buf, n)` 根据 fd 找到打开的文件及当前位置，通常从 Page Cache 取得内容；缺失时发起 I/O，返回实际读到的字节数并更新相应文件偏移。返回值可能小于 n，0 通常表示文件结束，错误需单独处理。
3. `close(fd)` 关闭这个描述符并释放其引用。同一个打开文件描述还可能被其他 fd/进程引用，所以关闭一个 fd 不一定销毁全部相关状态。

Page Cache 位于 RAM，CPU Cache 则是硬件缓存，不能混称。普通 `close` 也不保证之前所有写入已经持久落盘，持久化要看相应同步 API 和存储语义。接口定义可查 [Linux open(2)](https://man7.org/linux/man-pages/man2/open.2.html)；缓存路径见 [Linux Page Cache 文档](https://www.kernel.org/doc/html/latest/mm/page_cache.html)。

## 3. 文件的逻辑结构：记录怎么组织

这一节讨论**文件内容的记录组织**，下一节讨论**这些字节分配到哪些磁盘块**，两层可以独立选择。

### 顺序文件

记录按顺序排列。定长记录可用“记录序号 × 记录长度”直接计算偏移，较容易随机定位；变长记录若没有额外索引，通常需要扫描或借助分隔/长度字段。

适合批量处理、日志、按时间或编号遍历，以及经常读取全部记录的场景。“顺序组织”不代表绝对无法随机读取，关键看是否能快速算出位置。

### 索引文件

额外建立“关键字 → 记录位置”的索引，换取更快的查询：

```text
学号       记录位置
1001  →    A
1002  →    B
1003  →    C

查 1003：在索引中找到 1003 → 得到位置 C → 读取对应记录。
```

代价是索引占空间，插入、删除和修改时也要维护一致性；查询效率还取决于索引采用顺序表、树还是其他结构。

### 索引顺序文件

将有序记录分组，为各组建立较稀疏的索引：

```text
数据块 1：1000～1099
数据块 2：1100～1199
数据块 3：1200～1299

索引：
1000 → 数据块 1
1100 → 数据块 2
1200 → 数据块 3
```

先通过有序索引缩小到一组，再在组内定位记录，兼顾顺序处理与按键查找。教材可用顺序查找演示，但索引本身不必只能顺序查；有序结构可采用二分或多级索引。

## 4. 文件的物理结构：逻辑块放在哪里

### 连续分配

为文件分配连续的一段磁盘块，通过“起始块 + 逻辑块偏移”快速定位，顺序访问也较高效。问题是增长不方便，并可能产生外部碎片：总空闲容量够，仍找不到足够长的连续区间。extent 方式把连续区段作为单位，可以减轻“一整个文件必须完全连续”的限制。

### 链接分配：块内指针与 FAT

隐式链接把下一块的地址放在当前块里，目录/文件元数据记录起点等信息。文件块不必连续，增长方便，但定位后面的块通常要沿链读取，随机访问较差，指针损坏还可能使后续链丢失。

显式链接把链接关系集中存进 FAT（文件分配表）。FAT 可被缓存到内存，沿链不必每次都读取数据块尾部，但算法上查找第 n 个块仍可能走 n 次链接。它改善的是链接信息的组织与访问成本，并没有自动变成直接索引。

### 索引分配与多级索引

为每个文件保存逻辑块到物理块的索引：

```text
文件逻辑块 0 → 物理块 80
文件逻辑块 1 → 物理块 12
文件逻辑块 2 → 物理块 37
```

查逻辑块 1 时，索引直接给出物理块 12，不必先经过块 0。它支持随机访问，文件块不必连续，扩展比单段连续分配方便；一个数据块损坏通常不会像链指针断裂一样截断后续定位。不过索引本身占空间，大文件需要较多地址，小文件可能用不满一个索引块。

多级索引在一层放不下时，让上层索引指向下层索引块，叶层再定位数据；代价是额外层次访问，可通过缓存缓解。索引块损坏仍可能影响大量文件数据。

## 5. 权限与共享：名字和文件本体分开看

### 访问控制

文件权限说明某个主体能否读、写、执行等。简单权限位可按所有者、组和其他用户表示；ACL 则可为具体用户或组记录权限。访问矩阵可用位表达某项权限，但实际 ACL 不只是“每个用户占一位”，还需要身份和权限集合等信息。

口令保护、加密也可以保护文件，但目的不同：口令用于证明身份/授权，访问控制用于决定允许的操作，加密用于让没有密钥的人难以读懂内容。“密码和口令”本身并不是两种独立的文件分配机制。

### 目录项与 inode

在典型 Unix/Linux 文件系统中：

```text
目录项：文件名 → inode 编号

inode：
├── 文件类型、权限、所有者
├── 文件大小、时间信息
├── 硬链接计数
└── 数据块/extent 等定位信息
```

文件名主要属于目录项，inode 保存文件元数据与数据定位信息。具体文件系统可以有不同布局，某些小数据也可内联存储，不能把每个 inode 都想成相同大小的块地址数组。

### 硬链接：增加一个指向同一文件的名字

两个目录项指向同一文件系统中的同一 inode，就拥有了两个硬链接名字。修改任一名字打开的文件，修改的是同一个文件本体。

删除一个名字会减少硬链接计数。没有链接且没有打开文件等其他存活引用时，文件系统才能真正回收其资源。因此程序仍打开文件时，删除路径不一定让已打开的读取立刻失败。[Linux unlink(2)](https://man7.org/linux/man-pages/man2/unlink.2.html)描述了这一区别。

硬链接通常不能跨文件系统，因为 inode 编号只在所属文件系统内有意义：文件系统 1 的 inode 100 不等于文件系统 2 的 inode 100。普通用户通常也不能任意给目录建立硬链接，以避免目录环等问题。

### 符号链接：保存另一条路径

符号链接是一个特殊文件，内容表示目标路径，访问时再解析该路径。它可以跨文件系统，也可以指向暂时不存在的目标，因此目标移动或删除后可能成为悬空链接。

```text
/tmp/b.txt
    ↓
inode 200，类型为符号链接
    ↓
保存路径字符串 "/home/a.txt"
    ↓ 重新解析
/home/a.txt → inode 100，普通文件 → 文件数据
```

路径字符串可能放在 inode 内，也可能占用数据块，不必每次单独读盘。符号链接增加路径解析工作，但命中缓存时不一定产生多次磁盘 I/O，不能固定断言一定比硬链接慢多少。

## 6. 文件系统怎样管理空闲块

这里的“空闲表/链表”管理的是文件系统可用空间，不是磁盘分区表，也不是进程堆分配器；它们只是可以使用相似的数据结构。

### 空闲表法：记录连续空闲区间

每项记录起始块和连续块数，分配时切分，释放时尝试合并相邻区间。

![空闲空间表](assets/free-space-table.png)

连续空闲区较多时，表较小，也容易一次取得多个连续块，适合与 extent 思路配合。碎片严重时表项增多，查找可能需要遍历；释放后还要维护相邻区合并。

### 空闲链表法：把块或区间串起来

可以逐个链接空闲块，也可以链接连续空闲区间。单块链表的指针可存在空闲块自身，分配、释放单块方便，不必预留一张覆盖整个磁盘的大表。

![空闲空间链表](assets/free-space-linked-list.png)

缺点是批量寻找空闲块可能沿很长的链走，多次访问存储；寻找一大段连续空间不方便，链指针损坏还可能丢失后续空闲空间的管理信息。

### 位示图法：每块用一个 bit

给每个块分配一个位表示是否空闲，0/1 的含义由实现约定。例如约定 1 为空闲、0 为已用。**一个块对应一个 bit，不是一个 byte。** 位图逻辑上像表格，实际保存在文件系统的元数据块中。

![空闲空间位示图](assets/free-space-bitmap.png)

优点是紧凑，可用位运算扫描、统计数量，支持随机检查一个块状态，也较容易寻找连续空闲位。位图大小与总块数成正比；盘快满时搜索可能较长，大文件系统未必能把全部位图一直留在 RAM。分配/释放时必须保证位图与其他元数据一致。

### 成组链接法：一批一批保存空闲块号

把若干空闲块号组成一组，内存中保留当前组的空闲栈；组中的某个条目连接下一组所在的块，链接块还记录相应数量等信息，具体布局依实现而定。

![空闲空间成组链接](assets/free-space-grouped-links.png)

大多数分配/释放只操作内存中的当前组，组耗尽或装满时才读取/写回链接块，减少逐块追链。它不需要覆盖全盘的独立大表，但实现比普通链表复杂，不擅长寻找大批连续块；链接块损坏可能影响后续组。现代文件系统可能采用位图、extent 树等更适合其目标的结构，成组链接主要用于理解经典空闲空间管理。
