# Lua：语言规则、游戏脚本与运行时

游戏里使用 Lua，主要是为了让 UI、活动、引导和时序逻辑更易迭代。理解它时，先把语言语义、虚拟机实现和项目的脚本框架分开：元表、协程是语言能力，完整的热更新流程则需要项目自己设计。

本文涉及 `_ENV`、整数子类型、GC 模式等内容时以官方 Lua 5.4 为主要参照。Lua 5.1、LuaJIT 和项目定制版本可能不同，不能混用其行为。

## 1. 脚本如何执行，为什么适合游戏业务

在标准 Lua 实现中，一段源代码块（chunk）会先被编译成字节码，再由虚拟机执行。虚拟机解释字节码，不等于每运行到一行源代码就重新编译一行；LuaJIT 等实现还可能采用即时编译。

原笔记关注的三个优势分别对应：

- **table 与元表**：用少量语言机制组织列表、状态、对象和默认行为。
- **协程**：将等待动画、回包、剧情阶段等流程写成较线性的代码。
- **可替换的脚本逻辑**：降低部分业务修复的发版成本，但是否能安全热更取决于状态与引用管理。

性能密集部分常放在 C++，业务编排放在 Lua；不能只凭“脚本语言”就断言某个模块一定慢，实际还要看算法、跨语言调用、分配频率和具体运行时。

## 2. 基础语义：值、table 和遍历

### 2.1 八种类型与真假值

Lua 的八种基本类型是 `nil`、`boolean`、`number`、`string`、`function`、`table`、`userdata`、`thread`。变量不固定绑定一种类型，值带有类型；“动态类型”不应简单理解为不用检查类型。

只有 `nil` 和 `false` 为假，**0 和空字符串都为真**。例如卡槽 ID 从 0 开始：

```lua
local slotId = 0
if slotId then
    -- 会进入这里；这只能说明 slotId 不是 nil/false。
end

if slotId ~= nil then
    -- 如果 nil 才表示“没有卡槽”，应明确按这个约定判断。
end
```

赋值时，数字、布尔值等按值理解；字符串不可变，也按值使用。table、函数闭包、完整 userdata、协程对象的赋值不会深拷贝对象：多个变量可以指向同一个对象。light userdata 则是 C 指针值，不能与由 GC 管理内存的完整 userdata 混为一谈。

字符串是字节序列，不自动假定某种文字编码。Lua 5.4 的 `number` 包含整数和浮点子类型；这与不少 Lua 5.1/LuaJIT 项目的数值模型不同。参见 [Lua 5.4：值与类型](https://www.lua.org/manual/5.4/manual.html#2.1)。

### 2.2 table 同时承担列表和状态对象

table 是关联容器，既可以按整数索引访问，也可以用字符串等键访问。官方实现会结合数组部分与哈希部分存储；这是实现策略，不是业务代码应该依赖的物理布局。

在换色模块里，可以这样区分数据用途：

| 数据 | 合适的表达 |
| --- | --- |
| 颜色列表、卡槽列表 | 连续整数索引的列表，便于按顺序渲染 |
| 单个卡槽属性 | 颜色、解锁状态、是否装备、资源引用等键值字段 |
| 页面/模块状态 | 当前车辆、当前卡槽、显示状态、服务端数据快照 |

“数组从 1 开始”是 Lua 序列及常用库的约定，**不是 table 禁止键 0**。同样，给字段赋 `nil` 等于移除这个键；`false` 则仍是一条存在的键值记录。

### 2.3 pairs 与 ipairs 的区别

| 遍历方式 | 语义 | 容易踩的点 |
| --- | --- | --- |
| `ipairs(t)` | 按 1、2、3……访问整数索引，遇到首个 `nil` 停止 | 有洞的列表可能提前结束；不要用它遍历所有键 |
| `pairs(t)` | 默认通过 `next` 遍历键值对；Lua 5.4 也会考虑 `__pairs` | 顺序未规定，数字键也不能假定有序 |
| 数值 `for` | 自己指定索引范围 | 适合业务有明确范围，且需要自行处理缺失项的情况 |

不能把 `ipairs` 解释为“只访问 table 物理数组区”：它的规则基于整数键访问，而不是让程序直接检查内部存储分区。渲染列表需要稳定顺序时，应明确使用序列或排序后的键列表。

## 3. 变量作用域、环境表和闭包

### 3.1 local 与全局访问

`local` 声明词法局部变量。没有命中可见局部变量的普通名称，在 Lua 5.2+ 中通过 `_ENV` 对应环境访问。默认环境通常是全局环境，而 `_G` 是指向全局环境表的一个变量；把 `_G` 重新赋值不等于自动改变所有代码的 `_ENV`。

原笔记的“全局表”和“环境表”应放在一起理解：

- **全局环境表**：默认保存全局名称；常见宿主初始化时还会打开标准库。
- **`_ENV`**：当前代码访问自由名称时使用的环境引用，可以指向不同的表。
- **局部变量**：按词法作用域解析，通常避免全局表查找；被闭包捕获时可能作为 upvalue 存活。

所以，“local 都存在栈上，离开代码块立即销毁”不准确。词法可见性结束，不代表被捕获的值或其引用对象立刻消失。

在换色模块中，刷新中间结果、临时颜色项和函数内回调优先用 local；当前车辆、卡槽等共享状态放在模块的状态表或 Model 中。这样既明确所有者，也减少同名全局变量相互覆盖。

### 3.2 闭包保留的是外层变量的访问关系

闭包由函数和它捕获的外部局部变量组成。外层函数返回后，被闭包引用的变量仍可存活，通常称为 upvalue。table 等引用对象也会因这些引用而继续可达。

游戏 UI 中常见用途：

- 按钮点击时获得页面对象、选中槽位。
- 为颜色项或卡槽项绑定自己的 ID。
- 网络请求发出后，在回调里保留请求时的操作对象或上下文。

原记录中出现过“十个卡槽最终都指向第十个”的问题。这个现象应检查是否捕获了**同一个持续变化的外层变量**，不能直接归因于“Lua 的数值 for 总会捕获最后一个 i”。下面是共享变量导致问题的例子：

```lua
local callbacks = {}
local currentSlot
for i = 1, 10 do
    currentSlot = i
    callbacks[i] = function()
        return currentSlot
    end
end
assert(callbacks[1]() == 10)
```

如果业务希望保存创建回调时的卡槽，应捕获每次绑定独立的局部值：

```lua
local callbacks = {}
for i = 1, 10 do
    local slotId = i
    callbacks[i] = function()
        return slotId
    end
end
assert(callbacks[1]() == 1)
assert(callbacks[10]() == 10)
```

标准 Lua 的 for 控制变量本就具有局部作用域，第二段显式起名主要是让“绑定哪一个业务值”更清楚。异步回包还要区分“请求发出时的状态”和“回包时页面当前状态”，两者不一定应该相同。作用域和循环规则参见 [Lua 5.4：for](https://www.lua.org/manual/5.4/manual.html#3.3.5)。

### 3.3 点号与冒号：是否自动传 self

```lua
obj:Refresh(a)       -- 等价于 obj.Refresh(obj, a)
obj.Refresh(a)       -- 不自动传 obj
```

用 `:` 定义成员方法时，会隐含一个 `self` 参数。Mediator、View 的方法定义和调用应保持一致；错误地用 `.` 调用会让参数错位。

把方法作为按钮回调传出时，也不会凭空保留接收者。可以用闭包明确调用 `view:Refresh()`，或使用项目提供的绑定工具，同时留意闭包对 view 的生命周期影响。

## 4. 元表：给数据附加行为规则

普通 table 访问不存在的字段得到 `nil`，默认不能任意相加。通过 `setmetatable` 关联元表后，Lua 可在特定操作中调用元方法。元表不是“自动填补所有不存在的字段”，而是按规则决定如何处理操作。

| 元方法 | 触发行为 | 常见用途 |
| --- | --- | --- |
| `__index` | 普通查找没有找到键 | 默认值、原型/继承链、代理读取 |
| `__newindex` | 对原表中不存在的键进行普通赋值 | 代理写入、访问控制、统一赋值流程 |
| `__add`、`__sub` | 相应运算 | 自定义数值/向量式行为 |
| `__eq`、`__lt` | 相应比较 | 自定义比较语义 |
| `__tostring` | 转字符串 | 调试输出 |
| `__call` | 把值当函数调用 | 可调用对象 |

`__index` 可以是函数，也可以指向另一张表。`__newindex` 不是所有赋值的总入口：键已存在时通常直接覆盖，`rawset` 也可绕开元方法。编写元方法时，要避免再次触发自身造成递归。

### 4.1 只读代理为什么要用一张空表

如果直接给已经填好字段的表设置 `__newindex`，已有键仍可被覆盖。常见做法是让代理表保持空，把读取转到真正的数据表：

```lua
local data = { maxSlots = 10 }
local readonly = setmetatable({}, {
    __index = data,
    __newindex = function()
        error("read-only table", 2)
    end
})

assert(readonly.maxSlots == 10)
-- readonly.maxSlots = 20  -- 普通赋值会报错
```

这能防止普通误写，但不是安全沙箱：`rawset`、真实数据表的外部引用、嵌套可变对象等仍需另行约束。Lua 的对象、继承、默认配置和状态代理常基于 table + metatable 组合，具体类框架属于项目约定。

## 5. 协程：把等待拆成可恢复的执行阶段

Lua 协程是可主动挂起和恢复的执行流，由 `yield` / `resume` 协作切换。它不是 OS 线程，不会因为创建协程就自动获得多核并行，也不会自动替引擎创建“等回包”的调度器。

| 操作 | 意义 |
| --- | --- |
| `coroutine.create(f)` | 创建处于挂起状态的协程，尚未执行 f |
| `coroutine.resume(co, ...)` | 开始执行或从上次 yield 继续，并向协程传值 |
| `coroutine.yield(...)` | 主动挂起，把值返回给 resume 的调用者 |

resume 与 yield 是双向传值的；resume 还返回是否成功，调用方应处理失败。一次 resume 之后，协程运行到下一次 yield、结束或错误，不会自动按每帧切换。

等待动画、等待回包、分帧任务、剧情流程等适合这种表达：先执行一阶段，挂起，事件或下一帧到来时再恢复。真正的“等待条件 → 恢复时机”仍由引擎/业务调度器连接起来。

## 6. Lua 虚拟机与 C++ 交互

### 6.1 lua_State 与共享运行时状态

从官方实现看，`lua_State` 对应一个 Lua 执行线程，包含自己的栈和调用信息。`lua_newthread` 创建协程线程，它有独立的执行状态，但与创建它的线程共享同一个 Lua 运行时的全局数据。

内部的 `global_State` 管理 GC、字符串管理等共享资产。这里的“全局”是**同一个独立 Lua state/运行时内部**的共享，不是一个 C++ 进程永远只能有一份；多次创建独立 Lua 状态可以得到彼此独立的运行时。

共享对象也意味着不能凭“每个协程都有自己的栈”就让多个 OS 线程不加保护地并发操作同一个 Lua 运行时。

字符串不可变与字符串驻留是两回事。官方 Lua 5.4 会区分短字符串驻留和长字符串处理，不能把“所有内容相同的字符串永远只有一份”当作语言保证，详见 [Lua 5.4 lstring.c](https://www.lua.org/source/5.4/lstring.c.html)。

### 6.2 数据栈和调用信息分别做什么

数据栈是 C API 交换参数和返回值的主要接口，每个槽位可存放 Lua 值。调用信息则跟踪函数调用层次、执行位置、局部变量/栈范围等，支持 `A() → B() → C()` 调用与返回。

| 栈索引 | 含义 |
| --- | --- |
| 正数 `1` | 当前 C API 调用视角下的第一个栈元素 |
| `lua_gettop(L)` | 当前栈顶索引，也反映此视角下的元素数 |
| 负数 `-1` | 当前栈顶 |
| 负数 `-2` | 栈顶下面的元素；压栈/弹栈会影响这种相对定位 |

### 6.3 两个调用方向

**Lua 调 C/C++**：绑定函数通常符合 `int Function(lua_State* L)` 签名。注册后，Lua 保存一个可调用的 C 函数值；调用时 C/C++ 通过 Lua 栈取参数、做类型检查，把结果压回栈，并返回结果个数。不是把任意 C++ 成员函数地址直接塞进表就完成绑定。

**C++ 调 Lua**：取得 Lua 函数，按顺序压入参数，通过 `lua_pcall` 等接口调用，再检查调用状态和读取结果。保护调用返回错误时，应处理栈上的错误信息，不能继续把它当正常返回值。

C++ 对象通常通过 userdata 或绑定层包装供 Lua 访问。包装类型、对象所有权和析构策略必须一致：Lua 的 GC 不会自动知道引擎里某个 C++ 对象是否已失效。

### 6.4 接口边界的三个检查点

1. **栈平衡**：按函数约定计算净压栈/弹栈量，清理中间值和错误对象。不能机械地要求所有 C 函数返回前栈高都等于进入时，因为返回值本来就需要留在栈上。
2. **类型验证**：读取前确认参数类型和转换结果，防止把转换失败得到的默认值误当业务值。
3. **字符串指针寿命**：`lua_tolstring` / `lua_tostring` 返回 Lua 管理的内存，不属于调用方。字符串保持在栈上时有相应有效性保证；需要跨调用长期保存时，应复制成自己的字符串或按绑定约定保活，不可保存已经失去生命周期保障的裸指针。

字符串也可能含有内部零字节，二进制内容应使用带长度接口。以上接口规则可对照 [Lua C API](https://www.lua.org/manual/5.4/manual.html#4)。

## 7. 热更新：重新加载代码与迁移运行状态

Lua 函数是一等值，可以保存在变量、table 字段或闭包引用中。若调用点每次都读取模块表里的函数字段，替换该字段就可能影响后续调用；若调用点早已保存旧函数，替换模块表不会追溯修改那个引用。

### 7.1 require 为什么不等于强制重载

```text
require("MyModule")
    → 查 package.loaded
    → 已有有效缓存：返回缓存值
    → 否则通过加载器查找并执行模块
    → 保存加载结果，再返回
```

模块缓存值不一定是 table，加载源也不一定只是磁盘上的 `.lua` 文件，还可能来自其他 searcher、C 模块或项目加载机制。简单地再次 `require`，通常只会得到缓存。

### 7.2 清掉缓存以后，旧逻辑仍可能存在

即使清掉 `package.loaded["MyModule"]` 再加载，以下对象也不会自动全部更新：

- 之前保存的旧模块表、旧函数引用。
- 已创建的页面实例及其状态。
- 闭包、按钮回调、定时器回调。
- 仍处于挂起状态、执行旧代码的协程。

所以，热更新需按对象关系决定替换方式：原位更新模块字段还是替换表，是否重建实例、重新绑定回调，旧状态是否能被新代码理解，以及何时切换才不会破坏正在进行的操作。

原笔记提到的 `LoadLibrary` / `GetProcAddress` 是本地动态库装载与符号查找的另一条路线。它不等同于 Lua 模块热更；卸载旧库时，旧函数指针、实例和 ABI 兼容性都需专门处理，不能只“换一次地址”就视作完成。

## 8. GC：回收不可达对象，而不是数引用个数

### 8.1 从对象引用理解可达性

```lua
local a = {}
local b = a
a = nil       -- b 仍引用这张表，不能因此回收
b = nil       -- 若不存在其他可达引用，才成为可回收对象
```

从运行时必须保留的根出发，沿对象引用能找到的对象需要保留。常见保留路径包括全局环境、运行栈、registry、可达闭包的 upvalue，以及可达协程所关联的执行状态。

这里的限定是“可达”：不是所有已经创建过的闭包和协程都永久成为 GC root。只在两个不可达对象之间互相引用，也不能让它们永久保活，因此 tracing GC 可以处理普通循环引用。

### 8.2 三色标记与增量工作

三色帮助记录扫描进度：白色尚未发现，灰色已发现但还没完成其引用扫描，黑色已完成扫描。扫描灰对象时，把它引用的未发现对象纳入待处理集合，完成后再把当前对象标黑。

```text
扫描一部分对象 → 暂停 GC、继续运行 Lua → 下次接着扫描
```

![Lua 垃圾回收](assets/lua-garbage-collection.png)

例如 A 引用 B、B 又引用 A：若从根能找到 A，扫描会发现 B，再看到已发现的 A，不会无限循环；若根找不到整个环，这个环仍可被回收。

增量执行减少一次完成全部工作的压力，但运行中的程序可能继续改变引用关系，GC 实现需要写屏障等机制维持标记正确性。不能只记“三种颜色”，忽略程序与 GC 交错运行的问题；完整收集或较重的 GC 工作仍可能造成明显停顿。

### 8.3 分代思路与版本差异

分代 GC 利用“很多新对象很快死亡，长期存活对象往往继续存活”的经验，将年轻对象和老对象区别处理，频繁的小收集重点处理较新的对象，必要时再扩大收集范围。

Lua 5.4 支持增量和分代两种 GC 模式。实际项目的默认模式、调节参数和停顿表现要结合 Lua 版本与分配负载判断，不应把某一种 GC 描述套到所有 Lua/LuaJIT 项目上。参见 [Lua 5.4：垃圾回收](https://www.lua.org/manual/5.4/manual.html#2.5)。

换色 UI 等长期运行模块需要重点检查的不是“GC 有没有执行”，而是旧页面、定时器、回调或全局状态是否仍然保留不再需要的对象；对象仍可达时，执行 GC 也不会替业务解除这些引用。
