它在这三个方面特别适合做脚本层支撑：

## table：

table 是 Lua 里最核心的数据结构，很多时候它既承担容器角色，也承担对象和状态结构的角色。它底层可以同时支持类似数组和哈希映射的访问方式，所以特别适合游戏 UI 模块这种既有列表数据、又有结构化状态的数据场景。
换色模块里，我会用顺序部分存颜色列表、卡槽列表这类需要遍历渲染的数据；用键值部分存单个槽位的属性，比如颜色、解锁状态、是否装备、资源引用等。
另外像当前选中车辆、当前选中卡槽、页面显示状态、服务端返回的数据快照，这些也都适合放进 table 统一管理。
所以 Lua 里很多逻辑最终都围绕 table 展开，因为它足够灵活，既能表达列表，也能表达业务对象和页面状态

## 全局变量：

没有加local的变量
Lua 为了管理那些没有加 local 关键字声明的变量，在底层偷偷塞给你的当前代码块（Chunk）一个默认的 table。所有你以为的“全局变量”，全都被当成 Key-Value 键值对，塞进了这个 table 里，这个表被称为环境表。访问全局变量往往更像一次表查找

## local：

local，存在栈上，速度快，作用域随代码块结束，不用local默认为global

## Lua 里通常强调少用全局变量，主要有三个原因

作用域更清晰：local 只在当前模块或当前函数内生效，不容易被别的代码误改
性能更好：local 访问通常比全局查表更直接，而全局变量本质上往往要经过 _ENV / _G 查找
更容易维护：大型 UI 模块里变量名很容易重复，用 local 可以避免模块间互相污染
在这个换色模块里，大部分临时变量、函数内部状态、页面渲染中间结果，我都会优先用 local，比如当前一次刷新生成的颜色列表项、临时计算出来的卡槽状态、局部回调函数等
像当前选中车辆、当前选中卡槽这类需要模块共享的状态，我更倾向于放在模块自己的状态表或 Model 里，而不是裸露成真正的全局变量

## 闭包：

### 定义：

Lua 里的闭包，本质上是函数和它所捕获的外部局部变量共同组成的结构。
比如一个函数内部定义了另一个函数，而内部函数使用了外层函数的 local 变量，那么即使外层函数执行结束，这个变量也会因为被引用而继续存在，通常会以 upvalue 的形式被闭包持有。

### 使用：

按钮点击回调：点击某个按钮时，需要拿到当前页面上下文或当前选中槽位
列表项生成：给每个颜色项或槽位项绑定自己的索引、颜色 ID
异步回包处理：请求发出去后，回调里可能要保留发起请求时的页面状态或操作对象

### 坑：

就是十个卡槽，我当时用了一个循环来绑定点击回调事件，直接用了循环的i，发现点击的结果都是第十个，捕获的是同一个变量。解决：加了local

### 普通全局表

它是一个在 Lua 虚拟机（Lua VM）启动时就被物理创建出来的 table，里面装满了 Lua 官方提供的所有标准库函数和基础工具

#### 和环境表区别：

环境表是告诉编译器：“未声明的变量该往哪个表里找/存”，其实也是指向一个表，作用域级别的（不同函数可以有不同的 _ENV）

## pairs、ipairs：

ipairs 的工作原理： 它只认数组部分
它内部的 C 代码逻辑就是一个简单的 for 循环：从 i = 1 开始，每次 +1，只要查到 table[i] == nil，它立马判定“数组结束了”，直接下班！
pairs 的工作原理
它底层调用的是 Lua 的 next() 函数。它不仅会扫荡数组部分，还会钻进哈希部分把所有藏在角落里的键值对全揪出来。但代价是：哈希表的遍历是没有固定顺序的

## ：.

Lua 里 : 是带 self 的方法调用语法糖，obj:func(a) 等价于 obj.func(obj, a)；而 . 只是普通函数调用，不会自动传 self。
在 UI / MVC 模块里，这个问题很容易出现在 Mediator、View 的成员函数调用，以及按钮回调绑定时。
如果函数定义时用的是 :，但调用时误用了 .，就会导致 self 丢失或者参数错位，进而引发成员访问报错或逻辑异常。
所以这类模块里我会特别注意成员方法定义和调用方式保持一致，回调场景下也会用闭包或绑定工具把 self 带进去。

## 元表：

一个普通的表去执行 tableA + tableB，或者去访问一个它根本不存在的键 tableA.hp，它当场就会报错或者返回 nil。这时候就需要引入元表，利用内置函数 setmetatable(普通表, 元表)，元表里面定义了一些不存在的值或者键值对。

### __index：

如果表里没有这个 Key，Lua 不会立刻放弃，而是去检查它有没有元表，元表里有没有 __index。如果有，Lua 就会顺着 __index 指示的方向去找
实现继承。

### __newindex

试图给表中一个不存在的 Key 赋值 时。 如果表里本来就有这个 Key，直接覆盖；如果没有，Lua 就会拦截这次赋值，转交给元表的 __newindex 处理。
讲下：
Lua 的元表可以理解为给一个 table 或 userdata 附加一套“行为规则”，用来定制这个对象在某些操作下的表现。
普通 table 默认只是一份数据容器，但如果通过 setmetatable 给它绑定元表，就可以拦截或改写一些行为，让 Lua 这种很轻量的数据结构具备更丰富的行为表达能力
访问不存在的字段：__index
给不存在字段赋值：__newindex
运算符重载：__add、__sub 等
比较：__eq、__lt
转字符串：__tostring
被当函数调用：__call
__index 解决的是“读不到怎么办”，__newindex 解决的是“写不到怎么办”。
前者更常用于继承链和默认值回退，后者更常用于代理表、只读保护或者统一管理赋值逻辑。

### 只读表：

表现为空表，如果读用index指向真正的表，如果写，用newindex报错。

#### 用途：

Lua 本身没有传统强类型类系统，所以很多“对象行为”“继承”“默认字段回退”这类能力，都会基于 table + metatable 来实现。元表常见用途包括：模拟面向对象、做继承链、做默认值查找、做代理表、做只读保护，或者给配置 / 状态对象

## 协程

### 定义：

Lua 里的协程是一种用户态的轻量执行单元，本质上是可以主动挂起和恢复的函数执行流。
它和线程最大的区别是：协程不是并行的，一般还是运行在同一个线程里；它是协作式调度，而不是由操作系统抢占式调度。
也就是说，线程什么时候切换很多时候由 OS 决定，而协程什么时候让出执行权，通常是代码自己通过 yield / resume 控制。

### 用途：

游戏里常用协程，是因为很多逻辑天然就是“分阶段、按时序推进”的，比如等待动画播放完成、等待网络回包、分帧执行任务、剧情流程推进等。
如果不用协程，这些逻辑可能会写成很多层回调或状态机；协程能让流程代码写得更线性、更好读

### 优点：

更轻量，不需要系统线程调度。

### 使用：

coroutine.create(函数)： 创造一个协程。注意，创建出来后它不会立刻执行，而是处于 suspended（挂起
coroutine.create() 时，底层相当于调用了 C API 的 lua_newthread()。
这个函数会创建一个全新的 lua_State！这个新的 lua_State 有自己独立的“数据栈”和“调用栈”所以它跑起来不会和主线程打架，但是，它内部的全局指针依然指向最初的那个 global_State。
coroutine.resume(协程, 参数)： 唤醒协程。给它通电，让它开始跑，或者从上次暂停的地方继续跑。
coroutine.yield(返回值)： 协程在自己内部调用这个函数，立刻冻结当前的所有状态
resume 和 yield 是双向传值的

## Lua 虚拟机lua_State

### LUA调用CPP：

C++ 函数必须符合固定签名：int Function(lua_State* L);注册给lua，lua全局表会把它存成地址，调用时，把参数压入虚拟栈，调用地址，从而调用，随后cpp把答案压入lua栈，lua读取。

### cpp调用lua：

相反，也是压入栈，lua去拿。
lua_pcall

### cpp对象要包装成userdata，给lua使用。

### 数据栈—— C 与 Lua 的数据桥梁

这个栈的每个槽位可以装下任意 Lua 数据类型

### 调用栈

维护着 Lua 函数的调用层次。当 Lua 脚本里发生 A() -> B() -> C() 的调用时，lua_State 会记录当前的执行指令指针（PC - Program Counter）、局部变量在哪、以及返回地址。

### 全局状态

global_State（全局状态）： 全局唯一。它管理着垃圾回收器（GC）、字符串常量池（String Table，Lua 里相同的字符串在内存里只有一份）、所有被加载的 C 模块等“全局资产”。
lua_State（主线程）： 也就是你的 Main Thread。它包含自己的数据栈和调用栈，并且内部有一个指针指向那个 global_State

## 使用注意：

你用完栈之后，栈的高度必须和一开始一模一样
防止栈泄露
严谨的“类型验证” (Type Checking)C++ 是强类型，Lua 是弱类型（动态类型）。当你在 C++ 里从栈上拿数据时
栈上的元素定位有两种方式：正数索引和负数索引。正数索引（绝对坐标）： 从栈底开始数，1 是栈底的第一个元素，lua_gettop(L) 是栈顶元素。负数索引（相对坐标）： 从栈顶开始数，-1 永远指向栈顶，-2 是栈顶下面那个。
从栈上获取一个 Lua 字符串的 C 指针（const char*）时，这个指针的寿命，与该字符串在栈上的寿命完全绑定，所以一定要拷贝

## 热更新：

DLL方式：先编译好新的.dll,通过LoadLibrary和GetProcAddress重新定位函数地址。

### 是什么：

在不重启客户端的前提下替换或修正一部分 Lua 脚本逻辑让新的逻辑在运行中的游戏里生效
比如某个活动逻辑、UI 逻辑、数值判断、引导脚本有 bug如果能热更，就不用等完整客户端发版
游戏项目会特别关注它，是因为很多 UI、活动、引导、业务逻辑都写在 Lua 层，线上一旦出问题，如果能热更新，修复速度会比等客户端版本发布快很多。

### 原理：

LUA：在 Lua 里，函数本质上只是一个表（Table）里的普通变量，且晚期绑定
require：
require("MyModule")
查缓存： 去一个全局的内部表 package.loaded 里找，看看有没有一个叫 "MyModule" 的 Key。
命中缓存则直接返回： 如果找到了，说明这个模块以前被加载过，require 会直接返回缓存里的那个 Table，绝对不会去读硬盘。
没命中才去读文件： 如果没找到，它才会去硬盘上找 MyModule.lua，编译成字节码，执行它，然后把执行结果塞进 package.loaded["MyModule"] 里，最后返回给你。

### require后就会立刻生效吗？

不一定。因为 Lua 的 require 默认有缓存机制，模块加载过之后会记录在 package.loaded 里，如果不先清掉缓存，重新 require 可能还是拿到旧模块。
但就算清掉 package.loaded 并重新 require，也不代表热更新已经真正完成。
因为运行时很多地方可能已经持有了旧模块、旧函数、旧对象实例或者旧回调引用，这些引用不会因为文件重新加载就自动全部替换。

### 如果一个模块已经创建了很多页面实例、回调闭包或者定时器，你把模块代码热更了，为什么这些地方还是可能继续跑旧逻辑？

因为热更新替换的通常是模块定义或新加载的函数，但运行时已经创建出来的页面实例、闭包回调、定时器回调，往往还持有旧函数或旧对象引用。
这些引用不会因为模块文件重新加载就自动更新，所以它们后续触发时，仍然可能执行旧逻辑。
另外有些对象内部还带着旧状态，如果只替换代码、不处理状态，新的逻辑也未必能直接接上。
所以热更新时往往不只是“重新加载文件”，还需要考虑旧引用替换、实例重建、回调重新绑定，必要时还要做状态迁移

### 分代 GC ：每次 GC 是否有必要扫描所有对象？

核心思想：大部分新创建的对象很快就会死亡；能存活多轮的对象，通常还会继续存活很久。大量工作都浪费在“明知道大概率不会死”的老对象上。
