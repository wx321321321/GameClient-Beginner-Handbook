# 指针引用相关：

## 指针：存储目标对象地址的对象 引用：对象的别名
#### 空指针、野指针、悬空指针：
nullptr为空指针，悬空指针是资源被释放，野指针是初始化没管理资源。
#### const指针：
##### 底层const：
指向对象本身，如int*const ,意思是不能通过这个指针去改变量，但如果底层不是const，可以通过别的方式（其它的指针）改，相反，如果底层是从const，就算骗过了编译器，也是未定义行为，不能改。
##### 顶层const：
指向指针，不能换对象，但可以借此来修改对象。
引用的本质其实就是封装好的顶层const，完成了自解引用。
#### 数组指针与数组指针：
```cpp
int *p[5];：里面有五个整形指针   arr + 1，跳过一个整数
int (*p)[5];指向一个有五个元素的数组，可以通过p[0】来访问
&arr，实际上是数组指针，p=&arr,p++跳过一个数组
注意(*p)[1]和p【1】区别   sizeof(p)和sizeof(*p)大小不同
```
##### 数组名退化：
如返回值、函数传递时，会发生退化为int*退化为首元素指针，但sizeof不会退化。
#### NULL和nullptr
NULL 更像“值为 0 的老式空指针写法”，nullptr 才是现代 C++ 里真正类型安全的空指针。
如果调用fun(NULL)会调用int，nullptr就是为了解决这个问题。它可以隐式转换为：任意对象指针类型任意函数指针类型
#### 空指针调用函数：
##### 如果是非虚函数
编译器将普通成员函数翻译成类似 A_Hello(A* const this) 的全局函数。只要函数内部没有访问任何成员变量（即没有用到 this 指针），它就不会尝试对 0x0 地址进行解引用
##### 虚函数
崩溃
#### optional：
对于一些不需要指针管理的，以免用nullptr，本质是对象和bool，通过判断bool判断这个来判断对象是否存在，存在再去读值。解决之前用特殊值作为返回值来表示失败等情景。
##### 使用方法：
std::optional<int>x,用x.has_value()来判断是否存在，*x取值，这里不是解引用，重载了运算符。
#### void*：
指针的本质是一个内存地址。通常的指针（比如 int* 或 double*）除了记录地址，还附带了类型信息。类型信息告诉编译器：“从这个地址开始，往后读几个字节算一个完整的数据，但void* 是纯粹的地址
##### 特点：
能包容万物，不需要强转，不能直接解引用，因为不知道几个字节，使用前强转。同样的，不能做指针运算（ptr++）
#### 引用是否占用存储空间？
视情况而定，有的时候比如作用域局部变量，编译器优化给放在寄存器上，就不用。
##### 牢记一点！看到引用指针混用时，记得引用不一定有内存，看能否取地址。

### 指针和引用的区别：
```
指针是一个变量，存的是地址，引用是对象的别名
指针可以不初始化，也可以初始化为 nullptr引用必须在定义时初始化
指针可以为空引用按语言语义应当绑定到一个有效对象，通常认为不能为空
指针可以改成指向别的对象引用一旦绑定后，不能再引用别的对象
指针需要解引用 *p引用使用时和原对象几乎一致，像直接操作变量
指针本身可以取地址引用也可以取地址，但取到的是所绑定对象的地址
内存：引用绝大多数情况下占用。因为它底层是指针，在 64 位系统下通常占用 8 个字节的内存空间。例外（编译器优化）： 如果引用只是作为一个局部变量存在，且编译器能完全看透它的生命周期，可能会通过寄存器优化直接替换掉它，这时候它才真正做到“不占内存”。指针：固定4/8字节
sizeof指针是指针大小，引用是对象大小。
```

## 左值右值
### 基本：
#### 区别：
左值它在内存中有固定、明确的物理地址。可以用 & 运算符获取它的地址，有名字。它是临时凑出来的数值，没有固定的内存地址（通常存在于 CPU 寄存器或者栈的临时计算区中）。你绝对不能对它使用 & 取地址，也没有名字
#### ++i与i++：
++i (前置递增) 是 左值，它直接在变量 i 本身的内存里加 1，然后把 i 本身返回。因为返回的是原来的那个变量，所以它有名字、有地址。，i++ (后置递增) 是 右值它的逻辑是“先用后加”。为了让你能用到旧的值，编译器必须在底层偷偷克隆出一个临时的副本把旧值存起来  i=5，++i返回6，i++返回5.
#### 左右值引用：
右值引用可以绑定到 const 左值引用：Const T& 允许引用临时对象，且不会修改对象的状态，而右值引用本身允许修改资源（如移动语义），但将其绑定到 const 左值引用时，资源将不能被修改。
右值不能绑定到非 const 的左值引用 T&（左值引用默认想要修改内存，但右值马上要释放资源，因此编译器禁止了），左值不能绑定到 右值引用 （使用std::move)
### std::move：
#### 基本：
##### 移动操作：浅拷贝对方的指针，然后必须把对方的指针置为空，从而完成资源窃取。
##### 默认的拷贝构造函数执行的就是浅拷贝，只复制地址。
##### 深拷贝的原则是：遇到指针，绝不只抄地址，必须重新 new 一块新内存，然后把原内存里的值抄过来
这样处理后的变量叫做将亡值：既有佐治的内存地址和身份，又可以被窃取资源，当然，必须立刻处理(a=std::move(b))，如果不处理又恢复成了左值
#### 意义：
移动语义的核心收益在于转移堆内存指针的所有权，从而省去深拷贝，对平凡类型，移动操作和拷贝操作在汇编层面上是一模一样的。盲目对所有变量加上 std::move 只会让代码变得可读性极差
#### return值：
return local_var; 时，编译器会直接在调用方的函数栈帧里构造这个对象，彻底消除任何拷贝和移动的开销写了 return std::move(local_var);，你实际上是在强迫编译器放弃 RVO，转而把返回值变成一个右值引用，这反而会触发一次移动构造函数的调用
#### std::move_if_noexcept
如果程序员在要移动vector的对象类的移动构造函数后面加上了 noexcept 关键字，则使用移动构造函数。否则底层悄悄退化为普通引用，强行触发你的【拷贝构造函数】
#### 对右值引用进行move
函数参数传入&&，但有了名字，会是左值，就再move一下，不然还是不会触发移动函数。
如果一个东西有名字，它就是左值；如果你想把它当右值用，你就必须 std::move 它，或者 std::forward 它，这也是完美转发的意义。
### std::forward：
#### 原因：
在cpp中，一个变量有名字，就是左值，所以，当fun（10),在fun（int &&a){do(a)}中，do收到的是一个左值，编译器认为传入了一个左值，从而原本可能偷资源就好，现在需要拷贝，浪费性能。
#### 万能引用：
T&&，传给右值，就是右值引用，传给左值，就是左值引用。
##### 底层原理：
引用折叠cpp11新特性，11，12，21都是左值引用，22是右值引用。
##### std::forward
如果它通过模板类型 T 发现你原本传进来的是个右值，它就把 arg 重新强转回右值。如果它发现你原本传进来的是个左值，它就什么都不做，让 arg 继续保持左值形态。
##### 前提：
万能引用的前提必须是类型T（auto）因为触发条件它必须发生类型推导。格式必须是T&&,不能有const，也不能是stdvector《T&&>因为在定义时，已经确定了T的类型，不会再发生类型推导。
## 智能指针：
### RAII：智能指针的核心思想
把堆上的资源（动态内存、文件句柄、网络锁）绑定到栈上对象的生命周期里。在构造函数里获取资源，在析构函数里释放资源。因为局部变量（栈对象）在离开作用域时，系统一定会自动调用它的析构函数（哪怕中间发生了抛出异常）。这样就能保证资源 100% 被释放
##### 如果每次new之后delelte也不行，因为会有异常安全，当函数抛出异常后，它的后部分不会执行，delelte就失效了
#### 例子
##### 智能指针
##### std::lock_guard\nstd::unique_lock
防止死锁。如果没有它们，你必须手动 mutex.lock() 和 mutex.unlock()，一旦函数中间发生了 return 或抛出异常，锁就永远不会释放，程序直接卡死
##### std::lock_guard
一旦创建就死死咬住锁，直到它自己被销毁。特点： 极其轻量，性能最高。限制： 不可中途手动解锁，不可复制，不可移动。适用场景： 90% 的简单临界区保护（进函数加锁，出函数解锁）。构造时自动 lock，出了这个 {} 自动 unlock
##### std::unique_lock
手动开关： 可以在生命周期内随时调用 .lock() 和 .unlock()。延迟加锁： 构造时可以传参数 std::defer_lock，先不锁，等后面有空再锁。\n尝试加锁： 支持 try_lock_for 或 try_lock_until（限时等待，过时不候）。移动： 它可以作为函数返回值，或者存入容器（lock_guard 不行）。

### 控制块
控制块：强引用计数、弱引用计数（第一个强引用也会增加弱引用，弱引用为0会释放掉MSVC（微软）或 GCC 标准库底层实现的一种具体优化手段（它们把所有强引用整体看作“1个弱引用）自定义删除器、分配器
强引用计数归 0 时，销毁管理的对象。\n强引用计数和弱引用计数都归 0 时，销毁控制块本身。
### 其它问题：
##### std::shared_ptr线程安全吗？
对控制块的操作是线程安全的，基于原子操作，对它所指向的对象的操作不是线程安全的需要加锁
所以也会出现野指针/悬空指针
##### sharedptr构造：
new T 会进行两次内存分配（一次给对象，一次给控制块）；make_shared 会进行一次连续的内存分配，将对象和控制块放在一起，缓存命中率更高
std::make_shared《int>(10)
如果是int* rawPtr = new int(10);直接用构造函数接管裸指针
std::shared_ptr<int> p3(rawPtr);
##### make_shared缺点：
make_shared 的缺点是什么？（因为对象和控制块内存分配在一起，如果还有 weak_ptr 存在，即使对象生命周期结束被析构，它占据的内存也必须等到控制块被释放时才能一起被回收）
##### 构造可以接受weakptr，但不推荐，风险较高，建议用lock
lock原理：去检查strong计数，>0返回一个sharedptr，小于等于0std::bad_weak_ptr，推荐用lock
##### weakptr构造：
必须从weakptr或者sharedptr来构造
拷贝赋值和拷贝构造都可以接受sharedptr
##### 能不能用用 this 构造 shared_ptr
不能：shared_ptr 只要看到一个裸指针（Raw Pointer）传进它的构造函数，它就会无脑地为这个裸指针创建一个全新的控制块。它根本不知道这个裸指针是不是已经被别的 shared_ptr 管起来了，造成重复释放。
解决办法：为了解决这个问题，标准库引入了 std::enable_shared_from_this<T>
```
class Player : public std::enable_shared_from_this<Player>
外部：std::shared_ptr<Player> p1 = std::make_shared<Player>();
会将这个对象放到player中隐藏的weakptr中
类内使用std::shared_ptr<Player> safe_ptr = shared_from_this();就会直接去查weakptr
```
##### makeshared的底层逻辑非常死板：
只要塞给我一个裸指针必须为它 new 一个全新的控制块，多个智能指针共享同一个 int*，绝对不能把裸指针传给它们两次。你必须通过智能指针之间的拷贝或赋值来传递。
在类的外部，我们很容易写出 p2 = p1 这种代码来共享控制块。但是，在类的成员函数内部，根本没有 p1，只有 this 这个裸指针，没法进行智能指针的拷贝构造所以通过std::enable_shared_from_this<T>往类中偷偷加了个指针
##### 能否和普通指针混用：
能，但遵守原则：只负责干活（访问数据、调用函数），绝对不准碰公司的资产（绝对不能调用 delete）
eg：1.作为函数参数。2。对接 C 语言底层的旧库 3.类的非拥有型返回
单例管理器拥有一个对象，外部系统想要获取这个对象，千万不要返回 shared_ptr（这会让外部意外延长对象的寿命），应该直接返回裸指针
