# 模板

## 模板

### 重载、重写与模板：
##### 重载：同一个函数名，参数不同，在编译期选择调用哪个函数、
##### 重写：也叫覆盖，子类覆盖父类的函数，只要是同名就覆盖，不管参数对不对（根据作用域查询）
##### 模板：模板就是“把类型、值、行为参数化”的代码生成机制，有函数模板和类模板。 


### 模板基本：

##### 函数模板和普通函数同时存在时，编译器通常怎么选择
编译器会先做重载决议，看谁是更匹配的候选。一般常见经验是：如果普通函数和模板函数匹配程度一样好，通常会优先选普通函数
##### 模板的声明和定义：
声明和定义不能拆开写，.inl，这是目前业界最标准的做法。我们强行把代码拆开写，但在物理层面上依然让它们捆绑在一起，创建一个 .h 文件写声明创建一个 .inl (Inline 的缩写) 文件写模板定义（不叫 .cpp）在 .h 文件的最末尾，强行 #include "xxx.inl"、
#### 实例化：
在 C++ 中，模板本身不是真正的代码，它是给编译器看的“图纸”。
当写下一个类模板或函数模板时，编译器并不会立刻为它生成机器码。只有当在代码中实际使用它，并传入了具体的类型（比如 int 或 AActor）时，编译器才会照着图纸，为你实时生成一份专属的代码。这个过程叫做实例化、
##### 报错：
编译器遇到模板定义时，只做最基本的语法检查如果不调用，模板里即使有语义错误（比如调用了不存在的函数），也有可能不报错

##### 隐式实例化
直接调用函数 CrazySkill(myTarget)，编译器自动推导出 T 是 int 并生成代码
##### 缺点：
编译器在编译所有文件时，会像个没有记忆的傻瓜一样，把 vector<int> 的图纸来来回回翻译了 多遍，分别塞进多个 .obj 目标文件中。最后链接器（Linker）加班加点，把这，只保留 1 份。这就导致了编译时间极其漫长，且产生了大量冗余工作。
##### 显式实例化
在 cpp 文件里硬写一句 template void CrazySkill<int>(int);，强迫编译器立刻把这份图纸盖成实体房，这通常用来减少编译时间和解决链接错误
把模板的“声明”和“实现”分离，解决“无法解析的外部符号 (LNK2019)”
可以把定义和声明分开，只在一个地方显示实例化，其它的地方
.h中extern template class MyStack<int>;，在其他的地方就可以直接使用了
##### 非类型模板参数：
把信息“死死烙印”在编译期，压榨出极致的性能，必须传入常量，传入变量就报错



#### 全特化、偏特化
##### 全特化：
全特化是指你为模板的所有参数都指定了确定的类型必须以 
```
template<> 开头（表示参数列表已经空了，全部定死了）
template <> class vector<bool> { ... };，为了节省空间，按位存入
```
##### 偏特化
偏特化并没有把所有参数彻底写死成某个具体类型只有类模板（Class Template）支持偏特化

它不是把参数全部写死，而是针对参数的某种特定模式进行定制，参数减少/参数范围化
如果你想对函数模板进行类似偏特化的操作，只能通过函数重载
##### 消除歧义法则
内部必须加必须加 typename条件：不然会以为是T：：命名空间（消除歧义法则）
这个名字依赖于某个模板参数（比如它跟在 T:: 后面）。
cpp规定：默认所有依赖于模板参数的名字（Dependent Names）都不是类型
这个名字代表的是一个类型（比如迭代器、typedef 出的别名等），而不是变量或函数。
#### 模板的定义周期：
##### 第一阶段（定义期）：
 编译器第一次看到模板代码，此时它并不知道 T 到底是个什么东西（是 int？是 std::vector？还是你自己写的某个奇怪的类？）。
 ##### 第二阶段（实例化期）： 
 真正有人调用这个模板并传入具体类型时。
 ##### 消除歧义法则，就是为了解决编译器在“第一阶段”的语法解析危机。
#### 实例化过程：
##### 候选人提名
编译器拿着 int 去套模板 A 和 B。模板 A 说：“我是 T，我可以是 int。”（成功）模板 B 说：“我也是 T，我也能变 int。”（成功）结局：两位选手都进入了决赛圈。
##### 重载决议
编译器看着手里这两个完美的 int 候选人，试图选出一个“最合适的”。编译器左看右看，发现两个模板“一模一样”，没有任何依据能证明 A 比 B 好mbiguous Call（二义性冲突）。
你想让它们各走各的路，就必须给其中一个（或两个）加排他性条件（enableif/requires）
##### 实例化
只有当第二关选出了唯一的冠军，才会进入这一关。编译器翻开冠军的函数体，开始把 T 换成 int 生成机器码。Hard Error（实例化阵亡）。比如函数体里写了 val.begin()，但 int 根本没有这个成员。

## 类型推导规则
##### 类型推导：
在没有模板推导时，每次调用一个模板函数，都必须手动、显式地告诉编译器 T 是什么。模板推导机制免除了这个麻烦
#### 函数模板参数推导
只需要调用函数，把参数传进去，剩下的交给编译器
##### 推导失败
编译器的推导是很死板的，它不会自动做隐式类型转换。如果在同一个模板参数上，你给出了两个矛盾的线索，它就会报编译错误。
```
template<typename T>推导规则：根据void f(ParamType param);，对于ParamType的类别：
ParamType 是指针或普通引用（比如 T& 或 T*）保留原类型的 const 属性，但会忽略引用
ParamType 是万能引用（T&&）  如果你传左值，T 会被推导为左值引用（触发引用折叠）。如果你传右值，T 就是一个普通非引用类型。
ParamType 是纯粹的值传递，是按值传递，意味着你要拷贝出一个全新的独立对象。丢掉 const、引用。如果传入数组或函数，会退化成指针
```
##### auto
推导规则和模板推导几乎一模一样
对于初始化列表auto x = {1, 2, 3};，auto能推导出来std::initializer_list<int>，但函数模板不能
##### SFINAE
替换失败非错误：编译器在进行函数重载决议（Overload Resolution）时，它会拿着你传入的具体类型（比如 int），去尝试套用所有的模板候选人。
如果是函数体内部（Body）的语法错误： 编译器会直接抛出致命错误（Hard Error），编译失败。
如果是函数签名（Signature，包括返回值、参数列表、模板参数）上的语法错误： 编译器会触发 SFINAE去看下一个重载候选人。
要写一个打印函数，想让整数和浮点数走不同的逻辑当调用 print(10) 时，编译器会发现：T=int 既能套用 A，也能套用 B。它会直接甩给你一误：“Ambiguous call（调用歧义）

####  std::enable_if与requires
##### 前者问题：
假设你调用了一个 STL 算法，不小心传错了一个参数类型。编译器会把所有的 enable_if 候选人都试一遍，发现全部 SFINAE 失败了把你代码里尝试过的所有失败路径，几百上千行的模板实例化堆栈，连带着底层源码全部打印到屏幕上
##### requires 极度高效
不需要生成任何中间结构体，它可以像计算 1 + 1 一样，瞬间算出约束条件的 true/false
####  decltype 完全根据输入推导类型：
```
decltype(e)推导法则：
如果 e 是一个没有被括号包裹的普通变量名、函数名，或者是类的成员访问（如 obj.member 或 ptr->member）。结果： 直接返回该实体在代码中声明时的确切类型
如果 e 是一个函数调用表达式（比如 func(1, 2)）。结果： 直接返回该函数声明的返回值类型，不会真正执行这个函数，只在编译期看签名
如果 e （加了括号）是一个左值（lvalue），推导结果为 T&。\n如果 e 是一个将亡值（xvalue），推导结果为 T&&。\n如果 e 是一个纯右值（prvalue），推导结果为 T。
```
##### decltype(auto)
这通常用于完美转发。如果你直接用 auto，它会把引用给“缩减”掉（即 Top-level const 和引用会被剥离）。但如果你用 decltype(auto)，它能原封不动地保留函数的返回值类型（包括引用和 const）
```
int x = 10;
int& get_ref() { return x; }
auto  a = get_ref();       // a 的类型是 int（引用被删了，发生了值拷贝）
decltype(get_ref()) b = get_ref(); // b 的类型是 int&（保留了引用，但写起来很长）
decltype(auto) z = get_ref(); // z 的类型是 int&，它是 x 的别名
```

## 奇异递归模板
##### 子类把自己传给父类模板，父类再通过这个类型反过来调用子类。实际上就是用模板实现“静态多态”。
```
template<typename Derived>
class Base
{
public:
    void interface()
    {
        static_cast<Derived*>(this)->implementation();
    }
};

class Player : public Base<Player>
{
public:
    void implementation()
    {
        // Player 自己的实现
    }
};
```
##### 与动态多态区别：
动态多态，靠虚函数表 vtable 在运行时决定调用谁。
静态多态，编译期就知道 Derived 是 Player，所以会直接生成
```
static_cast<Player*>(this)->implementation();
```
##### 优缺点：
没有虚函数表
没有运行时虚调用开销
更容易内联
类型必须在编译期确定
不适合直接用一个 Base* 装所有派生类
