# 多态
同样的调用形式，在不同对象上表现出不同的行为。
##### 静态多态：编译期多态，编译时就已经确定调用哪个函数/哪个版本，如重载、模板。
##### 动态多态：运行时多态，典型例子是虚函数。

## 类对象：
##### class和struct区别：
（1）默认访问权限不同，classprivate，struct是public的。
（2）默认继承方式不同，class默认继承是private，struct默认public。
除此之外，没有什么区别。
### 对齐
#### 原因：
（1）每个数据成员的起始地址，必须是该成员大小（或其 alignas 指定值）的整数倍。
（2）整个类（结构体）的总大小，必须是该类中“最大基本类型成员大小”的整数倍。
（3）cpp中，不同对象的地址空间不同，所以空类必须是1
### 生命周期
#### 初始化：
类的初始化严格按照定义顺序，并且分为两步走：先创建对象，把所有对象设为初始值（如果使用初始化列表会直接用列表里的值来创建），然后根据构造函数中的逻辑来进行拷贝复制
#### 列表初始化优点：
##### 性能更高：
不使用初始化列表，成员变量会先进行一次“默认初始化”，然后在构造函数体内再进行一次“赋值”
##### 语法强制要求：有些成员不能修改。
常量成员 (const)：常量一旦创建就不能修改，所以不能在构造函数体内赋值。
引用成员 (&)：引用在定义时必须绑定对象，不能先定义后绑定。
没有默认构造函数的类成员：如果成员变量所属的类没有提供无参构造函数，编译器无法自动进行默认初始化，必须手动在列表中指定初始化方式
#### 析构：
严格按照构造的反向顺序来
delete p 首先调用p的析构函数进行析构，然后读取头部的header，获得空间大小，将空间free
### 内存布局：
#### 对象：
##### 静态数据成员：
不属于某个具体的对象，而是属于整个类。不占用对象的 sizeof 空间。必须在类外进行初始化（const int 等少数情况除外）。
##### 常量数据成员 (const)：
一旦初始化就不能修改。必须且只能在构造函数的初始化列表中初始化。不占size
##### mutable 成员：
即使在 const 成员函数中，也可以修改被 mutable 修饰的变量。常用于逻辑状态不改变但需要更新缓存或计数器的场景。
##### 普通成员：
对齐，按照生命顺序严格分布
#### 函数
##### 静态成员函数 ：
没有 this 指针。因此，它不能访问非静态成员（变量或函数）。它可以通过类名直接调用。
##### 常量成员函数
函数签名后加 const（如 void func() const）。承诺不修改对象的任何非 static 成员。const 对象只能调用 const 成员函数

##### 非 const 对象
其实是“特权阶层”，它既可以调用非 const 成员函数，也可以调用 const 成员函数
##### const 成员函数保护的是“对象”的属性，而 static 成员根本不属于任何对象，所以能修改static成员

## 2.继承：
### 权限：public、private、protect继承
#### public 继承：
表示 "is-a" 关系。比如 Bird 继承自 Animal。父类的接口在子类中依然是接口。
#### protected 继承：
通常用于某些特殊的类层次结构，希望把父类的功能传给孙子类，但不允许外部直接调用。
#### private 继承：
表示 根据...实现关系。只是想利用父类的功能，但不希望子类被当做父类来看待（隐藏掉父类的所有接口）。
### 隐藏：
隐藏机制保证了：子类的开发者对自己的作用域有绝对的掌控权。
##### 如果子类定义了同名变量，父类的变量依然存在（占据内存），但被隐藏了
##### 对于函数，只要是同名，参数完全不同，父类的函数也会“消失”，在子类中调用报错。
##### 想要调用方法：
using Base::func，将父类空间中的func拉入子类中
### 重载：
发生在同一作用域函数名相同，参数列表不同和返回值不同无关编译期根据参数做决议
### 多继承：
#### 空间布局：
从继承左到右，逐个拷贝进来，最后是自己的内存空间。
### 指针偏移(隐式转换)
#### 前提：public继承
此时，编译器会自动计算偏移量并修改指针地址
Base* p = new Derived
#### Private/Protected 继承：编译器认为这种继承是“内部实现细节”,可以在内部进行转换。
##### 编译器的“视界”受限于指针的静态类型
```
class Base1 { int a; public: void op1() {} };
class Base2 { int b; public: void op2() {} };
class Derived : public Base1, public Base2 { int d; };
Base1* p=new derived();p->op2会报错

class Base1 { int a; public: void op1() {} };
class Base2 { int b; public: void op2() {} };
class Derived : public Base1, public Base2 { int d; };
Derived* p=new derived();p->op2 
这个就会发生指针的偏移，在调用时编译器传给op2的是偏移后的this指针

derive中有base2，所以能偏移
class Base1 { int a; public: void op1() {} };
class Base2 { int b; public: void op2() {} };
class Derived : public Base1, public Base2 { int d; };
Base2* p=new derived();p->op2不会报错，因为指针一开始就是指向base2
```

#### 转换成derive
##### static_cast:完全依靠编译器硬记偏移量，缺点是类型一定要对得上
##### dynamic_cast：必须有 RTTI
基类必须至少有一个虚函数（通常是虚析构函数）。有了虚函数，对象才有虚表指针，才能顺藤摸瓜找到 RTTI
#### 侧向转换成Base1：
##### static_cast依旧可以:
编译器虽然现在只看到 Base2 的视野，但如果你告诉它 static_cast<Base1*>(p2)，它会根据你定义的类继承结构（全景地图）进行两次逻辑跳跃：
向上看： Base2 是谁的基类？是 Derived 的。向下看： Derived 还有哪些基类？哦，还有 Base1。
物理操作： 编译器会生成一段代码：p2 的地址 - Base2 的偏移量 + Base1 的偏移量。
前提： 你必须在转换的地方让编译器看到 Derived 的定义。如果编译器只知道 Base2 和 Base1 的存在，却不知道它们共同属于 Derived，转换就会失败。
##### 还是一样的要求：必须是derive不能本身是base2，静态转换开销少，但不安全。
##### dynamic_cast
甚至不需要在当前代码里包含 Derived 的头文件，只要 Base2 和 Base1 有虚函数，它就能在运行时安全地帮你跳过去
##### 向下转换（Down-casting）和侧向转换（Side-casting）在 C++ 中绝对不会发生隐式转换。
### 构造：如何做到挨个构造的：
当你定义 class C : public A, public B 时，编译器在程序运行前就定死了 C 对象的物理结构
每一个基类的构造函数都假设自己收到的 this 指针指向的是该基类的开头
构造 A 时：C 的起始地址就是 A 的起始地址，直接传 this 过去。
构造 B 时：神奇的事情发生了。编译器会自动生成一段指令，把 this 指针加上 A 的大小，然后把这个偏移后的新地址传给 B 的构造函数。
构造函数知道每个 vptr 在对象内部的固定偏移量，所以它能精准地在内存中找到那几个位置，把正确的虚表地址填进去
##### 主基类：第一个基类，剩下的是副基类
##### 析构：
只调用自己的析构函数（没有虚函数的条件下），然后free整个块，如果没malloc，实际上没事，虽然也是UB，如果malloc了，内存泄漏

## 虚函数与虚表：基类可以提供实现，子类可选重写
### 纯虚函数：
基类通常不提供实现，子类必须重写（否则子类也是抽象类）包含它的类称为抽象类，无法被实例化
##### 纯虚函数的函数体通常用于提供默认行为，子类在重写时可以显式调用
##### 但也不能实例化，必须子类重写才可以
##### 如果你想让一个类变成抽象类，但又没有任何合适的成员函数可以写成纯虚的，最简单的办法就是把析构函数写成纯虚的
#### 抽象类有虚表:
纯虚函数编译器通常会在虚表对应的位置填入一个特殊的函数地址，通常叫做 __purecall：这个 __purecall 函数的作用非常简单：如果由于某种极其诡异的操作，程序在运行时意外调用了这个位置，它会直接报错并终止程
##### 原因：
继承蓝图：子类的虚表是在基类虚表的基础上“拷贝”并“修改”而来的。如果基类没有表，子类就失去了构建虚表的模板。
##### 只要类中包含至少一个纯虚函数，它就是抽象类，其它无所谓。
### 带虚函数的类：
#### 构造顺序：
基类构造递归向下，先完成所有基类的构造。
虚表指针设置 就在此时，编译器将对象的 vptr 指向当前类的 vtable。
成员列表初化按照成员变量在类中声明的顺序依次初始化
构造函数体 执行 {} 大括号内部的代码。
#### 析构顺序：正好相反
执行子类构造函数体：执行 ~Derived() 大括号 {} 里的代码。
销毁子类成员变量：按照成员在类中声明顺序的逆序销毁（先销毁 m2，再销毁 m1
执行 vptr 降级：（关键底层操作） 对象的 vptr 被拨回指向基类的虚表。
承列表顺序的逆序销毁
### final
#### 去虚化： 
修饰类（禁止被继承）或虚函数（禁止被重写）。
##### 底层优化意义： 当编译器看到 final 时，它知道继承链到此为止了，就可以把原本运行期的动态查表调用，直接优化成编译期的静态绑定（去虚化）
##### 构造函数中调用虚函数，实际上执行的是自身的
##### 在构造前，会先把vptr设成当前要构造的对象，所以不会向下查。
##### 析构函数中调用虚函数，也是如此
在逻辑上发生了查找，但在物理（机器码）层面，现代编译器通常会把这个查找“省掉”，类似于final
##### 哪些函数不能被声明为虚函数
非成员、静态、内联、构造
### 虚表：
B中虚表指针指向的虚表和C中B对象部分的虚表指针指向的虚表不一样（因为有可能对函数重写）
#### 不动态绑定的情况：
1.值调用
2.使用类作用域限定符强行调用
3.析构构造中调用
4.final的类指针
5.按值传递 / 对象切片
如果派生类对象被按值赋给基类对象，或者按值传参给基类形参，会发生对象切片派生类那部分被切掉，后续再调用虚函数也不会到派生类实现了
##### override：强制编译器在编译期检查父类是否真的有这个虚函数
### 虚析构函数：
C++ 的底层实现（Itanium ABI）中，一个类的析构函数其实并不只有一个。编译器会为每个带有虚析构函数的类生成一组“分身”。
#### D0
##### 先调用D1，再释放内存
并不是说delete强制两步走，只要达到最终目的就好，用来应对多态情况：编译器发现这是多态，它不知道 ptr 到底指向谁，所以它不再亲自指挥释放，而是生成这样一行指令：去虚表里找析构入口D0，然后调用它。
#### D1
先调用D2，然后再清理虚基类内容，不释放内存。
#### D2
析构当前对象内的所有内容，析构完成后调用父类（非虚基类）的析构函数，直到头，并不释放内存
##### 为什么D1D2分开：
虚基类必须由“最底层派生类”负责构造和析构
多继承中，只有主基类函数虚函数表存D0D1D2，次基类虚函数表中存的是trunk，寻找到主基类表。
### 虚表相关：
C++ 的运行时底层没有函数名这个概念，虚函数的查找本质上就是一次 O(1)的数组下标寻址,编译器会根据虚函数在类中声明的顺序，给每个虚函数强行分配一个固定不变的下标
在大多数编译器的实现中，虚函数表的紧挨着的前一个位置，存放着一个指向 std::type_info 对象的指针。这个 type_info 结构体就是传说中的 RTTI，里面我是 Derived 类，我的父类是 Base，主要用于dynamic_cast，动态向下转换时，到这里来查，到底是不是。
##### 虚表：在常量区。虚表指针跟对象在哪里有关。
#### 实现原理：
通过虚表和虚表指针，虚表是一张表，里面记录着类中虚函数的真正地址，对于类，要用虚表指针指向虚表。运行时，当调用这个函数，先通过this指针找到虚表指针，再去寻找虚表，再寻找虚表中对应函数的入口地址。
虚函数如果是dll中，要在类定义前导入dll的lib在运行时，os导入dll会将对应虚表内容进行更改，或者伪造一张新的虚表，改一下对应的虚表指针。

## 虚继承：
### 核心思想：为了应对菱形继承中的二义性问题，使用虚继承的类，只有在最顶端的那个对象中存在：
```
A BC:A，D：BC
如果是D对象，则内存空间为：BCDA
如果是B对象：BA。
内存布局：
B类： 虚基类指针、B、A
D类：虚基类指针B、B、虚基类指针C、C、D、A
```
##### 为什么要用这个：
还是那个问题，编译器只有指针视野。
```
对于
B*p1=new B,B*p2=new D，p->funA，
编译器是不知道这个p是B类还是D类，但要去把指针偏移到A对象的起始位置，这个位置在BD中是不同的，所以，需要B和D中都有虚基类指针，来读取确定A的位置
```
##### 代价：
多了内存访问次数，降低性能。
解决菱形继承的二义性和动态多态，D 对象付出了巨大的内存代价
一个类改变，所有的内存布局都需要重新编译
##### 现代cpp解决办法：
现代 C++ 提倡一种折中方案：只允许继承一个带有数据成员的实体类，其他基类必须是纯虚接口
这样不用考虑二义性问题，就不用虚继承
##### 游戏引擎中：ECS架构，不是A是什么，而是都有什么
##### 构造顺序：
new D() 时，执行顺序如下：
最优先：初始化虚基类 A。由 D 直接调用 A()。
次优先：按声明顺序初始化非虚基类 B 和 C。
调用 B()，但 B 内部对 A() 的调用被抑制。
调用 C()，但 C 内部对 A() 的调用被抑制。
然后：初始化 D 自己的成员变量。
最后：执行 D 自己的构造函数体。
