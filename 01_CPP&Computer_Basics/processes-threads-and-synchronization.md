# 进程、线程与同步

并发工具首先解决“怎样组织多个执行活动、共享资源并保持正确”，不保证线程越多就越快。阅读这篇时把三个层次分开：操作系统负责进程、线程和调度；C++ 提供线程与同步语义；CPU 用原子指令、缓存一致性和内存顺序机制实现其中一部分。

## 1. 程序、进程和线程各是什么

程序是静态的代码和数据，例如磁盘上的 `.exe`。进程是程序的一次运行实例，包含地址空间、资源和执行状态。启动一个应用时，操作系统会建立相应进程；一个应用也可能创建多个进程，不能简单按“一个软件图标 = 一个进程”计数。

线程是进程中的执行流。现代通用操作系统通常以线程作为 CPU 调度的基本单位；进程主要作为资源管理和隔离边界。

### 谁共享资源，谁有自己的状态

| 项目 | 进程 | 同一进程内的线程 |
| --- | --- | --- |
| 地址空间 | 通常独立，需显式共享映射等机制才能共享某些内容 | 共享进程地址空间，包括代码、全局数据、堆和可访问的映射 |
| 执行现场 | 由其中的线程实际运行 | 各有寄存器现场、栈、调度状态以及线程局部存储等 |
| 文件等资源 | 通常拥有/引用文件描述符或句柄、权限、IPC 对象等 | 许多资源按进程共享，细节由 OS 决定 |
| 故障隔离 | 普通用户态崩溃通常限制在本进程，但共享资源等可能受影响 | 未处理的致命错误通常会终止整个进程 |
| 创建与切换 | 建立/切换地址空间等可能增加成本 | 同地址空间的切换通常少一些工作，但也不是免费 |

线程并非“不拥有任何资源”：至少需要栈、线程控制信息等。线程栈在使用习惯上归各线程管理，但在同一地址空间中并不天然禁止别的线程通过指针访问；跨线程引用栈对象必须保证生命周期和同步。堆对象也不是“随便访问都加锁”，只有发生并发冲突时才需要同步，线程独占的数据无须因此上锁。

### PID、PCB 与 TCB

PID 是进程标识符；PCB（进程控制块）是内核描述进程的管理结构，不能把 PCB 本身称为唯一标识符。教材常把以下信息归入 PCB，真实内核可能分在多个关联结构里：

- 身份与关系：PID、父进程 PID、用户身份、父子关系。
- 状态：新建、就绪、运行、阻塞、终止等。
- 执行现场：程序计数器、寄存器、栈指针、状态信息；在线程化系统中主要按线程保存。
- 内存：页表根、虚拟映射、代码/数据/堆/栈的管理信息。
- 调度：优先级、时间片、队列关系等。
- 资源：文件/句柄、动态库映射、IPC 对象和其他内核引用。

TCB（线程控制块）保存线程自身的栈、寄存器、状态和调度信息等。Linux 等系统的实际结构不一定严格叫这两个名字，但概念上的资源与执行状态仍需区分。

## 2. 并发、并行与上下文切换

并发表示多个活动在一段时间内都在推进，单核也可通过交错执行实现；并行表示同一时刻有多个执行活动在运行，需要相应的硬件执行资源。

进程/线程表现出动态性、并发性、相对独立性和异步性：调度和 I/O 会影响推进顺序。不能根据某次调试中的先后，推断下一次也会以同样时序运行。

### 什么时候发生调度

常见触发包括当前线程退出、等待 I/O/锁/事件而阻塞、主动让出、时间片耗尽，或更高优先级可运行任务出现。调度器可概念性分成：管理就绪/等待队列、选择下一个可运行任务、分派并切换上下文几个职责。

不能简单记成“所有中断里绝对不能调度、所有原子操作期间绝对不能调度”。内核在硬中断上下文或禁止抢占的临界区通常不能直接进行会睡眠的调度操作；可以记录调度需求，等到合适的返回/抢占点执行。原子操作对其他线程不可分割，也不意味着操作系统不能在它之前或之后切走。

### 切换要保存什么，为什么会慢

同进程内的内核线程切换，需要保存/恢复寄存器、程序计数器、栈指针等现场，并更新调度状态；通常不必切换用户地址空间。不同进程的线程切换还可能切换页表根及相关内存上下文，影响 TLB 命中。

Cache/TLB 的工作集变化也会形成间接成本。不是“把整份缓存保存到 PCB 再恢复”，也不是每次都清空 TLB：ASID/PCID 等可保留带标记的映射。具体开销取决于系统、工作集、核心迁移和调度实现，同进程切换也可能很贵。

内核调度的线程切换通常涉及内核路径；用户态线程/协程调度是另一种机制。进入内核本身也不等于必然换了线程。

### 调度指标与策略

| 指标/策略 | 关注点 |
| --- | --- |
| CPU 利用率 | CPU 有多少时间在做有效工作 |
| 吞吐量 | 单位时间完成多少任务 |
| 等待时间 | 任务在就绪队列等 CPU 的累计时间 |
| 周转时间 | 从任务提交到完成的总时间 |
| 先来先服务 | 按到达先后处理，简单但长任务可能阻挡后续任务 |
| 短作业/短任务优先 | 倾向较短任务，依赖对执行时间的估计，长任务可能饥饿 |
| 优先级调度 | 按优先级选择，需要考虑低优先级任务饥饿 |
| 时间片轮转 | 轮流获得时间片，响应性与切换开销受时间片影响 |
| 多级反馈队列 | 根据任务行为调整所在队列和优先级，平衡交互与吞吐 |

这些是理解调度的模型，不能假定某个现代 OS 原样只使用其中一种。

## 3. 数据怎么传，顺序怎么协调

### 进程间通信

| 方式 | 数据如何到达另一方 | 使用时要注意什么 |
| --- | --- | --- |
| 管道 | 经内核缓冲区传字节流 | 匿名管道常经父子/继承关系传递；命名管道可供无亲缘关系进程使用。单向/双向语义依 API，不能统一当作全双工 |
| 消息队列 | 经内核或服务维护的消息结构 | 可保留消息边界、类型等；有复制和系统调用等成本，不保证底层一定是链表 |
| 共享内存 | 不同进程映射同一片物理存储 | 建立后可少做数据复制，适合大量交换；需自行处理同步、布局和生命周期，性能不能仅凭名称断言最快 |
| Socket | 通过本地或网络端点传送数据 | 可用 Unix domain、本地回环或跨机器 TCP/UDP；KCP 是通常运行在 UDP 上的协议实现，不是与 socket 同层的内核接口 |
| 信号量等同步对象 | 表达许可、通知或执行条件 | 主要协调访问和顺序，不负责像消息队列那样携带业务数据 |

同一进程的线程已经共享地址空间，所以“线程通信”常变成“共享状态由谁读写、何时可见、何时允许继续”。可以使用队列、消息或快照降低共享范围，再用正确的同步保护边界。

### 互斥与同步

互斥要求同一时刻只有允许的参与者访问临界资源；同步还包含先后关系，例如必须先生产数据，消费者才能使用。互斥锁解决“谁能进入”，条件变量/事件等解决“条件没满足时怎么等”。

信号量保存许可数量，P/等待操作取得许可，不足时等待；V/释放操作增加许可。计数为 1 的二元信号量可用于某些互斥场景，但不等于 mutex：所有权、由谁解锁等语义不同。

事件用于通知某种状态或完成条件，具体 API 可能有自动复位/手动复位等规则。通知本身不保证按业务优先级唤醒任务；优先级队列应在任务调度层另行设计。

## 4. C++ 线程与异步任务的生命周期

### std::thread：对象与执行流要分清

使用可调用对象构造 `std::thread` 会启动新执行流；默认构造则创建不关联线程的空对象。新线程函数不必等构造者下一行执行后才开始运行。

如果 `std::thread` 析构时仍 `joinable()`，会调用 `std::terminate()`，即使线程函数实际上已经执行结束也一样。线程函数向外逃出的异常也会导致终止，不能自动传播到创建者。

- `t.join()` 阻塞**调用它的线程**，直到 t 关联的执行完成，并建立相应同步关系；不只主线程能调用。
- `t.detach()` 解除当前对象与执行流的关联，执行流结束后由实现回收关联资源；不保证它比进程活得更久，也不替引用对象延长生命周期。
- `joinable()` 表示对象仍关联一个可 join/detach 的执行流，不表示它此刻仍在运行。

以下四种状态返回 false：默认构造、成功 join 后、成功 detach 后、移动给另一个 thread 对象后。一个正在关联的执行流只能通过一次成功 join 或 detach 完成这次关联的处置；对象本身以后可重新接收别的线程。

线程构造通常将可调用对象和实参衰减复制/移动到其内部状态；这不提供“绝对线程安全”，指针和引用仍可指向共享对象。想按引用传某个普通对象，可使用 `std::ref`，并确保对象活得足够久：

```cpp
#include <functional>
#include <thread>

void reference_example() {
    int value = 0;
    std::thread worker([](int& out) { out = 42; }, std::ref(value));
    worker.join();
    // join 返回后，value 为 42；这里没有与 worker 并发读写。
}
```

`std::thread` 不直接收集返回值，可以用 `promise/future`、`packaged_task` 或有同步的结果对象，不必依赖全局变量。成员行为见 [C++ 标准草案 thread members](https://eel.is/c++draft/thread.thread.member)。

### std::jthread：自动收尾，协作停止

C++20 的 `std::jthread` 析构时若仍关联线程，会先请求停止，再 join。这样减少漏 join 的风险，但析构仍可能等待很久。

停止请求通过 `stop_token` 等让任务主动检查或配合可停止等待；它**不会强制中断任意代码**。任务忽略停止请求、死锁或长时间阻塞时，jthread 不能自动把问题消除。依据见 [jthread 析构规则](https://eel.is/c++draft/thread.jthread.cons)。

### std::async 和 std::future

`std::async` 用 future 接收结果或异常。启动策略决定是否另起执行流：

| 策略 | 行为 |
| --- | --- |
| `std::launch::async` | 以独立线程式的执行语义异步执行；不保证“调用瞬间立刻获得 CPU” |
| `std::launch::deferred` | 暂存任务，第一次非定时等待（如 get/wait）时在执行该等待的线程里调用 |
| 默认策略 | 相当于允许 async 与 deferred，由实现选择；标准不规定必须按当前系统负载决策 |

```cpp
#include <future>

int async_example() {
    auto result = std::async(std::launch::async,
                             [](int a, int b) { return a + b; }, 10, 20);
    return result.get();
}
```

`future.get()` 等待并取得结果，或重新抛出任务存下的异常。对普通 `future<T>`，get 后不再持有该共享状态，不能再次 get；不要依赖实现“一定友好报错”。结果类型是值、引用还是 void，会影响取得结果的方式，不能全说成统一的一次移动。

`future.wait()` 只等待、不取走结果；状态有效时可多次 wait，get 消耗状态后则不能继续使用它等待。需要多个消费者共享读取时可另考虑 `shared_future`。

来自 `std::async` 且实际选择 async 的共享状态，在最后释放引用时可能需要等待任务完成，所以临时 future 的析构可能让看似异步的调用变成串行。不是每种 future 的析构都阻塞，也不是 deferred 任务在析构时必定执行。规则见 [async 标准草案](https://eel.is/c++draft/futures.async)。

## 5. 锁保护什么，为什么需要 RAII

锁用来保护临界区中的共享状态并建立同步。它不要求“把当前核心所有脏缓存刷进主存，并让所有其他缓存失效”。正确理解是：解锁的 release 与之后成功加锁的 acquire 等语义，使受保护写入按 C++ 规则对后续持锁者可见；实现用什么指令由平台决定。

### 互斥锁

`std::mutex` 可保护多个变量共同满足的业务不变量。争用时实现可能先尝试用户态原子操作、短暂自旋，再进入内核阻塞；不是每次 lock/unlock 都发生上下文切换。

```cpp
#include <mutex>

std::mutex balance_mutex;
int balance = 0;

void deposit(int amount) {
    std::lock_guard<std::mutex> lock(balance_mutex);
    balance += amount;
}
```

所有冲突访问都要遵守同一同步协议，不能写入时加锁、读取时随意裸读。RAII 让正常返回和异常离开作用域时都释放锁，比手工散落 `lock()`/`unlock()` 容易维护。`std::unique_lock` 允许延迟加锁、主动解锁和与条件变量配合。

互斥锁适合复杂状态或可能需要等待的临界区，但持锁范围过长会限制并行，也可能造成死锁。它既不是“高并发必选”，也不是“性能一定很差”。

### 自旋锁

自旋锁拿不到时循环重试，不把线程立即挂起，因此是忙等待。它仍然是锁，持锁线程被抢占时别人也可能一直等，不能把它称为保证进度的无锁算法。

适合锁持有极短、竞争受控且持锁者能很快继续执行的场景。长临界区、单核、高争用或持锁期间阻塞，都可能让自旋浪费 CPU、加剧延迟。

以下只演示 acquire/release 关系，不是生产级公平锁：

```cpp
#include <atomic>

class SpinLock {
public:
    void lock() noexcept {
        while (flag_.test_and_set(std::memory_order_acquire)) {
            // 可按目标平台加入等待提示、退避等策略。
        }
    }

    void unlock() noexcept {
        flag_.clear(std::memory_order_release);
    }

private:
    std::atomic_flag flag_ = ATOMIC_FLAG_INIT;
};
```

x86 的 `_mm_pause()` 是自旋等待提示，可改善部分流水线和资源使用情况；它不是解锁、内存屏障或 OS 线程让出，也不是可移植的 C++ 接口。手写锁时还需考虑重入、所有权、饥饿和等待策略，不能只验“循环能跑”。

### 读写锁

`std::shared_mutex` 提供共享读锁与独占写锁：读—读允许并发，读—写和写—写互斥。只持读锁的代码不能修改被保护状态。

可用“读者数 reader_count、是否有写者 writer_active、等待写者数 waiting_writers”等共享状态理解实现，内部再配合原子操作、互斥和等待机制。真实实现不一定恰好有这三个字段，也不保证固定公平策略。读远多于写时可能合适，但额外管理成本、写者饥饿等问题需要测量。

## 6. 条件变量：条件不满足时怎样安全等待

互斥锁只决定谁能访问共享数据；如果队列为空，消费者还需要等待生产者放入数据。

手工“解锁后再睡眠”有一个窗口：

```text
消费者：检查队列为空 → 解锁 ─────────→ 准备睡眠
生产者：                    放入数据并通知
```

如果通知发生在消费者真正等待之前，就可能丢失唤醒。条件变量把“释放互斥锁并进入等待”衔接起来；醒来后重新取得互斥锁，再检查共享条件。

```cpp
#include <condition_variable>
#include <mutex>
#include <queue>

std::mutex queue_mutex;
std::condition_variable queue_changed;
std::queue<int> queue;

void push(int value) {
    {
        std::lock_guard<std::mutex> lock(queue_mutex);
        queue.push(value);
    }
    queue_changed.notify_one();
}

int pop() {
    std::unique_lock<std::mutex> lock(queue_mutex);
    queue_changed.wait(lock, [] { return !queue.empty(); });
    int value = queue.front();
    queue.pop();
    return value;
}
```

关键是状态修改和条件检查遵守同一把锁。通知不会存成一个永久“信号余额”，也不能代替共享状态。消费者可能在通知前就运行，此时直接看到非空即可；也可能虚假唤醒，或醒来时数据已被其他消费者取走，所以必须重新检查谓词。

这里的 `pop` 等待直到有元素；实际可关闭的工作队列还需把“队列已关闭”等状态纳入谓词和退出逻辑。信号量保存许可数量，条件变量主要负责等待与通知，这是二者的重要区别。等待语义见 [C++ condition_variable 规则](https://eel.is/c++draft/thread.condition.condvar)。

## 7. 死锁怎样形成，怎样避免

进程和线程都可能死锁。线程中常见于 mutex、读写锁、条件等待和共享数据结构；进程间还会涉及文件锁、数据库锁、跨进程信号量、IPC 和设备。递归锁只解决部分同线程重复加锁场景，不会消除多个资源的循环等待。

经典资源死锁需要以下四个条件同时成立：

1. **互斥**：某些资源不能同时给多个参与者。
2. **请求并保持**：持有一部分资源时，还等待其他资源。
3. **不可剥夺**：不能任意强行夺走已分配资源。
4. **循环等待**：等待关系形成环。

预防可以破坏其中一项，但要看资源性质：

- 可共享或可复制的资源，可能重新设计以减少互斥；真正不能并发修改的资源，不能简单取消保护。
- 一开始就取得本次所需的全部资源，拿不全则一个也不保持，可破坏请求并保持，但可能降低利用率。
- 获取后续资源失败时主动释放已有资源，重新尝试；必须能安全回滚中间状态，还要防止反复退让形成活锁。
- 规定所有参与者按一致的全局顺序获取锁，破坏循环等待。顺序必须稳定且确实覆盖所有路径，不能拿不相关指针做未经定义的简单大小比较。

多个 C++ mutex 可考虑用 `std::scoped_lock` 或 `std::lock` 的死锁避免算法统一取得，但已有锁和业务等待关系仍需整体检查。

死锁发生后，系统可尝试剥夺可恢复资源、撤销/终止参与者、回退到检查点或事务状态。普通 mutex 不能随意被另一线程强行解锁；终止线程也可能留下共享数据损坏，所以“强杀一个线程”不是普遍安全的解除方案。

## 8. 原子操作与 CAS

### 原子性是可观察语义，不是“调度器绝对不能打断”

原子操作要求其他相关访问无法观察到被拆开的中间效果。线程仍可能在相邻操作之间被调度走；某个原子类型的实现还可能使用锁，因此不能把 `std::atomic` 全部解释成“一条永不打断的硬件指令”。

常见标量原子可通过硬件指令高效实现；是否 lock-free 应看 `is_lock_free()`/`is_always_lock_free` 等。竞争严重时缓存行来回转移，原子操作也可能很贵，不保证比 mutex 快几个数量级。

在 x86 的普通可缓存、适当对齐场景中，带锁读改写通常由缓存一致性机制取得所需独占权；不能说每次都锁住主板内存总线。其他体系结构还可能使用独占加载/存储重试或专门原子指令。硬件背景见[计算机组成原理](computer-architecture.md)。

### std::atomic 的常用操作

```cpp
std::atomic<int> counter{0};
```

| 操作 | 含义 |
| --- | --- |
| `load()` | 原子读取 |
| `store(value)` | 原子写入 |
| `fetch_add(n)` / `fetch_sub(n)` | 原子读改写，返回修改前的值 |
| `compare_exchange_weak/strong(expected, desired)` | 比较当前值与 expected，相等则写 desired，失败则把观察到的当前值写回 expected |

`counter.store(counter.load() + 1)` 是两次原子操作，整体仍不是一个原子自增，多个线程可能丢失更新；需要使用 `fetch_add` 或正确 CAS 循环。

### CAS 成败及 weak/strong

CAS 可以理解为：检查位置 V 是否仍等于预期 A，若是则改成 B，比较与更新作为一次原子读改写。C++ 的 compare-exchange 是接口，不保证所有类型都对应一条相同硬件指令。

`weak` 允许伪失败，即比较值相同也可以报告失败，常用于本来就要重试的循环；`strong` 不允许这种伪失败。两者真正比较失败时都会更新 expected，循环里要按算法重新计算 desired 或重设预期，不能假定 expected 还是最初值。

### ABA：值没变，不代表期间没发生变化

以链栈的节点地址为例，原来的含糊 `AAB → BB` 不足以表达问题：

```text
最初：head → A → B → C
线程 1：读取 head=A，记住 next=B，准备 CAS(head, A, B)
线程 2：弹出 A，再弹出 B，再把 A 压回：head → A → C
线程 1：只比较 head 仍是 A，CAS 成功，把 head 改成旧的 B
```

此时 B 已不再是应当接回的栈顶，“地址又变回 A”掩盖了结构变化。可将指针与版本号一起比较，或采用适合算法的标记方法；版本回绕和宽原子支持仍需处理。节点可能被释放/复用时，还必须解决安全内存回收，版本号不能替代 hazard pointer、epoch 等生命周期方案。

## 9. 内存序：让不同线程对数据的先后达成约定

### 为什么有缓存一致性仍不够

现代 CPU 用 Store Buffer、推测执行和乱序执行提高吞吐，编译器也可在语义允许范围内调整指令。写入某变量不必马上到达 DRAM，其他核心也不必按源码中不同地址的顺序观察到它们。

```text
核心执行写入 → Store Buffer → 缓存/一致性网络 → 其他核心可观察
```

这只是理解硬件的一张图，实际传播路径依处理器而定。缓存一致性主要协调同一缓存行中的副本；C++ 还规定每个原子对象的修改顺序与线程间同步，不能把 MESI 本身当成完整的 C++ 内存模型。

对于普通共享数据，缺少所需同步会产生数据竞争，C++ 行为未定义。内存序的作用不是“修复一个本来合法、只是偶尔晚看到的普通变量”。

### 常用内存序的保证

| 内存序 | 适合的操作与保证 |
| --- | --- |
| `relaxed` | 保留该原子操作的原子性与对象修改顺序等要求，不据此发布其他普通数据 |
| `release` | 用于 store 或读改写的释放部分，可发布本线程此前的相关操作 |
| `acquire` | 用于 load 或读改写的获取部分；读取到相应 release 发布的值时建立同步 |
| `acq_rel` | 用于读改写，同时具有获取和释放语义，不适用于单独 load/store |
| `seq_cst` | 默认顺序；在相应 acquire/release 保证之外，为所有 seq_cst 操作和栅栏建立受约束的单一全序 |

release 不能用于单独 load，acquire 不能用于单独 store。CAS 还区分成功与失败顺序，失败部分是读取，不能指定 release/acq_rel。

“前面的绝不后移、后面的绝不前移”可辅助理解 acquire/release 的约束方向，但严格依据是 C++ 的同步与 happens-before 关系，不能把它扩展为任何相关机器指令都必须原样排列。seq_cst 的全序也不覆盖程序的所有普通指令，不意味着整个程序被硬件串行执行。

### 一次发布数据的例子

```cpp
#include <atomic>

int data = 0;
std::atomic<bool> ready{false};

void publish() {
    data = 42;
    ready.store(true, std::memory_order_release);
}

int consume() {
    while (!ready.load(std::memory_order_acquire)) {
        // 教学用短等待；长等待应考虑条件变量或合适的等待接口。
    }
    return data;
}
```

假设只有一次发布，且发布后不再有其他写入：消费者的 acquire 读到生产者 release 写入的 true 后，发布前的 `data = 42` happens-before 消费者对 data 的读取，因此可以安全读出 42。

如果消费者并没有读到相应发布结果，就不能仅凭“代码里一个 release、一个 acquire”宣称同步已建立。把两处改成 relaxed，也不能再据此保护普通 data 的读写。上述关系以 [C++ 原子顺序规则](https://eel.is/c++draft/atomics.order)为准，编译器再针对不同 CPU 生成相应指令和屏障；有些平台不需要为每个 acquire/release 额外发一条屏障指令。

### mutex 与 atomic 怎么选

mutex 保护一段临界区，容易维护多个变量共同成立的条件，也便于配合条件变量等待。atomic 适合单个状态、计数器、发布标志，以及经过完整设计的无锁算法。

多个 atomic 的单次操作都安全，不代表多个对象的组合更新自动具有事务性。例如“余额减少与库存增加必须一起成立”，通常先用锁把业务不变量表达清楚，再根据测量考虑优化。原子性、可见性、顺序和生命周期要一起成立，不能只把变量类型换成 atomic 就算完成并发设计。

## 10. 协程、池化与游戏中的任务拆分

### 协程保存什么，什么时候切换

协程支持暂停和恢复执行。其调度常在用户态由语言/运行库完成，OS 仍调度承载它的线程；“程序员显式控制”也可以体现为 `co_await` 和运行库调度，而不必手工保存寄存器。

有栈协程可能切换用户态栈与寄存器现场；C++20 无栈协程通常把跨暂停点所需状态放在协程帧中，通过生成的状态机恢复。帧常动态分配，但可能被优化到其他存储，大小取决于保存的状态，不能统一称为“极小的堆数据结构”。

暂停/恢复本身常不需要一次内核线程切换，但等待的 I/O、调度器实现等仍可能调用系统。协程能挂在一个线程上，也能由多线程执行器调度；只有在明确单线程、无其他并发访问、且不跨暂停点依赖易变状态时，才可省去部分线程锁。跨 `co_await` 的逻辑交错仍可能破坏不变量。

### 进程池、线程池与混合架构

进程池提前创建一批工作进程，线程池提前保留工作线程，让它们反复执行任务，减少每个任务都创建/销毁执行资源的成本。池大小、任务阻塞和队列背压仍需设计，堆数量不是解决吞吐的通用办法。

需要独立故障边界、插件隔离或模块天然独立时，多进程常有价值；需要频繁共享数据、低成本任务协作时，同进程多线程通常更方便。

以“一个场景 10,000 名玩家同时发操作，服务器处理并广播”为例，可以分层考虑：

1. 进程级分职责：网关、场景逻辑、数据库/缓存服务、日志等。
2. 场景进程内部按数据依赖分任务：网络收发、独立计算、受控的逻辑更新等，明确哪些状态归哪个执行流。
3. 用异步/事件驱动减少等待造成的空耗，并控制任务队列。
4. 超大场景还要处理 AOI、分区分片和广播规模；单纯增加线程数不会减少全量交互的算法成本。

### UE 的命名线程与工作线程

UE 中常讨论 Game Thread、Render Thread、RHI Thread 等有固定职责的线程，具体启用情况依引擎版本和运行配置。访问这些线程专属状态的任务具有线程亲和性。

Worker Thread 是任务系统中的通用执行资源，适合处理没有固定线程要求、基于安全数据或快照的计算。TaskGraph 等接口可表达 AnyThread 或命名线程目标；不同任务 API 的选项并不完全一样，不能把 AnyThread 当成任意 UE API 都共有的参数。

LLT 通常指 UE5 的 Low Level Tasks 后端调度层：把短任务分配到共享工作线程，重点是任务调度，不是每提交一个任务就新建一个线程。UE::Tasks 与 TaskGraph 的关系、后端细节要按目标引擎版本核对；[Epic Tasks System 文档](https://dev.epicgames.com/documentation/en-us/unreal-engine/tasks-systems-in-unreal-engine)说明二者共享调度器与工作线程后端。

任务化之后仍要守住对象生命周期和线程归属。耗时计算可用快照交给 Worker，结果回到合适线程应用；并发任务之间用依赖关系表达先后，不能默认所有 UObject 或游戏状态都可从任意线程读写。
