# 进程、线程与同步

本质是计算机为了提高并行效率、命令执行速率的各种工具

## 进程与线程：

### 进程：程序运行起来后，操作系统为它分配的一整套运行资源

进程是具有一定独立功能的程序关于某个数据集合上的一次运行活动，是系统进行资源分配和系统隔离的一个独立单位：当启动微信，os会创建一个进程给它，分配内存与文件资源。

#### 进程

程序是静态的。比如硬盘上的一个 .exe 文件、一个游戏客户端程序。它只是代码和数据的集合，还没跑起来。
进程是动态的。当程序被加载到内存、开始运行时，就成了进程。

##### 并发性、独立性、异步性

#### 唯一标识符：PCB，也就是进程控制块

##### 内容：

1.ID：进程 ID（PID）父进程 ID（PPID）用户 ID
2.进程状态信息：（就绪态）（运行态）（阻塞态）（终止态）
3.CPU 现场上下文信息：程序计数器、通用寄存器、栈指针、程序状态字（进程切换时，要把当前运行现场保存到 PCB 里，下次恢复时再读出来。）
4.内存管理信息：页表基址、段表信息、代码段、数据段、堆、栈相关描述、虚拟内存映射信息
5.调度信息：进程优先级、时间片，决定它什么时候上 CPU
6.资源信息：记录这个进程占了哪些系统资源
7.进程间关系信息：父进程、子进程等

##### 分配的资源：

独立的虚拟地址空间、代码段、数据段、堆、线程、文件描述符/句柄、动态库映射、IPC 对象、权限和调度信息

##### 线程控制块：

记录当前线程的栈信息以及寄存器信息。

#### 进程通信方式：

1.管道：数据先进先出，父子进程或者兄弟继承中使用，半双工/全双工都有。一个内核里的缓冲区。
2.消息队列  内核维护的消息链表 不要求进程有亲缘关系，由内核管理，比较稳定，但数据要拷贝进内核，再从内核拷贝出来，速度一般
3.共享内存  多个进程映射同一块物理内存 大家直接读写这块内存 速度最快 不需要频繁经过内核拷贝 适合大量数据传输  多个进程同时读写，会有竞争
4.socket  通用的进程通信接口，TCP,UDP,KCP，可以跨机器//直接本地回环
5.PV操作信号量  “传数据”的方式，而是：  进程同步 / 互斥工具

#### 线程之间通信：

同一个进程里的多个线程，共享同一份地址空间。
线程通信的核心不是“怎么传数据”，而是：怎么保证多个线程读写同一份数据时不乱。

#### 进程切换：

##### 进程切换时机：

主动切换：线程需要等待某些极其缓慢的操作，于是它主动把 CPU 控制权交还给操作系统
被动切换：进程调度。

##### 切换开销：

切换进程不只是换一段代码执行这么简单，保存/恢复寄存器、切换地址空间、切换页表（可能导致 TLB 失效）、切换内核态管理信息

##### 进程调度：

调度器：
1.排队器，按照一定的顺序将各个进程排列成一个队列，队列可能有不同的类型，例如阻塞队列，就绪队列
2.分派器，将决定要上处理机运行的进程从就绪队列中取出来，让其去运行
3.上下文切换器，在切换进程的时候不仅要保存被换下来的进程的上下文还要把要运行的进程的上下文布置好。

##### 时机：

1.正在运行的进程运行完毕，或者被阻塞，或者时间片用完

##### 不能调度的时机：

1.中断处理的过程中
2.一系列原子操作中。

##### 指标：

CPU吞吐率、等待时间、周转时间

##### 调度策略：

先来先服务，短进程有限，优先级，时间片轮转，多级反馈。

#### 同步：

各个进程之间的执行要按照一定顺序进行，互斥则是指，两个进程不能同时访问一个资源。

##### 线程同步方式：

1.信号量：如果只允许一个那就是互斥量。
2.信号事件，通过通知，还可以实现多线程优先级的比较。（优先级队列）

#### 死锁

进程和线程都会发生死锁，只不过发生场景往往不同。

##### 条件：请求和保持，不剥夺，互斥条件、循环等待

##### 解除：1.剥夺资源2.撤销进程3.进程回退

##### 预防：

1.互斥条件：无法
2.请求与保持条件：规定每个线程在开始干活前，必须一次性申请拿到所有需要的锁。如果拿不全，就一个都不拿，全退回去在旁边等
3.不可剥夺条件：规定如果一个线程拿到了部分锁，但进一步申请新锁失败时，它必须主动释放掉手里已经占有的锁，退一步海阔天空，过一会儿再重新尝试整体获取
4.环路等待条件：系统里所有的锁强制编上号（比如按内存地址大小，或者按业务逻辑 1、2、3），规定所有线程必须严格按照序号递增的顺序去申请锁

##### 信号量保存“许可的数量”；条件变量不保存信号，只负责通知线程“共享状态可能变了，醒来重新检查”

##### 条件变量：

当条件不满足时，让线程睡眠等待；条件满足后再被唤醒，避免线程一直循环检查、浪费 CPU。锁只解决“同一时间谁能访问共享数据”，不解决“条件不满足时怎么高效等待”。

```
可以手动解锁，但“解锁后再睡眠”中间存在竞态。例如消费者：
1. 发现队列为空
2. 解锁
3. 准备睡眠
恰好生产者在第 2、3 步之间执行：
1. 放入数据
2. 发出通知
此时消费者还没进入等待队列，会错过通知，然后开始睡眠。这叫丢失唤醒。
消费者：解锁 ────────── 睡眠
                 ↑
生产者：      放数据并通知
条件变量的关键能力是：释放互斥锁 + 加入等待/睡眠在同步语义上作为一个不可错过通知的整体完成。线程醒来后，还会自动重新获取互斥锁，再检查条件：
cv.wait(lock, [] {
    return !queue.empty();
});
所以不是“互斥锁不能手动解锁”，而是：手动解锁不能安全地衔接睡眠和通知；条件变量负责解决解锁与等待之间的竞态问题。
```

##### 线程死锁和进程死锁：

线程死锁：mutex、recursive_mutex、读写锁、条件变量配合锁使用不当、同一进程里的共享数据结构
进程死锁：文件锁、数据库锁、信号量、管道 / IPC 资源、设备资源、多进程间共享内存上的同步锁

### 线程：

执行功能的基本单位，拥有系统分配的栈资源用来保存信息，但自身不拥有资源，和其他线程共享父进程的资源。

#### 对于进程的堆资源，随便访问，对于堆访问要加锁或者原子操作。不同线程的栈空间，不应该跨线程访问。

#### 进程池：提前创建一批工作进程，让它们反复执行任务，避免每个任务都创建、销毁一次进程

### 多线程：

是指在一个程序中同时运行多个线程。每个线程都是程序中的独立执行流，共享同一进程的资源（如内存、文件描述符等）。

#### 并发：指在某些时刻有多个线程运行，它们的执行是交替进行的，但不一定同时。并行：指多个线程真正的同时运行（需要多核处理器）。

#### 线程切换开销：

##### 同进程线程切换：

当前线程的通用寄存器、程序计数器栈指针、浮点寄存器等状态保存到内存的线程控制块，但不需要切换地址空间（页表/CR3），所以开销一般比进程切换小。还需要切换到内核态

##### 不同进程切换：

需要切页表，会导致 TLB 命中率下降等额外开销。

#### 线程和进程区别：

##### 1.基本：

进程是os分配给程序资源的基本单位，一般而言，是一个程序运行时包括资源的总和。而线程本身不占用资源，共享父进程的资源，是CPU 调度的基本单位。

##### 2.内存：

进程相互之间绝对隔离。进程 A 看不到进程 B 的内存，同一个进程下的所有线程共享整个进程的内存（包括堆 Heap、全局变量、代码段）。但每个线程有自己私有的栈 (Stack) 和寄存器。

##### 3.切换开销：

进程切换： 极其沉重。CPU 需要把整个工厂的状态（页表、各种缓存）全部存起来线程切换： 非常轻量。因为大家都共用同一个进程的内存

##### 4.崩溃的波及范围

进程： 极其坚挺。如果是多个独立的进程在跑，进程 A 崩溃操作系统只会把 A 杀掉，进程 B 安然无恙。线程： 一损俱损。只要其中一个线程因为非法访问内存引发了崩溃，操作系统会直接拉闸，整个进程（包括里面所有的线程）瞬间暴毙。

##### 5.创建和销毁的速度

进程： 创建一个新进程非常慢（操作系统要分配内存、建页表）。线程： 创建和销毁的速度极快。

### 协程：

协程完全运行在用户态，操作系统甚至根本不知道协程的存在协程的切换是由程序员通过代码显式控制的

#### 开销：

没有系统调用，需要在用户态的内存里，把当前的几个关键寄存器存到一个极小的数据结构中，然后把另一个协程的寄存器状态读出来放进 CPU，开销极低

#### 协程的本质只是一个保存在堆内存里的数据结构，空间很小。

多个协程运行在同一个单线程内，由于是协作式调度，那么在这段同步代码中，不需要加任何锁，天然是线程安全的

#### 什么时候用多进程，什么时候用多线程？

多进程可以先粗略理解成：同时存在多个进程实例。

##### 适用于：

1. 隔离性要求高 ：一个模块崩了，不想把整个系统带崩、插件系统
2. 模块天然就是独立系统：游戏服务器不同功能模块

##### 多线程适用于：

共享同一进程地址空间、通信方便、更轻量

##### 对于场景体，通常不是“只选多进程”或者“只选多线程”，而是：多进程 + 多线程 + 异步/事件驱动 混合架构。

eg：一个场景，10000 名玩家，同时发操作，服务器要处理并广播结果
1.进程级拆分：把不同职责拆开，比如：网关进程、场景逻辑进程、数据库/缓存进程、日志进程
2.线程级：在单个场景进程内部，再用多线程处理：
对于超大场景，还需要进一步做 AOI、分区分片，而不是简单靠堆线程数

## 多线程与原子操作：

### std::thread

初始化一个std::thread，实例化自动启动
如果一个 std::thread 对象在析构时，既没有被 join 也没有被 detach，程序会直接调用 std::terminate() 导致崩溃
获取返回值极其麻烦（通常需要配合全局变量、指针或锁），且手动管理 join/detach 容易出错

#### t.join()：

主线程阻塞，乖乖等子线程执行完。

#### t.detach()：

斩断情丝，让子线程脱离主线程的控制，在后台自生自灭

#### joinable()（状态检查）：

在调用 join() 或 detach() 之前，用来检查线程是否还在活跃状态。一个线程只能被 join 或 detach 一次

##### 返回 false

1：默认构造的空对象。 你声明了它，但没给它分派任务。
2：已经被 join() 过。 线程汇合后，底层资源已被回收，它就变成了空壳。
3.：已经被 detach() 过。 线程被放飞到后台，当前对象与它断绝了关系。
4：被 std::move() 掏空了。 它的控制权被转移给了另一个 std::thread 对象。

##### std::thread 的构造函数

盲目地将所有参数拷贝（或移动）到新线程的独立内存空间中。这是为了绝对的线程安全。想按引用传递参数（让线程修改你原来的变量），直接传是不行的，必须使用 std::ref() 包装！

### std::jthread

std::thread 的完美替代品。如果 std::jthread 在离开作用域时你忘记了处理它，它的析构函数会自动帮你调用 join()，并且它还自带了取消机制，可以直接中断线程

### std::future和std::async

#### std::async：

第一个参数其实是一个启动策略（std::launch），如果不填，编译器会使用默认策略，由系统视当前负载自行决定。

```
std::launch::async（强制发货）： 保证立即在另一个线程中启动任务
std::launch::deferred： 根本不开启新线程！ 任务会被挂起，直到去调用 future.get() 或 future.wait() 的那一刻，它才会在调用者所在的线程（通常是主线程）里同步执行
```

#### std::future：

std::async 不会立刻给结果，而是返回一个 future 对象
由 std::async 产生的 future，其析构函数会一直阻塞，直到异步任务执行完毕

##### future.get()：

提取结果，它内部使用的是移动语义旦提取完成，这个 future 对象内部的共享状态就被清空了，再次提取会报错。

##### future.wait()：

如果你只是想等后台任务干完活，不需要返回值，用 wait()。它可以被调用多次。（调用get后也不能用）

```
std::future<int> result_future = std::async(std::launch::async, complex_calculate, 10, 20);
```

## 锁：

保护共享资源、协调执行顺序、强制刷新 CPU 缓存
操作系统提供的锁，底层自带了非常强硬的内存屏障。当你执行加锁和解锁时，它会强制把当前 CPU 核心缓存里的脏数据刷入主内存，并让其他核心的缓存失效。

### 底层：原子操作。

### 互斥锁

C++ 中，通常使用 std::mutex 来实现互斥锁。

#### 优缺点：

优点：适合高并发访问阻塞等待
缺点：性能开销大，会造成死锁，导致线程堵塞

```
std::mutex w_mtx;， mtx.lock(),mtx.unlock()
```

### 自旋锁

一种非阻塞的锁，线程它会在循环中忙等待（即持续检查锁是否可用）

#### 优缺点：

优点：适合锁持有时间非常短，切换上下文开销低，高性能需求。读写锁允许多个线程同时读取共享资源，但当有线程写入时，其他线程无法读取或写入。适用于读操作远多于写操作的情况

### CAS

一个硬件级别的原子指令。它包含三个操作数：内存位置 V、预期原值 A、新值 B。如果 V 的值等于 A，就将 V 更新为 B；否则不更新。整个过程不可中断

#### 问题：ABA问题

eg：一个栈，栈顶：AAB，线程1想把最上面的A改为B，但在执行CAS前一帧，线程2pop了栈顶，就会变成BB

#### 解决措施：版本号。CAS比较（值，版本号）

#### weak和strong区别：

前者允许伪失败，即因为硬件指令导致CAS并没有成功

### 读写锁：

#### 底层：

核心是维护一个共享状态：
reader_count：当前读者数量
writer_active：是否有写者持有
waiting_writers：等待写者数量

#### 规则：

读-读：允许并发
读-写：互斥
写-写：互斥

#### 利用自旋锁或者互斥锁来实现

### 原子操作：

每次加锁/解锁，如果发生线程阻塞，都会触发操作系统的上下文切换 (Context Switch)，这对追求极致帧率的引擎来说，开销太大了。

#### 解决办法：atomic原子指令

atomic 直接翻译成 CPU 硬件级别的原子指令。它锁住的是主板上的内存总线，速度比 mutex 快几个数量级。
原子操作是不可分割的最小操作单元。在它执行的过程中，绝对不会被操作系统的线程调度机制打断。

#### 原子操作底层：

锁住这个变量所在的 cache line，让当前核心独占修改，其他核心暂时不能同时改这一行，核心 A 会让其他核心缓存里的这条 cache line 失效，然后自己独占它。CAS 是 CPU 原子指令，不会被打断，大部分操作都基于CAS来进行

#### 使用：

std::atomic 是一个模板类，可以把普通变量包装成“原子变量”。对它的操作，CPU 会保证是一气呵成的，绝不会被其他线程打断。

```
std::atomic<int> global_counter{0};
load()：原子地读取值。
store(val)：原子地写入值。
fetch_add(val) / fetch_sub(val)：原子地加/减，并返回旧值
compare_exchange_weak / strong (CAS操作)如果 CAS 发现 islock 里面的值和 expected 不一样（比如 islock 是 true，expected 是 false），它会强行把 expected 修改为 islock 里的当前真实值（也就是 true）。
```

#### 内存序：默认使用最严格的内存序

Cpu为了优化性能，会乱序执行代码，并将数据放在L1L2中，其它的不知道，因此需要依靠内存序来补充。

#### 内存序底层：

##### 1.禁止乱序重排：

```
现代 CPU 不会让每次写入都立刻到达内存条。
CPU 核心
   ↓
Store Buffer
   ↓
L1/L2 Cache
   ↓
缓存一致性网络
   ↓
其他核心
执行 data = 42 时，写入可能暂时停在 Store Buffer。后面的操作可能继续执行；Load 也可能被提前、推测执行。因此，不同核心可能暂时看到不同地址的不同顺序。
此外，编译器也可能在不影响单线程结果的前提下调整指令顺序。
```

##### 缓存一致性只能保证同一个地址

```
MESI/MOESI 等协议大致保证：
修改缓存行前，核心先取得独占所有权。
其他核心中的相同缓存行被失效。
对同一个原子变量，所有线程认可一致的修改顺序。
但它不能单独保证不同地址之间的顺序：
data = 42;   // 地址 A
ready = true;// 地址 B
其他核心可能先看到地址 B 的变化，再看到地址 A 的变化。这正是内存序要解决的问题
```

##### 实现方法：

```
C++ memory_order
        ↓
限制编译器重排
        ↓
生成对应的原子指令/内存屏障
        ↓
约束 Store Buffer、Load 推测等硬件行为
        ↓
配合缓存一致性协议传播数据
        ↓
实现 happens-before 和跨线程可见性
```

##### 使用：ready.store(true, std::memory_order_release);

```
memory_order_relaxed：只保证对当前这一个 atomic 变量的操作是原子的
```

```
memory_order_acquire 和 memory_order_release（成对使用
```

Release（释放/发布，用于写操作）： 保证在这一行代码之前的所有内存读写，绝不会被重排到这一行之后。它就像一记发令枪，告诉你：“我前面的数据都准备好了！

#### mutex与atomic：

##### mutex：

std::mutex 是互斥锁，std::shared_mutex 更接近读写锁，自旋锁更多是实现策略或自定义封装
适用：保护一整段临界区保护多个变量之间的一致性，适合复杂共享状态修改通常获取不到锁时，线程会阻塞/挂起等待

##### atomic：

atomic 不只是定义变量，更关键是：对该对象的读写、读改写操作具备原子性，并可配合内存序建立线程间同步关系
适用：适合单个变量的原子读写、计数器、标志位、简单无锁结构，优点是避免了传统互斥锁的加解锁开销，但它只保证原子操作本身，不自动保证“多个变量共同满足某个业务不变量

## UE多线程：

核心：分为命名线程和工作线程
命名线程是具有固定身份和职责的线程，例如 Game Thread、Render Thread 和 RHI Thread，任务对这些线程具有明确的线程亲和性。Worker Thread 则是任务调度器线程池中的通用执行线程，任务通常提交到 AnyThread，由调度器选择空闲 Worker。命名线程负责线程专属状态，Worker 适合执行无固定线程依赖、基于线程安全数据或快照的并行计算。

### 调度器：LLT

LLT 是 UE5 底层的 CPU 任务调度器。它不是“创建线程”的接口，而是把大量短任务调度到一组共享 Worker Thread 上执行。
