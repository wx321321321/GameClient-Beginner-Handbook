# STL

STL 是一套“数据结构 + 通用算法 + 统一访问方式”的框架，主要三个部分是容器算法迭代器，目的是让算法和数据结构解耦。核心思想是容器负责存数据，算法负责处理数据，迭代器负责把两者连起来

#### vector

##### 底层：内部只有三个指针
```
_M_start (起始指针)： 指向这块连续内存的绝对开头。也就是第 1 个元素的地址。
_M_finish (存活边界)： 指向最后一个有效元素的下一个位置。
_M_end_of_storage (容量边界)：
```          
指针一般在栈上，分配的空间在堆上
##### 特点：连续内存，支持随机访问，push_back 快，尾插尾删高效，中间插入删除慢，扩容可能导致迭代器失效

##### 迭代器失效：rehash、插入（插入点及之后的迭代器失效），删除（指向被删除元素以及删除点之后的迭代器失效）

##### shrink_to_fit() ：
shrink_to_fit() 只是一个非强制请求，标准不保证一定把 capacity 缩到 size，也不保证采用哪种方式实现。对于 vector 来说，如果真的发生缩容，通常可能通过重新分配一块更小的连续内存、再移动元素来完成，因此地址可能变化；也可能实现直接不处理。所以不能假设它一定在原地址上缩
其它缩容方法：新建数组swap
##### push_back和emplace_back()：
``` 
push_back：先构造，后拷贝/移动，会尊重 explicit
emplace_back：直接在目的地构造

emplace_back 利用了 C++ 的参数转发。如果你传入的是已经存在的对象（左值），比如 
Item obj; 
v.emplace_back(obj);
那么它依然会调用拷贝构造，此时和 push_back 没有区别。
如果是右值，则直接在目的地构造，emplace_back 会无视 explicit
``` 
##### 扩容性能优化：
如果搬移数量过多:将原table中的数据分开几部分，分别在插入·查找删除时候一次搬入一部分。

##### reserve与resize

reserve(8) 的单位是 8个元素，不是8字节。它保证 capacity >= 8，但不改变 size，也不构造对象。
resize(4) 把 size 调整为4。如果原来有2个元素，只新构造2个；如果原来有6个，则销毁末尾2个，并不一定重新分配空间。
##### vector<bool>
``` 
vector<bool> 不是普通的 vector<T> 行为模型，它是标准库专门做的一个特化（specialization），目的是按位压缩存储 bool。
普通 vector<int>：每个元素真的是一个 int 4B
普通 vector<char>：每个元素真的是一个 char 1B
但 vector<bool>：每个元素通常只占 1 bit，不是 1 byte
``` 
``` 
vector<bool> 里的元素通常不是“真实的 bool 对象”，而是“某一位”。
这会直接导致一个很关键的问题：vb[i] 返回的往往不是 bool&，而是一个代理对象（proxy object）
先看普通 vector<int>：
vector<int> v = {1, 2, 3};
int& x = v[0];
x = 10;
这里 v[0] 返回的是一个真正的 int&。但 vector<bool> 不行，因为：
一个 bit 没法单独拥有地址也没法返回“真正的 bool&”

所以它通常返回一个类似这样的东西：
“我代表第 i 个 bit，你对我赋值时，我帮你改对应那一位；你读我时，我帮你转成 bool”
也就是代理类，比如标准库里常见叫：
std::vector<bool>::reference
``` 
坑
``` 
1：operator[] 返回的不是 bool&
vector<bool> vb(10);
bool& b = vb[0];
你会得到编译错误。

坑 2：不能正常取元素地址
普通 vector<int>：
vector<int> v = {1,2,3};
int* p = &v[0];
但 vector<bool>：
vector<bool> vb = {true, false};
bool* p = &vb[0]; // 通常不行
因为 vb[0] 不是一个真正的 bool 对象。

```

##### vector扩容：

```

        ↓
```

#### deque 双端队列。

##### 特点：支持头尾高效插入删除，支持随机访问，通常不是整体连续内存
##### 底层：分段连续内存，首先是一个中控数组，连续的内存空间，指向真正数据块的目录，第二个，数据缓冲区，离散在内存中。

##### 解决扩容：O1
如果最后一个 Chunk 还没满，直接塞进去。如果满了，deque 绝对不会去搬运旧数据！它只会向操作系统申请一个新的 Chunk，然后把这个新 Chunk 的地址记录到“中控数组”的尾部。
##### 头插：O1
申请一个新的 Chunk，把地址记录到“中控数组”的头部，然后把数据写进新 Chunk 的最后面
在底层引入了一个极其聪明的“相对坐标系”概念：内部起始偏移量 
##### 中控数组满了：
中控数组确实会发生类似 vector 的扩容（申请一个更大的指针数组，把原来的指针拷过去）。但注意：拷贝指针的速度极快，真正海量的数据块（Chunks）在内存中纹丝不动！
##### 代价：
被拖慢的随机访问：算出目标数据在第几个 Chunk 里，去中控数组里查到那个 Chunk 的真实内存指针，算出目标在这个 Chunk 内的偏移量
解决办法：在游戏引擎中可以参考ringbuffer来进行，如果知道队列的最大可能长度的话，双指针加取余。
##### 迭代器失效：
插入：迭代器失效（中控数组可能扩容，而deque的迭代器封装了中控数组的指针），指针和引用绝对不失效
中间插入：
迭代器、指针、引用全部失效。因为要在某个 Chunk 中间硬塞数据，必须强行挪动其他元素
##### 一个块大小：标准库实现里会写一个规则，类似：
每块尽量占固定字节数，再根据 sizeof(T) 算每块放几个元素
#### list：双向链表。

##### 特点：不支持随机访问，中间插入删除快，迭代器稳定性较好，额外指针开销大
##### 底层
链表（通常是双向链表）已知位置插入 / 删除本身很快插入删除不会像 vector 那样整体搬移元素。不支持随机访问每个节点有额外指针开销内存不连续，缓存不友好实际遍历时常常更慢
##### 为什么工程里经常更偏向 vector
因为真实程序里，性能往往不只看理论复杂度vector 连续存储，对 CPU cache 更友好遍历、排序、批量处理通常都更快很多“频繁插入”其实是尾插，vector 也很适合就算是中间插入，如果数据规模和模式合适，vector 依然常常比 list 更实用
#### array:定长数组封装。
``` 
array<int, 3> a = {1, 2, 3};
``` 
##### 特点：大小固定,底层连续,比原生数组更“STL 化”

##### int A[10]
内存位置： 栈区（Stack）。内存绝对连续
缺点：退化为指针,没有边界检查,运行期（动态）越界： 你写 A[a] = 5;（越界访问），编译器大概率连个警告都不给
##### std::array<int, 10>
来完全替代 int A[10]。内存位置： 栈区（Stack）。内存绝对连续
底层源码就是包了一层 struct { int _M_elems[10]; }。这意味着它依然是 40 字节，没有任何额外的性能和内存开销
绝不退化： 传参时它依然是一个完整的对象
支持迭代器，可以直接套用 std::sort 或基于范围的 for 循环
使用at会进行检查，追求性能也可以直接括号。
##### std::vector<int>(10):
对象指针在栈上，但对象连续内存在堆上
堆分配开销： std::vector<int>(10) 在创建时，不仅调用了构造函数，还会默认初始化： 注意，写成 (10)，它不但分配了 10 个空间，还会把这 10 个整数默认初始化为 0（这又是一笔遍历写入的开销）

##### cpp STL优化：
C++ 的红黑树实现通常会在根节点之上再加一个红色的 Header 节点。它的 parent 指向真正的 Root，它的 left 指向树的最左节点（即最小值），right 指向最右节点（即最大值）

#### 哈希表：
##### 本质是：
用一个 哈希函数把 key 映射成数组下标，从而把“查找”从 O(n) 变成平均 O(1)。但它的性能好坏几乎全靠：哈希函数、装载因子、冲突处理、扩容策略
##### 桶：
在底层其实就是一个连续的动态数组，类似于一排带编号的抽屉，根据输入键计算出hash值，去找编号，再将节点放入抽屉，节点cpp中在堆上创建。
##### C++标准库采用了拉链法：
桶里面存放的不是元素本身，而是一个指针。这个指针指向一条单向链表果发生了冲突，就把新来的元素包装成一个链表节点（Node），然后“挂”在这个桶对应的链表上
##### 冲突解决：
#### 链地址法
每个桶存一个链表/小数组/小vector，冲突就挂到桶里。
链表中的节点通常是通过 new 或 malloc 动态分配的。这意味着，同一个桶里的节点，在物理内存上大概率是随机散落的，很大概率出现cachemiss。频繁newdelete造成大量内存碎片
##### 解决办法：自己用malloc写内存池，使用定位new，每一个哈希值都对应一大块空间
##### 优点：无论装载因子多高（甚至 > 1.0），它都能稳定工作（大不了退化成链表）。
#### 开放定址法
桶数组里直接存元素，冲突就“找下一个空位”。
##### 优点
所有的元素都紧凑地存放在一整块连续的数组内存中。冲突了按规则往后找下一个空位
##### 缺点：
聚集现象  主聚集： 当采用线性探测时，如果连续几个槽位被占了，接下来的元素大概率也会撞上去，导致这一块越来越拥挤，形成“连成一片”的拥堵区。这会导致查找冲突的时间复杂度从 O1急剧恶化
##### 罗宾汉哈希
每个元素在插入时，不仅记录数据，还记录一个PSL（探测序列长度），也就是它距离自己原本“该待的那个理想桶”有多远
如果它遇到了一个已经存在的元素，发现自己的 PSL 居然大于那个它的 PSL，新元素就会毫不客气地把它踢走，自己霸占那个位置。
这种算法极其平滑地分配了所有元素的查找成本。没有人的查找路径会特别长（方差极小），从根本上解决了极端拥堵导致的性能暴跌
#### rehash 触发条件通常是装载因子超过阈值
##### 流程：
建新桶： 在内存中申请一块全新的、长度为 16 的连续数组（新桶）。
重新分配（解链与重链）： 遍历旧的桶数组，顺藤摸瓜找到每一个链表节点。
计算新位置： 对于每一个节点，用它的 Key 重新对 16 取模，算出一个新的桶编号
改写指针： 哈希表根本不会去销毁这个节点，也不会去 new 一个新节点把数据拷过去。 它仅仅是把这个节点从旧的链表上“摘”下来，然后修改它的 Next 指针，把它“挂”到新桶对应的链表上。
销毁旧桶： 所有节点都转移完毕后，把那块长度为 8 的旧数组（旧桶）销毁。

##### 迭代器失效：
1.rehash（但是指向元素的指针（Pointers）和引用（References）依然有效）
2.删除，只有对应迭代器失效。

## 迭代器：
##### 可以看作为：一个统一访问容器元素的位置对象
```
vector 用下标
list 没法随机下标
set 也没有下标
```

### 迭代器分类：

#### 输入迭代器（Input Iterator）

##### 特点：只能读 单向前进

##### 常见场景：从输入流里读数据
```
最典型例子：istream_iterator
#include <iostream>
#include <iterator>
using namespace std;
int main() {
    istream_iterator<int> in(cin);
    istream_iterator<int> end;

    while (in != end) {
        cout << *in << endl; // 读当前输入的值
        ++in;                // 继续读下一个
    }
}
```

#### 输出迭代器（Output Iterator）

##### 特点：只能写,单向前进
##### 常见场景：把数据写到某个地方
```
最典型例子：ostream_iterator
#include <iostream>
#include <iterator>
#include <vector>
using namespace std;

int main() {
    vector<int> v = {1, 2, 3};

    ostream_iterator<int> out(cout, " ");
    for (auto x : v) {
        *out = x; // 写到输出流
        ++out;
    }
}
```
##### 工作流：数据像水一样，按顺序流动。
cin 是 输入流，默认从键盘读数据。cout 是 输出流，默认往屏幕/控制台写数据
```

cout << x
把数据“送进去”输出流
```
为什么叫“流”：因为数据不是一下子全给你，而是一个一个顺序经过
cin 是系统已经帮你定义好的标准输入流对象，一般不用你自己定义


#### 前向迭代器（Forward Iterator）
##### 特点：能读能写只能往前可以多次遍历

#### 双向迭代器（Bidirectional Iterator）

##### 特点：能前进 ++it，也能后退 --it
```

#include <iostream>

```

### 寻路算法总结：

#### BFS：队列，按距离分层。O(V+E)
适用范围：
- 无权图
- 所有边权相同且非负，通常认为都是 1
如果所有边权都是相同正数 c，BFS 找到最少边数后乘以 c 即可。

#### Dijkstra：每次确定当前距离最小的节点，贪心算法。O(V+E)logV
适用范围：所有边权 >= 0，允许权重为 0，但不允许负边。
维护两类节点：
- 已确定最短距离的节点
- 只有暂定距离、还未确定的节点
每次从未确定节点中取出 dist 最小的节点 u：u 是当前最有希望被最终确定的节点，然后松弛 u 的所有出边。
过程：
```
假设：
A -> B，权重 4
A -> C，权重 1
C -> B，权重 2
B -> D，权重 1
C -> D，权重 5
初始化：
dist[A] = 0
dist[B] = ∞
dist[C] = ∞
dist[D] = ∞
处理 A：
dist[B] = 4
dist[C] = 1
选择最小的 C：
dist[B] = min(4, 1+2) = 3
dist[D] = min(∞, 1+5) = 6
选择最小的 B：
dist[D] = min(6, 3+1) = 4
最终：
A = 0
C = 1
B = 3
D = 4
```
负边可以让一个当前距离更大的节点，之后反过来把已确定节点的距离降低。这破坏了 Dijkstra 的贪心前提

#### A*：带方向感的 Dijkstra
```
Dijkstra 选择：
g(n) 最小的节点,其中：
g(n) = 起点到当前节点 n 的已知代价
A* 选择：f(n) = g(n) + h(n)
其中：
g(n)：起点到 n 的实际已知代价
h(n)：从 n 到目标的预计剩余代价（启发函数）
f(n)：经过 n 到达目标的预计总代价
所以 A* 不只是看“我已经走了多远”，还看“我离终点大概还有多远”。
```
##### 常见启发函数 h(n)
常见网格启发函数如下。
四方向移动：曼哈顿距离 只能上下左右：h = abs(x1 - x2) + abs(y1 - y2);
任意方向移动：欧几里得距离 h = sqrt(dx * dx + dy * dy);
八方向网格：对角距离 可以横、竖、斜向移动时，可以使用：max(|dx|, |dy|)
##### 可采纳性
为了保证 A* 得到最优路径，启发函数通常要求：h(n) <= n 到目标的真实最短距离
这叫可采纳 Admissible。也就是：可以低估，但不能高估。
例如真实还需要走 10：
h(n) = 7    可以
h(n) = 10   可以
h(n) = 15   通常不保证最优
为什么不能高估？
因为高估可能让算法错误地认为某条实际上很好的路径代价太高，从而提前选择其他次优路径。
##### 一致性
更强的条件是：h(u) <= w(u,v) + h(v)这叫一致性 Consistent。
可以理解为启发函数满足三角不等式。
如果启发函数一致，那么：
f(n) = g(n) + h(n)
沿路径不会下降，节点第一次正式取出时就可以确定。
常见的曼哈顿距离、欧几里得距离，在移动代价匹配时通常是一致的。
##### A* 与 Dijkstra 的关系
如果：h(n) = 0那么：f(n) = g(n)
A* 就完全退化成 Dijkstra。
如果：h(n) = 真实剩余最短距离那么 A* 几乎可以直接沿着最优路径前进。
因此：
h 越准确，搜索越少
h 越保守，越接近 Dijkstra
h 高估过多，可能失去最优性


#### Bellman-Ford 允许负权边 O(VE)
流程：
```
Bellman-Ford 不贪心地确定某个节点，而是：
重复扫描所有边，不断用更短的路径更新距离。
假设最短路径最多经过 V-1 条边。
Bellman-Ford 每扫描一轮所有边，可以保证：
第 1 轮：找到最多经过 1 条边的最短路径
第 2 轮：找到最多经过 2 条边的最短路径
第 3 轮：找到最多经过 3 条边的最短路径
第 V-1 轮：得到所有不含环的最短路径
这其实可以看成动态规划。
```
Dijkstra 的问题在于，它会过早地宣布：当前距离最小的节点已经确定，以后不会再变
但这个不会。
